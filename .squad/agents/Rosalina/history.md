### 2026-09-20: Phase 4 QA rulings (§15) — the best fix was one layer below the reported bug
Toad found the wizard asserting *"isn't used by any other mystery"* when the mystery-name lookup had failed — false, on the sentence Detach-vs-Delete is decided from, on an irreversible action. **I was asked to write "couldn't check" copy and to rule on whether the three-button row survives an untrustworthy count. Also: **a trailing colon promises a list**, so the names-missing sentence ends in a full stop — a colon above an empty block is its own small lie.
**Explicitly diverged from my own §14.1 precedent, and said so in the doc.** That ruling (one string, no "Still checking…") rested on `pendingDelete` being an open-time *snapshot* so a progress message could never progress. ### 2026-09-20: Phase 4 design-review ceremony (facilitated; output is §14 of `docs/updates/mystery-entity-linking-ux.md`)
**Facilitation lesson that paid off immediately: read the *committed code*, not the plan for it.** Three of my Phase 4 specs turned out to hinge on as-built details no document mentioned. (1) **`message` still defaults to `'This cannot be undone.'` even though `footnote`'s default was changed to `''`.** So a wizard removal that passes no `message` silently renders a sentence my own §7.3 says is *false* there (removal is deferred, so "cannot be undone" isn't true yet). ### 2026-09-18 second addendum: corrected a real mistake — `fill="currentColor"` is not the same claim as "filled silhouette"
Shipped filled `icon-wizard` was rejected by Skyler on sight ("outline-driven and a little cartoony/low-fidelity... the only icon that is filled in is the favicon"). Root cause, confirmed directly in `icon-sprite.component.ts`: I classified `icon-trash`/`icon-pencil` as "solid filled silhouettes" purely from their `fill="currentColor"` attribute, without looking at what the path geometry actually draws. Both are **outline drawings expressed as a filled path with counters cut out of it** (trash: hollow lid + hollow tapered body; pencil, `fill-rule="evenodd"`: hollow ruled lines + an open page-fold cutout) — a real, legitimate SVG technique, but it reads as an outline icon, not a filled one. **Lesson for next time: `fill`/`stroke` attributes are not sufficient evidence of an icon's visual register — render the path (or at minimum trace what the geometry implies: closed counters/subpaths inside a fill = hollow outline-by-subtraction, not solid) before generalizing "this family is filled."** The app's actual, unambiguous filled/outline split is: every `icon-nav-*`/`icon-mystery-*` symbol plus `close`/`menu`/`plus` is genuine `fill="none" stroke="currentColor"` outline (that's the real dominant system, `1.8` nav/mystery-section, `2` for close/menu/plus); `icon-trash`/`icon-pencil` are outline-by-subtraction wearing a `fill` attribute; only `icon-logo` (the favicon/brand mark, hardcoded hex) is a genuinely filled, deliberately one-off exception. `icon-trash`/`icon-pencil`'s odd non-standard viewBoxes (`0 40 32 32`, `0 0 100 100`, vs. everything else's clean `0 0 24 24`) were a second signal I noted but under-weighted — non-standard viewBox is a decent tell that an icon was imported rather than authored to this app's own system, worth treating as a flag next time. Redrew the hat as true outline (`viewBox 0 0 24 24 fill=none stroke=currentColor stroke-linecap/linejoin=round stroke-width=1.8`, matching the mystery-section — not nav — flavor specifically because round caps read closer to Skyler's "cartoony/low-fidelity" ask than the nav rail's sharp corners): two strokes only, a closed triangle cone + one open brim curve, reusing the `icon-wizard` symbol ID Luigi already wired up (only the markup inside changes). Doc corrected in place with strikethroughs, not silently rewritten — `docs/design/mystery-wizard-icon-concepts.md` Section 5 is now the live recommendation, Sections 1-4 kept as a marked-up record of the mistake.

### 2026-09-17: Cross-domain asset links — `.entity-link` (advisory; spec in decisions/inbox/rosalina-cross-domain-link-style.md)
Skyler reported "no hover effects" on `/mysteries/{id}` asset links. The real finding is larger and worth remembering: **this app has no anchor style at all.** Tailwind preflight resets `a { color: inherit; text-decoration: inherit; }` and nothing ever re-established it — grep for `a {`/`a:hover` across `styles.css` and every component `.scss` returns nothing. So a bare `<a [routerLink]>` renders as plain body text; `mystery-detail.html`'s four asset lists (monsters/minions/locations/bystanders, lines 88/108/129/149) are literally undiscoverable except by cursor change. Three inconsistent one-off workarounds had grown around the gap: `dashboard.html:50` `text-accent font-semibold no-underline`, `minions-list.html:23` `text-inherit underline`, and everywhere else bare `font-semibold`. Reusable facts: (1) `--color-accent` is the only entity-link color already shipping (dashboard), so it's the house precedent, not an import — 6.29:1 light, 6.11:1 dark. (2) **`ring-focus` is the wrong focus indicator for a bare text link.** `--color-focus-ring` is indigo@20% alpha and every existing consumer pairs it with `focus:border-accent` — the border does the contrast work, the ring is only a glow. On a borderless link it'd be the sole indicator at ~1.3:1 and fail 2.4.11. Use `outline: 2px solid var(--color-accent); outline-offset: 2px` instead; `outline` also survives inline line-wrap where `box-shadow` doesn't. (3) The app's house transition is Tailwind's `transition-colors` = 150ms `cubic-bezier(0.4,0,0.2,1)`, and in v4 that property list *includes* `text-decoration-color` — so an underline that fades in on hover is expressible with the existing utility, no new timing invented. (4) Put it in `@layer components` in `styles.css`, unlike `.action-btn` which is un-layered: these anchors already compose call-site utilities (`font-semibold`, `text-[1.1rem]`), and an un-layered class would out-specify them. (5) Genuine gap found: `playbookName` renders as a `bg-badge-playbook` chip with no link in `hunter-detail.html:12`/`hunters-list.html:20`, and there is no `playbooks/:id` route in `app.routes.ts` — the one real cross-domain relationship with zero navigation. (6) Live nit: `mystery-detail.html:149-151` puts the anchor text on its own line, so the anchor captures leading/trailing whitespace and any underline renders with a trailing gap — must be collapsed to one line.

### 2026-08-02: Dark Theme Palette — Values for Yoshi's Token Catalogue
Produced `docs/theming/dark-theme-palette.md` filling in every token in `docs/theming/theming-plan.md`'s Token Catalogue. Key calls, for future reference in this codebase:
- Dark neutrals stay in the `slate` family (not `zinc`/black) — matches existing light-mode identity. Elevation via a 3-step lightness ladder: `surface-sunken` (slate-950, darkest) → `surface` (slate-900) → `surface-raised` (slate-800, lightest) — inverted-feeling but intentional, since shadows don't read well on dark backgrounds.
- Accent/danger both *lighten* for dark mode (`indigo-600`→`indigo-400`, `red-600`→`red-400`) with `on-accent` flipping from white to `slate-900` — a single token can't be both "good button fill" and "good text-on-dark-surface" at the same darkness the way it can on a white background. Hover moves lighter, not darker, once base tokens are already light tints (opposite of light mode's darken-on-hover).
- Type badges (monster/minion/bystander/location) keep their light-mode hue family in dark mode, just inverted to deep-bg/light-text — reasoning: they're a memorized legend, and the theme toggle re-colors live with no reload, so a hue swap between themes would make a badge appear to "change identity" mid-toggle.
- Found a real gap: Yoshi's Phase 5 illustrative striping fix (`--color-surface`/`--color-surface-sunken` for table zebra rows) collapses to ~1.13:1 in dark mode — those two tokens are a coarse elevation jump, not fit for fine per-row alternation. Recommended `--color-accent-subtle` for even rows instead (also closer to the original literal `#dbeafe` pale-blue-wash intent than a neutral surface token would have been).
- Found an uncataloged badge: `monster-archetype` badge (`purple-100`/`700`, added post-migration-docs) has no token in Yoshi's catalogue at all and would stay light-only silently. Flagged for catalogue addition, not added myself.
- Flagged a token gap: no `--color-on-danger` exists in the catalogue, but is needed once `--color-danger` lightens (confirm-delete button's white text would fail against a lightened red fill otherwise).
- Did the WCAG contrast math by hand for the highest-traffic pairings rather than hand-waving it — worth it, it directly overturned my first-choice toast green (`emerald-600` failed AA with white text at ~3.77:1; `emerald-700` passes at ~5.49:1).
