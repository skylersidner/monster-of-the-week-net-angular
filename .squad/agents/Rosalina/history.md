### 2026-08-23: Favicon direction (advisory, not implemented) — redraw as solid mark, don't export nav sprite
Skyler asked whether the favicon should just reuse `icon-nav-monsters` or be a new mark that could also replace the "MOTW" text pill. Recommendation: redraw, don't export. `icon-nav-monsters` is `stroke-width="1.8"` line art tuned for 24px nav rail — the mouth stroke and thin horn lines will mush/vanish at 16px favicon size, and `currentColor` strokes have no inherent contrast on a static baked asset (browser tab chrome varies light/dark, unlike DOM context). Recommended: solid-filled silhouette (same horn+trapezoid vocabulary, drop the mouth line) on a filled `indigo-600` chip, not transparent — guarantees contrast on any tab bar. On unifying with the MOTW pill: worth doing, not just cosmetic — found a real reason in `docs/simple-authentication-update/architecture.md`/`open-questions.md`: `AuthLayoutComponent` was explicitly told *not* to copy MOTW's classes because `bg-white/20 text-white` (translucent-white-on-indigo) is invisible on `bg-surface-sunken` — the current pill only works because it's guaranteed to sit on an indigo backdrop (sidebar/drawer), it doesn't travel to the login page which already needs its own logo. A solid-fill badge mark (not translucent-over-indigo) would be portable to any background and could serve as both favicon and logo, closing that already-surfaced gap.

### 2026-08-02: Dark Theme Palette — Values for Yoshi's Token Catalogue
Produced `docs/theming/dark-theme-palette.md` filling in every token in `docs/theming/theming-plan.md`'s Token Catalogue. Key calls, for future reference in this codebase:
- Dark neutrals stay in the `slate` family (not `zinc`/black) — matches existing light-mode identity. Elevation via a 3-step lightness ladder: `surface-sunken` (slate-950, darkest) → `surface` (slate-900) → `surface-raised` (slate-800, lightest) — inverted-feeling but intentional, since shadows don't read well on dark backgrounds.
- Accent/danger both *lighten* for dark mode (`indigo-600`→`indigo-400`, `red-600`→`red-400`) with `on-accent` flipping from white to `slate-900` — a single token can't be both "good button fill" and "good text-on-dark-surface" at the same darkness the way it can on a white background. Hover moves lighter, not darker, once base tokens are already light tints (opposite of light mode's darken-on-hover).
- Type badges (monster/minion/bystander/location) keep their light-mode hue family in dark mode, just inverted to deep-bg/light-text — reasoning: they're a memorized legend, and the theme toggle re-colors live with no reload, so a hue swap between themes would make a badge appear to "change identity" mid-toggle.
- Found a real gap: Yoshi's Phase 5 illustrative striping fix (`--color-surface`/`--color-surface-sunken` for table zebra rows) collapses to ~1.13:1 in dark mode — those two tokens are a coarse elevation jump, not fit for fine per-row alternation. Recommended `--color-accent-subtle` for even rows instead (also closer to the original literal `#dbeafe` pale-blue-wash intent than a neutral surface token would have been).
- Found an uncataloged badge: `monster-archetype` badge (`purple-100`/`700`, added post-migration-docs) has no token in Yoshi's catalogue at all and would stay light-only silently. Flagged for catalogue addition, not added myself.
- Flagged a token gap: no `--color-on-danger` exists in the catalogue, but is needed once `--color-danger` lightens (confirm-delete button's white text would fail against a lightened red fill otherwise).
- Did the WCAG contrast math by hand for the highest-traffic pairings rather than hand-waving it — worth it, it directly overturned my first-choice toast green (`emerald-600` failed AA with white text at ~3.77:1; `emerald-700` passes at ~5.49:1).

### 2026-08-02: `--color-surface-hover` dark value (Yoshi's catalogue addition)
Picked `slate-700` (`#334155`) for the dark value of this later-added token (light = `gray-200`, Skyler's call, converged across 6 sites). Gotcha worth remembering: the *obvious* next step up the elevation ladder (`slate-800`) is already `--color-surface-raised` — since the confirm-delete modal's Cancel button sits directly on that surface, reusing `slate-800` as its hover fill would make the hover invisible there. Went one step further to `slate-700` instead (also `--color-border`'s value — accepted as a minor, non-functional coincidence, unlike the `slate-800` collision which would've been a real bug). Lesson: when adding one new token to an already-designed ladder, always check it against *every* surface it'll render on top of, not just the nearest one.

### 2026-08-03: `--color-badge-mystery`/`--color-on-badge-mystery` — kept amber, not my own teal proposal
My original palette doc floated `teal-100`/`teal-800` (light) / `teal-950`/`teal-300` (dark) as a placeholder for this reserved token, under the assumption "mysteries don't have a type badge today." That assumption was already stale when I wrote it: `mysteries-list.html`, `mystery-detail.html`, `mystery-create-dossier.html`, and `search-results.ts`'s domain-badge map all already render `mystery.adventureType.name` via a literal `bg-amber-100 text-amber-700` chip — and it appears side-by-side with every other domain badge on the global search page, the exact scenario hue-collisions matter most. Lesson: **always grep the actual templates for a token's real usage before trusting a Catalogue row's "n/a"/"reserved" framing** — a token being unfilled doesn't mean the feature doesn't exist yet, it may just mean nobody's pointed the existing literal at it. Re-litigating the hue once I saw amber was real: kept amber rather than switching to teal — my own hue-preservation philosophy (don't let an already-shipped badge "swap identity" between themes) applies just as much to *adopting* a token as to picking dark values for one, and checking the actual amber-vs-orange hex values side by side (light: `#fde8d8`/`orange-800` vs `amber-100`/`amber-700`; dark: `orange-950`/`orange-300` vs `amber-950`/`amber-300`) showed the adjacency I'd worried about in the abstract holds up as visually distinct in practice. Values: light `amber-100`/`amber-700` (unchanged, already shipping), dark `amber-950`/`amber-300` (~10.4:1). Also hand-verified the light pairing for the first time (~4.51:1, passes AA but tightly) since I'd never actually checked it before — it had been shipping un-vetted.
