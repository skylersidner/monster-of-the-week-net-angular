### Global Search Phase 1 — backend endpoints + ranking (2026-08-01) — requested by Skyler Sidner, design in docs/search/{architecture,phases,open-questions}.md
- New `Services/Search/` folder: `ISearchProvider`/`SearchMatchCandidate`/`SearchFieldWeight` (`ISearchProvider.cs`), `SearchTokenizer`/`SearchMatchTier` (tokenize + 4-tier predicates: Substring/BoundaryPrefix/StartsWith/Exact), 5 providers (Mystery/Monster/Minion/Location/Bystander), `ISearchService`/`SearchService`
- New `Controllers/SearchController.cs`: `GET /api/search/quick`, `GET /api/search`
- Added `SearchResultItemResponse`/`SearchResultDetailResponse`/`PagedSearchResultResponse` to `ApiContracts.cs`; `ToItemResponse()`/`ToDetailResponse()` + excerpt truncation helper in `ApiMappers.cs`
- Registered 5x `ISearchProvider` + `ISearchService` scoped in `Program.cs`
- **Deviation from architecture.md**: doc shows `EF.Functions.ILike` (Npgsql-only) chained `.Where()` clauses as the matching primitive. This repo's test convention (`MonsterRepositoryTests.cs`) runs repository-style tests against SQLite in-memory, not Npgsql — `EF.Functions.ILike` isn't translatable there. Went with: each provider does one unfiltered `.Select(x => new { Id, Name, <excerpt field> }).ToListAsync()` (cheap at this dataset's scale per the doc's own Section 1 reasoning), then `SearchTokenizer`'s tier predicates run as plain C# string comparisons in-memory. Fully portable across SQLite (tests) and Postgres (prod), and testable without a DB at all for the tier-matching logic itself.
- **Design addition not in the "illustrative" `SearchMatchCandidate` shape**: added an internal `ExcerptSource` (raw, untruncated) field to the record, populated by each provider (Hook??Concept for Mystery, Description for others) so `SearchService`/`ApiMappers` can build `Get`'s `excerpt` without a second DB round-trip or widening `ISearchProvider`'s interface (which the task pinned exactly). `GetQuick`'s mapper (`ToItemResponse`) just never reads it, satisfying "quick never computes excerpt."
- **Real bug caught only via manual curl against Postgres, not unit tests**: `SearchService.RankAsync` originally used `Task.WhenAll(providers.Select(p => p.SearchAsync(...)))`. All 5 providers share one scoped `MotwDbContext` (`AddDbContext` = scoped); EF Core's `DbContext` throws `InvalidOperationException` ("second operation started...") on concurrent async use of the same instance. Fixed to a sequential `foreach` + `await`. Unit tests with fake in-memory providers didn't catch this since `Task.FromResult` doesn't exercise real concurrency — **always manually smoke-test fan-out-to-multiple-providers-sharing-one-DbContext code against a real DB, not just xUnit with fakes**.
- **Backend enforces the 3-char minimum query length itself** (both endpoints return `[]`/empty page below it, or for empty/whitespace/dash-only queries), per the task's explicit spec. This contradicts architecture.md Section 2's closing note ("the backend does not reject short queries... the full results page URL must keep working if a user manually edits `?q=an`") — followed the task prompt since it repeated the requirement explicitly; flagged for Yoshi/Skyler in case that architecture.md note was meant to stand.
- Fixed a pre-existing (unrelated, already-broken-at-HEAD) compile error in `MonsterServiceTests.cs` line 23 — `UpsertMonsterRequest`'s `MonsterArchetypeId` is non-nullable `Guid`, test passed `null` (introduced in commit 6b035c2, never updated). One-line fix (`null` -> `Guid.NewGuid()`) was required just to get `dotnet build`/`dotnet test` running at all.
- Verified manually against real Postgres (`docker compose up -d postgres`, `dotnet run`): quick/full search, pagination across pages, tiered ranking (boundary-prefix beats substring), excerpt truncation (≤160 chars incl. trailing "…", word-boundary cut), below-min-length/empty/dash-only queries returning empty results — all correct.
- 39/39 tests green (4 pre-existing + 35 new Search tests), build clean with 0 warnings.

### Global Search Phase 4a — entity long-text matching + real snippets (2026-08-01) — requested by Skyler Sidner, design in docs/search/{architecture,phases,open-questions}.md
- `SearchMatchCandidate` (`ISearchProvider.cs`) grew `MatchedSubResourceName: string?` (always null in 4a, wired now so 4b doesn't reshape the record again), `Snippet: string?`, `MatchSpans: IReadOnlyList<SearchMatchSpan>`; new `SearchMatchSpan(int Start, int Length)` record. Field order: `(EntityType, EntityId, Name, MatchedField, MatchedSubResourceName, MatchStrength, Weight, ExcerptSource, Snippet, MatchSpans)` — every positional-constructor call site (5 providers + `SearchServiceTests.cs`) needed updating.
- `SearchTokenizer` gained `CandidateField` (readonly record struct: `FieldName, Text, Weight, AllowSubstringTier, SubResourceName=null`) and `PickBestMatch(fields, tokens, rawQuery)` — evaluates every field via the existing `ComputeMatchStrength`, keeps the single highest `Score = MatchStrength * Weight`, ties broken by list order (first-listed wins, since the loop only replaces on strictly-greater score).
- New `Services/Search/SearchSnippetBuilder.cs`: `Build(fieldText, tokens, matchStrength) -> (Snippet, Spans)`. WindowRadius=70 const. Anchor = 0 for StartsWith/Exact (matchLength approximated as `sum(token lengths) + (count-1)` single-space joins, since `Tokenize` discards the original separator chars so the real raw-query span can't be reconstructed exactly — fine, only affects how much trailing padding is shown, never match correctness); anchor = leftmost qualifying token occurrence for BoundaryPrefix/Substring (own `FindBoundaryPrefixIndex` mirrors `BoundaryPrefixMatches` but returns a position). Word-boundary trimming on **both** edges mirrors `ApiMappers.TruncateExcerpt`'s technique exactly (always cut back to the nearest space *within* the raw window, even if the raw cut already happened to land on a word boundary — same conservative "can't peek outside the window" behavior the existing trailing-edge trim has, so this isn't a new asymmetry, just applying the established technique symmetrically). Span-finding is a plain per-token `IndexOf` scan over the *final* snippet text (not gated by tier), then overlapping/adjacent (`span.Start <= lastEnd`) spans get merged.
- All 5 `*SearchProvider.cs`: build a `List<CandidateField>` per entity (`Name` Primary+substring-allowed, plus `Description` for Monster/Minion/Location/Bystander or `Concept`/`Hook`/`Overview`/`Notes` for Mystery — all Tertiary, substring disallowed), call `PickBestMatch`, only invoke `SearchSnippetBuilder.Build` when the winning field isn't `Name`.
- **Where the Mystery excerpt fallback chain extension actually lives — deviation from the task prompt's file list.** The prompt (and `phases.md`) say "`ApiMappers.cs`: extend the excerpt fallback chain… `Hook → Concept → Overview → Notes`." But `ApiMappers.TruncateExcerpt` only ever truncates an already-resolved `ExcerptSource` string — it has no domain-specific field-selection logic and never did (Phase 1's `Hook → Concept` fallback was already computed inside `MysterySearchProvider`, not `ApiMappers`). Extended it in the same place, `MysterySearchProvider.SearchAsync`, for consistency with the existing separation of concerns (`ApiMappers` = domain-agnostic truncation/mapping only; providers = where domain field selection lives). Behavior matches the spec exactly; only the *file* differs from the prompt's literal wording.
- `ApiContracts.cs`/`ApiMappers.cs`: new `SearchMatchSpanResponse(Start, Length)`; `SearchResultDetailResponse` gained `MatchedSubResourceName`, `MatchSpans` (inserted in the same relative positions the task spec showed); `ToDetailResponse` now maps `MatchedSubResourceName` straight through and `MatchSpans` via `.Select(span => new SearchMatchSpanResponse(...))`.
- New xUnit files: `SearchSnippetBuilderTests.cs` (window-radius-exactness via deterministic filler strings — e.g. `"beacon" + new string('x', 70)` vs `71` to pin the 70-char constant precisely rather than fuzzy-asserting a range; all 4 anchor tiers; word-boundary trimming verified via a reusable `AssertContentAlignsWithWordBoundaries` helper that checks the char just outside each ellipsis is a literal space in the source field, rather than hand-computing exact offsets — much less brittle for prose-shaped fixtures; span merge/adjacency/gap cases; a "one giant unbroken word" fallback-path test). `PickBestMatch` tests added to `SearchTokenizerTests.cs` (matches existing file's organization) including the worked "Name tier-2 (score 200) beats Description tier-4-exact (score 100)" case from the task brief, verified substring tier never fires when `AllowSubstringTier: false`, and a tie-break-by-list-order test. New `SearchProvidersTests.cs` — real SQLite-backed (`MonsterRepositoryTests.cs`'s `SqliteConnection("DataSource=:memory:")` pattern, not fakes) end-to-end coverage of `MonsterSearchProvider`/`MysterySearchProvider`: Description-only match, Name-beats-Description precedence, substring-tier-never-fires-on-long-text, Notes-only match, and the Hook/Concept-empty→Overview excerpt fallback — this goes beyond what Phase 1 did (Phase 1 only unit-tested via fakes) since the field-selection logic is now genuinely per-entity-data-dependent and worth exercising against a real EF query shape.
- Extended `SearchServiceTests.cs`: renamed the now-inaccurate `ToDetailResponse_SnippetIsAlwaysNull_AndMatchedFieldIsAlwaysName` to `_SnippetIsNull_WhenMatchedFieldIsName` (still true for Name-matched candidates, but no longer true globally now that non-Name matches populate it) + added pass-through tests for `Snippet`/`MatchSpans`/`MatchedSubResourceName`.
- Manually verified against real Postgres seed data (`docker compose up -d postgres`, `dotnet run`): `?q=an` returns real windowed snippets across Description/Concept fields with correctly-positioned `matchSpans`; `?q=stillness` confirms Name-vs-Description precedence live (Monster "All-Father Stillness" matches via Name with `snippet:null`, while a Minion/Mystery containing "Stillness" only in body text correctly show `matchedField` + populated snippet); `?q=hind` (mid-word-only fragment) returns zero results confirming substring tier is genuinely off for long text in production data, while `?q=ind` correctly boundary-matches "individuals" in a Mystery's Hook. Seed data currently has no Mystery with empty Hook+Concept, so the excerpt-fallback-to-Overview path was validated via the new SQLite integration test rather than live Postgres.

### Global Search Phase 4b — Monster/Minion sub-resource (Attack/Power/Armor/Weakness) matching (2026-08-01) — requested by Skyler Sidner, design in docs/search/{architecture,phases,open-questions}.md
- `MonsterSearchProvider`/`MinionSearchProvider`: query shape switched from a flat `.Select(x => new { Id, Name, Description })` to a nested projection that also pulls `Attacks`/`Powers`/`Armors`/`Weaknesses` (`.Select(a => new SubResourceProjection(a.Name, a.Description)).ToList()` per collection) — used a private `sealed record SubResourceProjection(string Name, string? Description)` per-provider instead of an anonymous type, purely for readability (a shared helper method that builds `CandidateField`s from the sub-resource list needed a concrete, nameable type to accept as a parameter; anonymous types with identical shape *do* unify across the same compilation, so `dynamic`/generics weren't strictly required, but a named record reads better and avoids relying on that unification detail). No `.Include()`, no `EF.Functions.ILike` — confirmed the nested-collection-projection pattern translates cleanly against both SQLite (test suite) and real Postgres (manual `docker compose up -d postgres && dotnet run` smoke test) with no code differences needed between the two.
- Both providers build one `AddSubResourceFields(candidateFields, kind, subResources)` static helper call per sub-resource kind (`"Attack"`, `"Power"`, `"Armor"`, `"Weakness"`), each producing a `{Kind}.Name` (Secondary, `AllowSubstringTier: true`) and `{Kind}.Description` (Tertiary, `AllowSubstringTier: false`) `CandidateField` per instance, both tagged with that instance's own `Name` as `SubResourceName`. `MonsterCustomMove`/`MinionCustomMove` deliberately never touched — no candidate fields added for either, per `architecture.md` Section 3's explicit exclusion. Zero changes needed to `SearchTokenizer`/`SearchSnippetBuilder`/`PickBestMatch`/the snippet-building branch in either provider — Phase 4a's machinery absorbed the larger candidate list and the `FieldName != "Name"` snippet-gate correctly as-is, exactly as the architecture doc promised.
- Extended `SearchProvidersTests.cs` (matched Phase 4a's convention of real-SQLite-backed, no-fakes tests in this file rather than fragmenting into a new file) with 15 new tests: sub-resource-Name-beats-entity-Description precedence (score 200 vs 100), an 8-case `[Theory]` over all 4 kinds × both fields confirming `MatchedSubResourceName`/`MatchedField`/`Weight` are all correct, a multiple-simultaneously-matching-sub-resources dedup test per provider (Monster: Attack exact beats Power boundary-prefix; Minion: Armor exact beats Weakness boundary-prefix), a CustomMove-exclusion regression test per provider, and a "Fire Breath"-style end-to-end test per provider that also calls `.ToDetailResponse()` to exercise the exact mapping the controller uses (no `WebApplicationFactory`/HTTP integration harness exists anywhere in this repo yet, so this is the closest true "hits the same code path as `GET /api/search`" test without inventing new test infrastructure not established by prior phases — flagged as an interpretation call, not a literal HTTP roundtrip).
- **Doc inconsistency flagged, not treated as a blocker**: `architecture.md` Section 5's worked JSON example shows `"matchedField": "Attack.Name"` paired with a `"snippet"` that reads like prose from the Attack's *Description* ("…massive lungs capable of a devastating fire breath…"), not its (short) `Name`. That can't happen with the actual shipped machinery — `SearchSnippetBuilder.Build` is always called with the *winning* field's own text (`match.Value.Text`), so an `Attack.Name` win only ever produces a snippet windowed from the Name string itself (e.g. just `"Fire Breath"`), never a different field's text. Manually confirmed live against Postgres (`?q=Force+of+Silence` → `matchedField: "Attack.Name"`, `snippet: "Force of Silence"`, exactly the Name text, not Description prose). Read the doc's example as illustrative/aspirational rather than literal-spec; implementation follows the real Phase 4a-established behavior (which the Phase 4b prompt itself confirmed needed no changes), not the doc's example snippet content.
- Manually verified against real Postgres seed data (`docker compose up -d postgres`, `dotnet run`): `?q=Force+of+Silence` → Monster "All-Father Stillness" via `Attack.Name`, `matchedSubResourceName: "Force of Silence"`; `?q=oppressive+spectral` → same Monster via `Power.Description` with a correctly windowed/spanned snippet; `?q=Loud+Noises` → same Monster via `Weakness.Name` *and* a Minion via `Weakness.Description` (`matchedSubResourceName: "Noise"`) simultaneously, confirming cross-provider Monster/Minion parity live, not just in SQLite tests; search latency ~110-130ms per request against Docker Postgres on localhost, well under the 150ms revisit-trigger in `architecture.md` Section 1.
- 90/90 tests green (75 pre-existing + 15 new), build clean with 0 warnings. No stale `dotnet run` process this time; still worth checking before build/test on this repo per the 4a note.
