### Global Search Planning (2026-08-01)

- **Dataset is small/flat/single-tenant**: 5 domains, no auth/campaign scoping, realistically tens-to-hundreds of rows each. This ruled out `pg_trgm`/`tsvector`/persisted index tables for Phase 1 — plain `ILIKE` chains per token beat any indexed alternative on cost/benefit at this scale. Revisit only if row counts or query volume grow materially.
- **Word-boundary prefix match without a token column**: `ILIKE 'token%' OR ILIKE '% token%' OR ILIKE '%-token%'` per query token (AND across tokens) gives "prefix of any word, split on space/dash" semantics fully inside EF Core's LINQ→SQL translation — no raw SQL/regex needed. Reusable pattern for any future "match at word boundaries" requirement in this codebase.
- **Extensibility without a schema**: `ISearchProvider`-per-domain + code-level weight tags (not a persisted `SearchableField` table) is the right call whenever "make X configurable later" doesn't yet have a real scale/ops reason to warrant persisted state — a compile-time registry is strictly simpler and driftless. Only reach for the persisted-table version alongside a real full-text-search migration.
- **Icon reuse pattern**: `page-layout.html`'s nav icons are inline `@switch` SVGs with no shared component — any new UI needing the same 5 domain icons (search dropdown, results page, likely future features) should extract to a `DomainIconComponent` rather than re-copy path data a 3rd/4th time.
- **Route precedent confirmed**: all 5 domain detail routes are flat/top-level (`/mysteries/:id`, `/monsters/:monsterId`, `/minions/:minionId`, `/locations/:locationId`, `/bystanders/:bystanderId`) — useful lookup table for any future cross-domain linking feature.
- **Docs**: `docs/search/README.md`, `architecture.md`, `phases.md`, `open-questions.md`.

### Global Search — Matching Design Revision (2026-08-01, same day as initial plan)

- Owner feedback pattern worth remembering: when a stakeholder floats "maybe X only applies to titles, not sure about long text" as their own tentative idea, the right architect move is confirming it with concrete reasoning (noise + snippet-extraction cost, not just "sounds right") rather than either rubber-stamping or overriding — then extend it into a clean rule if one falls out naturally (here: substring-tier scope = weight-tier scope, once sub-resource names were promoted to Secondary and prose fields correspondingly demoted to Tertiary).
- When a response contract will predictably need a new field in a later phase (here: `snippet` for "what actually matched"), add it now as always-null/optional rather than deferring — cost of adding early is ~zero, cost of adding after the frontend ships against the narrower shape is a real component rework.
- `ILIKE '%token%'` (unanchored) vs `ILIKE 'token%'` (prefix): prefix can use a btree index later (`text_pattern_ops`); unanchored substring never can, under any collation — pg_trgm is the only indexed path for substring/fuzzy matching in Postgres. Worth remembering any time "search" or "contains" comes up again in this codebase.

### Theming Architecture Planning (2026-08-01)

- **Tailwind v4 `@theme` custom properties are real CSS variables at `:root`, referenced via `var()` in generated utilities** — not inlined at build time. This is the key mechanism that makes semantic-token dark mode work as pure CSS cascade (`.dark { --color-surface: ...; }` overrides the same property every `bg-surface` utility already points to) with zero `dark:` variant sprinkling needed for color. Already implicitly used in the Tailwind migration for `--color-indigo-700`/breakpoints, but worth stating explicitly as the theming mechanism's foundation.
- Recommended semantic token layer over a mechanical `dark:`-on-every-literal-class pass, explicitly because a 3rd theme (mentioned as a real possibility) is a template-risk-free palette-only addition under tokens, vs. unbounded class-list growth under the sprinkle approach. Accepted trade-off: a re-pointing pass across every already-migrated template, phased identically to the original Tailwind migration (shell first/highest risk, wizard last/highest functional risk).
- CSR-only confirmed (no `provideClientHydration`, no `server` builder target) — FOUC prevention still needs an inline synchronous `<head>` script (not just an Angular `APP_INITIALIZER`/`provideAppInitializer`), since the browser has essentially blank HTML until the JS bundle loads and bootstraps in a CSR app; Angular-side initialization only reconciles, never originates, first paint.
- `pages/*` (dashboard, data-admin) vs `features/*` (mysteries, monsters, minions, bystanders, locations, search) split confirmed as: `pages/` = single cross-cutting app-level views registered via direct `loadComponent` in `app.routes.ts`; `features/` = domain-vertical resources with their own `*.routes.ts` + `loadChildren`. Any future single-page, no-CRUD, app-wide utility view (Settings was the case here) belongs in `pages/`, not `features/`.
- Confirmed remaining color-bearing inline styles outside Tailwind entirely: `page-layout.html`'s "Soon" badge (x2), API-unavailable modal, notification toast `[style.background-color]`. `mystery-create-monster-phase.html`'s `style="width: ..."` and `mystery-create-tracker.html`'s `[style.grid-column]` are structural (not color) and correctly out of scope for any theming pass.
- Type badges (5 domains) and admin table nth-child row striping (`data-admin.scss`/`weapon-tag-admin.scss`, hardcoded hex + `!important`) both need dedicated token namespaces rather than reuse of generic accent/danger/success roles — they're semantically fixed legend colors, not state colors, and easy to silently miss in a dark-mode pass since they don't visually read as "needs a dark variant" the way a page background does.
- Docs: `docs/theming/theming-plan.md`.

### Theming Plan — Luigi's Five Pre-Phase-1 Review Points (2026-08-02)

- **Tailwind v4 utility-name generation is a literal string concatenation, not a role-aware parse.** A `--color-X` token's utility name is exactly the family prefix (`bg-`/`text-`/`border-`/etc.) glued in front of everything after `--color-`. Never bake a Tailwind property word (`bg`, `text`, `border`) into the tail of a token name as if it indicated "which utility this is for" — it stutters (`--color-toast-success-bg` → `bg-toast-success-bg`) and any doc prose assuming the stripped form (`bg-toast-success`) is simply wrong and silently unstyled at runtime (Tailwind's on-demand generator gives no build error for an unmatched class name). The `on-*` convention (already used for `--color-on-accent`) is the clean fix for fill/text pairs; a third role like a chip border doesn't fit `on-*` and should avoid the property word entirely (e.g. `-line` not `-border`) rather than stutter too.
- Every `--color-*` token is available under every color-consuming utility prefix regardless of its intended role (`bg-text-primary` is a real, valid, if nonsensical, utility) — this is universal and harmless (no dead-CSS bloat; Tailwind only emits rules for classes actually referenced), distinct from the naming-stutter problem above. Don't conflate the two when explaining scope to a stakeholder.
- `computed()` in Angular must stay pure — it cannot itself own a `matchMedia`/event listener. The valid pattern for "signal driven by a browser event" is `toSignal(fromEvent(target, 'event'))` (subscription lifecycle tied to `DestroyRef` automatically, safe to construct in a field initializer since that runs in the class's injection context) feeding a separate, genuinely pure `computed()`.
- CSR bootstrap verification pattern worth reusing: `bootstrapApplication` only ever touches the DOM subtree under the `app-root` selector match; with no hydration step, there's no mechanism that would diff/strip a pre-bootstrap `<html>` class. Safe general rule for any "set state on `<html>`/`<body>` before Angular boots" design in this app.
- When a stakeholder wants a risk deferred to its own later phase ("if this can be put off... without needing to alter the rest"), the right move is to decouple the underlying service/mechanism (ships in place, on schedule) from the specific guarantee being deferred (its own new phase, own risk/rollback) — not to weaken the mechanism itself.
- Always re-verify a relayed "developer X found Y in file Z" claim by grepping the actual file before acting on it — `page-layout.spec.ts` was flagged as needing test-disabling for color-fragile assertions; on inspection it had none (its `.sidebar-mobile`/`.api-modal` selectors are structural, unrelated to color). The one real hit app-wide was `search-results.spec.ts` (badge literal classes), which also surfaced an undocumented Files-changed gap — the search feature's results page reuses badge tokens but wasn't in any phase's file list.
- Docs: `docs/theming/theming-plan.md` (Decision D/E/I, Token Catalogue, Phases 0/1/4, Risk Register, new Phase 8).

### Theming Plan — Token→Utility Mechanism Correction Formalized (2026-08-02)

- **Tailwind v4 utility generation is pure prefix concatenation with zero name-awareness, and there is a real, mechanically-derivable split it implies for every `@theme` token:** Category A (role name has no utility-family word, genuinely multi-family — leave in `@theme`, let it auto-generate) vs. Category B (role *is* a single family — its name necessarily contains the family word, so auto-generation stutters; fix with a hand-written `@utility` block, don't rename). Worth applying this test *before* writing a new token's Catalogue row, not after discovering a stutter at build time.
- **`@theme` vs `@theme static` is not stylistic.** A bare `@theme` tree-shakes any token no utility currently references out of `:root`, while a `.dark`/theme-override block (plain hand-written CSS) always emits in full — the two disagree, and a token can end up defined in one theme scope only. Any codebase using Tailwind v4's theme-token mechanism for hand-written CSS (not just utility classes) needs `static`, and it needs to be a *hygiene rule enforced going forward*, not a one-time fix — a second bare `@theme` block anywhere silently reintroduces it.
- **`@reference "tailwindcss"` in a component's `@apply`-bearing SCSS only loads Tailwind's stock theme — it cannot see this app's own `@theme`/`@utility` layer.** Must be a relative path to the app's actual `styles.css`. This is a loud build failure (not silent), but it's still a real per-file blocker worth checking proactively before a phase repoints an `@apply` line — I verified by grepping all `.scss` files using `@apply`/`@reference` app-wide (10 files) rather than trusting a prior framing of "which phases are affected"; one phase (4, via `monsters-list.scss`) had been missed by that framing.
- When a downstream implementer's decision file explicitly leaves items "open for Yoshi/Skyler," triage each one individually rather than blanket-deferring: some are genuinely mine to call now (an in-doc naming choice, a twice-deferred instruction conflict with no case for the status quo), some are genuinely someone else's (a values/precedent call belongs with the designer even if the mechanism is mine). Don't let "flag it" become the default move for everything in that section.
- A twice-flagged, low-risk, currently-invisible inconsistency (the API-modal `bg-surface` vs. `surface-raised` conflict — invisible because both tokens were still `white`) is exactly the kind of item that should get resolved on the second flag, not deferred a third time once every other document (palette doc, Catalogue role description, sibling components in the same file) already agrees on the answer.
- Docs: `docs/theming/theming-plan.md` (Overview, Decision B + 3 addenda, Token Catalogue naming subsection + new Conventions subsection, Phases 1-7, Risk Register).

### Theming Plan — `@reference` Directive Independent Verification (2026-08-02)

- **`@reference "<own-stylesheet>"` (not bare `"tailwindcss"`) is Tailwind's own documented mechanism** for component-scoped/isolated CSS compilation contexts needing custom `@theme` tokens — confirmed by reading `/docs/functions-and-directives` directly, which gives Vue/Svelte `<style>`-block examples in exactly this shape. Not a workaround; it's the textbook answer.
- **Angular's own docs (`angular.dev/guide/tailwind`) and Tailwind's Angular framework guide are both bare 5-6-step global-setup walkthroughs** — neither mentions component-scoped styles/`@apply`/`@reference`/theming for *any* framework, so their silence here is scope (getting-started guide), not evidence of an Angular-specific incompatibility. Angular's `ViewEncapsulation.Emulated` component stylesheet compilation is architecturally the same isolated-PostCSS-context shape as a Vue SFC `<style>` block, which Tailwind's docs do cover — reinforces there's nothing Angular-specific blocking this.
- **Node.js subpath imports (`package.json` `imports` field, `#`-prefixed alias) is a real, Tailwind-documented alternative to hand-computed relative `@reference` paths** — resolves per-file/per-depth fragility with one `package.json` entry, no Angular tooling involvement (resolved by Tailwind's PostCSS import resolution, not tsconfig paths). Worth adopting before Phase 2+ propagate more relative-path `@reference` lines.
- Docs: `.squad/decisions/inbox/yoshi-theming-reference-directive-evaluation.md`.

### Bug 2 Follow-up — Skyler's Three Decisions Resolved (2026-08-04, same day)

- Locations/bystanders don't have a `create()`/`unlinkFromMystery()`/`getByMystery()` on their Angular services (`LocationService`/`BystanderService`) even though `MonsterService` has the equivalent trio — the mystery-create store bypasses the service layer entirely for these two domains via raw `apiService.post/get/delete`. Worth checking for this "service layer has a gap, store works around it with raw apiService calls" shape any time a domain's wizard-integration code looks inconsistent with its sibling domains.
- Backend already has zero `IsNullOrWhiteSpace`/blank-name enforcement for ANY entity (Monster/Location/Bystander/Minion all rely solely on frontend Angular `Validators.required`) — `required string Name` in the EF entity only blocks null, not empty string. When asked to "make field X required, propagate to the backend," always check whether the gap is actually null-vs-non-null (schema/migration question) or blank-vs-non-blank (application validation question) — they're frequently conflated but need different fixes; here it was purely the latter, no migration needed anywhere.
- Conditionally-required form fields ("required only if a sibling field has content") don't fit a static `Validators.required` array. ### Authentication & Authorization Architecture — Public-Web Readiness (2026-08-08)

- **`MapIdentityApi<T>()` has no logout endpoint.** That single fact decided the whole mechanism question: the requirement said "sign out must actually revoke the session," and the .NET 8+ one-liner's bearer tokens are self-contained with no server-side revocation list. Worth remembering as the standard disqualifier any time `MapIdentityApi` looks like a free win — it also can't be trimmed (2FA/recovery-code surface is fixed) and its response contracts can't be reshaped to match a codebase's own DTO conventions. Landed on Identity services + cookie auth + hand-written controllers: framework for the crypto/state machines, our own HTTP surface for the conventions.
- **The decisive argument for EF Core global query filters over per-repository `.Where()` was not the 85 repository methods — it was the five `ISearchProvider`s.** `MonsterSearchProvider` et al. hold `MotwDbContext` directly and issue their own projections, bypassing repositories *and* services entirely. Any ownership convention living in the repository layer would have silently missed global search, which returns names and description snippets from every matching row. Generalizable check: before choosing an enforcement layer, grep for who else touches the DbContext directly — a layer-based convention is only as good as the layer's actual monopoly on data access.

Derive, don't denormalize. Worth remembering as the general test: *navigational* top-level-ness is not *ownership* top-level-ness; check whether the parent FK is required before treating a domain as a root.
- **Cookie auth's viability is a hosting-topology decision, not an auth decision.** `SameSite` is evaluated on the registrable domain (port-independent), so today's `localhost:4200 → localhost:5225` is already same-site; production is the risk. ### Auth Architecture — #7 Reverted, and What a Reverted Premise Actually Costs (2026-08-08, same day, third pass)

- **A stakeholder reversing an answer is not a flag flip when downstream reasoning was built on it — and the tell for "built on it" is that the consequence stops making sense, not that it stops being true.** Skyler's #7 (email confirmation not a login gate) reverted to my original recommendation. Five documented "trade-offs," one behavioural rule, one enumeration analysis, one rate-limit justification, and one UI affordance had all been derived from the wrong premise. Re-opened each from the corrected premise rather than reverting by assumption: two kept their conclusion with *new* reasoning, two flipped, one was deleted, one net-new interaction surfaced. The failure mode to avoid is a half-reversed document — prose asserting the gate while still carrying mitigations designed for its absence.
- **"Mitigates X" and "removes X from the threat model" are different claims and need different prose.** The five trade-offs (squatting, reclaim, data transfer, junk accounts, typo failure) weren't wrong-but-smaller under the gate — they stopped existing, because an unconfirmed account is inert. Deleting them and writing one sentence about what the gate *buys* was correct; shrinking them would have implied residual risk that isn't there.
- **When a rule's only justification dies, re-decide the rule — don't assume it flips.** "Password reset available to unconfirmed accounts" existed solely as the squatted-address reclaim path. With that gone I re-argued it from scratch and it *did* flip (blocked), but for three fresh reasons: it wouldn't help the user anyway (still can't sign in), it's a free mail-sending oracle, and `MapIdentityApi` gates on `IsEmailConfirmedAsync` for the same reasons. A dead justification doesn't automatically mean a dead rule.
- **The enumeration/UX interaction is the genuinely subtle one, and the resolving test is "is the password verified before this branch is reached."** Restoring the gate reintroduces a "correct password, unconfirmed" case. Collapsing it into the generic failure per #15 creates a real dead end (right password, told it's wrong, no hint a link is waiting). Resolved as four cases / two responses: distinct response for unconfirmed, because it's reachable only *after* the password is proven — not an unauthenticated oracle. Lockout stays collapsed under the same test, because `PasswordSignInAsync` returns `LockedOut` from `PreSignInCheck`, *before* the password is checked. Same-shaped question, opposite answers, one principle.
- **`SignInManager.PasswordSignInAsync` returns `NotAllowed` from `PreSignInCheck` — before the password is validated.** So the naive wiring (`if (result.IsNotAllowed) return EmailNotConfirmed()`) leaks "registered and unconfirmed" for *any* password, converting a deliberate, safe exception into a plain enumeration oracle. The safe form pairs it with an explicit `CheckPasswordAsync`. Exactly the kind of framework detail where the design's security property lives entirely in one implementation line, so it belongs in the doc and in the reviewer's focus list, not left to whoever writes the endpoint.
- **A conclusion surviving a premise change deserves an explicit re-derivation note, not silence.** The 10/day global registration cap kept its shape, but its stated justification ("only bound on usable account creation") had evaporated. Rewrote it around the resource actually at risk — outbound email quota and sender reputation, which is a *global* resource, hence a global limiter. Same answer, better reasoning, and the doc now says why it was re-checked rather than looking like it was never revisited.
- **Removing a mechanism elsewhere can silently delete a mitigation you're relying on.** #7's real cost is an ordering hazard (no email delivery means nobody can register, including the owner). My original design closed it with auto-confirm for allowlisted super-admin emails — but #8 had since deleted the allowlist. Two independently-reasonable resolutions combined into an unmitigated risk. ### Auth Architecture — Luigi's Four Blocking Findings Adjudicated (2026-08-15)

- **All four findings were the same structural shape, and it's a shape worth watching for in any multi-section design doc: a requirement stated in one section with no wiring in the section (or phase step) that would implement it.** §7 required `GET /api/auth/csrf` at bootstrap → §6 and every Phase 3 step omitted it, so *nothing* fetched it and login was impossible as written. §6 required `authErrorInterceptor` not to genericise login's failures → no mechanism named anywhere, and no section stated login's failure status. Nothing in the design was *wrong*; four things were *unreachable*. A doc that argues its decisions well can still be unimplementable, and the review that catches it is the one that traces each requirement forward to a step rather than reading each section for correctness.
- **Two of the four fail silently, and both silences come from a success-shaped failure.** `ng serve`'s history fallback answers an unproxied `/health/live` with `index.html` and a **200**, and `HealthService.getLiveness()` uses `responseType: 'text'` — so the probe *resolves* on a blob of HTML and `isApiUnavailable()` can never become true. And a `401` login failure would be *handled* by `authErrorInterceptor` (session cleared, bounce to `/login`, error swallowed) rather than erroring. Generalizable: any `responseType: 'text'` health probe against a dev server with a history fallback is structurally undetectable, and any global 401 handler collides with an endpoint whose job is to *evaluate* credentials.
- **`CanMatchFn` returning a `UrlTree` is incompatible with the two-shell (`''` + `''` complementary guards) route pattern — declined Luigi's sub-recommendation on this.** Returning `false` is what makes the router fall through to the sibling shell; a `UrlTree` cancels the navigation and redirects *instead* of trying siblings. Since shell 1's `''` prefix-matches every URL, its guard also runs for `/login`, so `UrlTree('/login')` loops until Angular's redirect limit throws. The real fix for the dead-end was just the missing `{ path: '', pathMatch: 'full', redirectTo: 'login' }` child — which `PageLayoutComponent` has carried at `app.routes.ts:9` all along for exactly the same reason.
- **When choosing an HTTP failure status for a new endpoint family, check what the codebase's existing result-translation layer can already express before arguing semantics.** `ServiceErrorType` has exactly two members (`NotFound`, `Validation`) and every controller maps `Validation → BadRequest(new { … })`. So `400 { code }` for login failure costs nothing and `401` would cost a third enum member plus a new arm in every switch — a concrete, codebase-grounded argument that outranked the abstract "401 is the semantically correct code for bad credentials." Decision #37.
- **A "belt and braces" recommendation is worth accepting *as* belt and braces, and saying so in the doc.** Both the `400`-not-`401` contract and the interceptor's `/api/auth/` URL skip independently prevent the same silent failure; specifying both, and writing down that they're redundant on purpose, is what stops a future reader deleting one as duplication.
- Partial agreement on one item is a legitimate outcome and should be recorded at sub-recommendation granularity: adopted the empty-path child verbatim, declined the `UrlTree` half of the same finding, and left the doc silent on the guards' return type rather than pre-empting Skyler's ruling with prose arguing my side.

### Simple Authentication — A Minimal Stepping Stone Under an Existing Robust Plan (2026-08-18)

- **`AddAuthentication().AddCookie()` needs zero NuGet packages** — `Microsoft.AspNetCore.Authentication.Cookies` is in the `Microsoft.AspNetCore.App` shared framework, unlike `Microsoft.AspNetCore.Identity.EntityFrameworkCore`. That single fact decided the mechanism for a minimal pass: Identity's entire value (PBKDF2 hasher, lockout, token providers, user/role store, 7 tables, a `MotwDbContext` base-class change) maps one-to-one onto the features the owner explicitly excluded. Both paths produce the *same artefact* — a Data-Protection-encrypted ticket validated by the same `CookieAuthenticationHandler` — which is exactly why the later migration is cheap and why the whole Angular side is written once.
- **The right design move for a "smaller version of an existing plan" is to copy the plan's *values* verbatim wherever they're mechanism-independent, and only re-derive where the mechanism differs.** Cookie options, `SetFallbackPolicy`, the 401/403 override, Data Protection persistence, the `400 { code }` failure contract, the two-shell routes, `credentialsInterceptor`, and single-origin hosting all transfer unchanged. Only the things that are *about Identity* (security stamps, `PasswordSignInAsync`, `ValidationInterval`, antiforgery) don't exist yet. Stating that split explicitly is what makes the forward-compat table short and checkable rather than hand-wavy.
- **Best new finding: `MapFallbackToFile("index.html")` is an *endpoint*, so a global fallback authorization policy gates it — and the failure is an unrecoverable bootstrap deadlock.** Deep links 401 before any HTML is served, so the browser never loads the app that would let you log in. The robust plan lists it in one line; it's load-bearing on day one for anything that adopts single-origin hosting in the same pass. Same middleware-vs-endpoint distinction explains why JS/CSS stay public (fine, and worth saying out loud).
- **Two column/table names chosen purely to make a future migration cheap, and both are worth reusing as a rule.** (1) Name the minimal table `app_users`, *not* `users`, because the robust plan maps Identity's user table to `users` — distinct names mean the later migration is create-alongside-and-drop rather than rename-and-widen. (2) Never name a plaintext column `password_hash`; a column whose name asserts a property it doesn't have outlives whoever created it and will be misread by the next security reviewer.
- **Plaintext is the one storage format from which a rehash is possible without user involvement** — with N users the migration is a script calling `UserManager.CreateAsync(user, plaintext)`; with one user it's "register again and drop the table." Genuinely the only operational upside, worth stating so the trade-off reads as analysed rather than apologised for. Writing it as mutation from day one costs nothing and turns the migration into a no-op. Generalizable: when a future change converts a currently-benign idiom into a silent security hole, adopt the safe idiom immediately rather than documenting the hazard.
