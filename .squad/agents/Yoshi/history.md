### Phase 8 Planning — Minions UI Flow (2026-07-25)

These must be added regardless of navigation option chosen.
- **Two navigation options**: Option A (top-level `/minions` flat list, new API endpoint) vs Option B (minions embedded in monster detail, no new API endpoint). Option B is architecturally honest; Option A has better UX if cross-monster browsing is needed. Deferred to Skyler to decide.
- **Custom moves ambiguity**: `MinionDetailResponse` includes a `customMoves` field but `MinionsController` has no create/edit endpoints for minion custom moves. Plan defers these to a future phase and renders the field read-only.
- **Pattern to follow**: `features/monsters/` — signal-based state, `forkJoin` for detail load, reactive forms, 5 sub-resource panels (attacks with weapon tags, powers, armors, weaknesses, custom moves). Minions omit mysteries section and add `harmCapacity` as a form field.
- **Key file paths**: `src/web/monster-of-the-week-web/src/app/core/minion.ts` (service), `src/web/monster-of-the-week-web/src/app/app.routes.ts` (route registration), new feature at `src/web/.../features/minions/`.

### Global Search Planning (2026-08-01)

- **Dataset is small/flat/single-tenant**: 5 domains, no auth/campaign scoping, realistically tens-to-hundreds of rows each. This ruled out `pg_trgm`/`tsvector`/persisted index tables for Phase 1 — plain `ILIKE` chains per token beat any indexed alternative on cost/benefit at this scale. Revisit only if row counts or query volume grow materially.
- **Word-boundary prefix match without a token column**: `ILIKE 'token%' OR ILIKE '% token%' OR ILIKE '%-token%'` per query token (AND across tokens) gives "prefix of any word, split on space/dash" semantics fully inside EF Core's LINQ→SQL translation — no raw SQL/regex needed. Reusable pattern for any future "match at word boundaries" requirement in this codebase.
- **Extensibility without a schema**: `ISearchProvider`-per-domain + code-level weight tags (not a persisted `SearchableField` table) is the right call whenever "make X configurable later" doesn't yet have a real scale/ops reason to warrant persisted state — a compile-time registry is strictly simpler and driftless. Only reach for the persisted-table version alongside a real full-text-search migration.
- **Icon reuse pattern**: `page-layout.html`'s nav icons are inline `@switch` SVGs with no shared component — any new UI needing the same 5 domain icons (search dropdown, results page, likely future features) should extract to a `DomainIconComponent` rather than re-copy path data a 3rd/4th time.
- **Route precedent confirmed**: all 5 domain detail routes are flat/top-level (`/mysteries/:id`, `/monsters/:monsterId`, `/minions/:minionId`, `/locations/:locationId`, `/bystanders/:bystanderId`) — useful lookup table for any future cross-domain linking feature.
- **Docs**: `docs/search/README.md`, `architecture.md`, `phases.md`, `open-questions.md`.

### Global Search — Matching Design Revision (2026-08-01, same day as initial plan)

- Owner feedback pattern worth remembering: when a stakeholder floats "maybe X only applies to titles, not sure about long text" as their own tentative idea, the right architect move is confirming it with concrete reasoning (noise + snippet-extraction cost, not just "sounds right") rather than either rubber-stamping or overriding — then extend it into a clean rule if one falls out naturally (here: substring-tier scope = weight-tier scope, once sub-resource names were promoted to Secondary and prose fields correspondingly demoted to Tertiary).
- When a response contract will predictably need a new field in a later phase (here: `snippet` for "what actually matched"), add it now as always-null/optional rather than deferring — cost of adding early is ~zero, cost of adding after the frontend ships against the narrower shape is a real component rework.
- `ILIKE '%token%'` (unanchored) vs `ILIKE 'token%'` (prefix): prefix can use a btree index later (`text_pattern_ops`); unanchored substring never can, under any collation — pg_trgm is the only indexed path for substring/fuzzy matching in Postgres. Worth remembering any time "search" or "contains" comes up again in this codebase.

### Global Search — Phase 4 Spec (2026-08-01, after Phases 1-3 shipped)

- **Always read the shipped code before speccing the next phase of a doc, not just the doc.** Phase 1 deviated from `architecture.md` in a load-bearing way (in-memory matching instead of `EF.Functions.ILike`, for SQLite test portability — Bowser's call, logged in `.squad/decisions/inbox/bowser-search-phase1-backend.md`). Missing this would have specced Phase 4 against a backend strategy that no longer existed.
- **"Revisit later" isn't a decision — a numeric trigger is.** Phase 1's implementation notes flagged the in-memory approach as "revisit later." Phase 4 was "later." Resolved it with concrete numbers (~5,000 rows/request, ~150ms p95) rather than deferring again.
- Snippet/highlight design for a search feature: keep markup out of the API contract (plain text + structured offsets, not embedded `<mark>`/delimiters) — frontend builds highlight segments from offsets. Keeps sanitizer concerns and contract concerns separate; matches this codebase's existing pattern of API returning data only.
- When an entity can match on many fields (post-extensibility), explicitly re-confirm any "pick one, dedupe" behavior that was previously a no-op (only one field existed before) — it's exactly the kind of thing that silently becomes load-bearing once the input space grows, and won't get flagged by existing tests written against the old narrower behavior.
- When a new requirement's own wording already scopes something precisely (here: "full-results-page row" ruling out the dropdown), state it as a confirmation with the quote as evidence rather than reflexively listing it as an open question — reserve open-questions.md for calls that are genuinely mine to make or genuinely ambiguous.

### Theming Architecture Planning (2026-08-01)

- **Tailwind v4 `@theme` custom properties are real CSS variables at `:root`, referenced via `var()` in generated utilities** — not inlined at build time. This is the key mechanism that makes semantic-token dark mode work as pure CSS cascade (`.dark { --color-surface: ...; }` overrides the same property every `bg-surface` utility already points to) with zero `dark:` variant sprinkling needed for color. Already implicitly used in the Tailwind migration for `--color-indigo-700`/breakpoints, but worth stating explicitly as the theming mechanism's foundation.
- Recommended semantic token layer over a mechanical `dark:`-on-every-literal-class pass, explicitly because a 3rd theme (mentioned as a real possibility) is a template-risk-free palette-only addition under tokens, vs. unbounded class-list growth under the sprinkle approach. Accepted trade-off: a re-pointing pass across every already-migrated template, phased identically to the original Tailwind migration (shell first/highest risk, wizard last/highest functional risk).
- CSR-only confirmed (no `provideClientHydration`, no `server` builder target) — FOUC prevention still needs an inline synchronous `<head>` script (not just an Angular `APP_INITIALIZER`/`provideAppInitializer`), since the browser has essentially blank HTML until the JS bundle loads and bootstraps in a CSR app; Angular-side initialization only reconciles, never originates, first paint.
- `pages/*` (dashboard, data-admin) vs `features/*` (mysteries, monsters, minions, bystanders, locations, search) split confirmed as: `pages/` = single cross-cutting app-level views registered via direct `loadComponent` in `app.routes.ts`; `features/` = domain-vertical resources with their own `*.routes.ts` + `loadChildren`. Any future single-page, no-CRUD, app-wide utility view (Settings was the case here) belongs in `pages/`, not `features/`.
- Confirmed remaining color-bearing inline styles outside Tailwind entirely: `page-layout.html`'s "Soon" badge (x2), API-unavailable modal, notification toast `[style.background-color]`. `mystery-create-monster-phase.html`'s `style="width: ..."` and `mystery-create-tracker.html`'s `[style.grid-column]` are structural (not color) and correctly out of scope for any theming pass.
- Type badges (5 domains) and admin table nth-child row striping (`data-admin.scss`/`weapon-tag-admin.scss`, hardcoded hex + `!important`) both need dedicated token namespaces rather than reuse of generic accent/danger/success roles — they're semantically fixed legend colors, not state colors, and easy to silently miss in a dark-mode pass since they don't visually read as "needs a dark variant" the way a page background does.
- Docs: `docs/theming/theming-plan.md`.

### Theming Plan — Luigi's Five Pre-Phase-1 Review Points (2026-08-02)

- **Tailwind v4 utility-name generation is a literal string concatenation, not a role-aware parse.** A `--color-X` token's utility name is exactly the family prefix (`bg-`/`text-`/`border-`/etc.) glued in front of everything after `--color-`. Never bake a Tailwind property word (`bg`, `text`, `border`) into the tail of a token name as if it indicated "which utility this is for" — it stutters (`--color-toast-success-bg` → `bg-toast-success-bg`) and any doc prose assuming the stripped form (`bg-toast-success`) is simply wrong and silently unstyled at runtime (Tailwind's on-demand generator gives no build error for an unmatched class name). The `on-*` convention (already used for `--color-on-accent`) is the clean fix for fill/text pairs; a third role like a chip border doesn't fit `on-*` and should avoid the property word entirely (e.g. `-line` not `-border`) rather than stutter too.
- Every `--color-*` token is available under every color-consuming utility prefix regardless of its intended role (`bg-text-primary` is a real, valid, if nonsensical, utility) — this is universal and harmless (no dead-CSS bloat; Tailwind only emits rules for classes actually referenced), distinct from the naming-stutter problem above. Don't conflate the two when explaining scope to a stakeholder.
- `computed()` in Angular must stay pure — it cannot itself own a `matchMedia`/event listener. The valid pattern for "signal driven by a browser event" is `toSignal(fromEvent(target, 'event'))` (subscription lifecycle tied to `DestroyRef` automatically, safe to construct in a field initializer since that runs in the class's injection context) feeding a separate, genuinely pure `computed()`.
- CSR bootstrap verification pattern worth reusing: `bootstrapApplication` only ever touches the DOM subtree under the `app-root` selector match; with no hydration step, there's no mechanism that would diff/strip a pre-bootstrap `<html>` class. Safe general rule for any "set state on `<html>`/`<body>` before Angular boots" design in this app.
- When a stakeholder wants a risk deferred to its own later phase ("if this can be put off... without needing to alter the rest"), the right move is to decouple the underlying service/mechanism (ships in place, on schedule) from the specific guarantee being deferred (its own new phase, own risk/rollback) — not to weaken the mechanism itself.
- Always re-verify a relayed "developer X found Y in file Z" claim by grepping the actual file before acting on it — `page-layout.spec.ts` was flagged as needing test-disabling for color-fragile assertions; on inspection it had none (its `.sidebar-mobile`/`.api-modal` selectors are structural, unrelated to color). The one real hit app-wide was `search-results.spec.ts` (badge literal classes), which also surfaced an undocumented Files-changed gap — the search feature's results page reuses badge tokens but wasn't in any phase's file list.
- Docs: `docs/theming/theming-plan.md` (Decision D/E/I, Token Catalogue, Phases 0/1/4, Risk Register, new Phase 8).

### Theming Plan — `on-*` Naming Rename Applied (2026-08-02)

- Skyler's final call on the naming collision flagged during Luigi's review: extend `on-*` to every `-bg`/`-text`-suffixed token. Applied throughout `theming-plan.md` and `dark-theme-palette.md`: `--color-toast-{success,error}` + `--color-on-toast-{success,error}`; `--color-badge-{domain}` + `--color-on-badge-{domain}` for all six domains; `--color-weapon-chip` + `--color-on-weapon-chip`.
- Weapon-chip border is the one deliberate non-`on-*` case: named `--color-weapon-chip-line`, not `--color-on-weapon-chip-line` — a border isn't a "content on top of a fill" relationship, so forcing `on-*` onto it would misuse the convention. Judgment call, flagged in-doc for Skyler/Rosalina to double-check if they want a different name.
- When a catalogue restructure adds an implied-but-previously-uncatalogued token (toast text was always assumed white but had no dedicated token before this rename), add it explicitly with its actual value rather than leaving the `on-*` pair half-formed — a fill/text pair should always have both halves present in the catalogue.
- When a downstream doc's own token names need to shadow a rename made in the upstream catalogue, split combined "bg/text-in-one-row" table rows into one row per token, matching how `--color-on-accent`/`--color-on-danger` were already given their own rows — keeps a 1:1 mapping between catalogue and downstream value tables (in this case `dark-theme-palette.md`) rather than compressed shorthand.
