## 2026-09-20 — Mystery entity linking Phase 5: acceptance criteria, split 5a / 5b (rev 9)

- Deliverable: `docs/updates/mystery-entity-linking-acceptance-phase-5.md`, a **sibling** to the Phase 4 doc rather than an extension. Reasons worth reusing: sub-phases that ship separately need separately judgeable criteria; the Phase 4 doc is now *cited as the origin of decisions 15/16*, so it has become a record and rewriting it blurs that; a second artifact in the same voice keeps a three-voice split from becoming four
- **The expectation inverts between phases and that must be stated in both directions.** Phase 4's AC-A6 ("assert values, not the absence of a PUT") is correct for Phase 4 and wrong after 5a — but only for monsters and minions; Locations/Bystanders keep Phase 4 behaviour because decision 9 is monsters-and-minions only. Wherever a phase plan contains an optimisation, the acceptance doc has to say which phase flips the assertion
- **Prefer a state-comparison assertion over a request-ledger one where both work.** `5a-U1` (record sub-resource ids, press Next, compare) needs no interception, survives batching refactors, and fails the likeliest wrong 5a. But ledger assertions are irreplaceable where the failure produces the *right end state by the wrong route* — duplicate deletes, re-keyed rows — which is most of Phase 5
- **H1 find: arch §5.2's "minions are already safe and show what right looks like" is true of the minion row and false of its sub-resources.** `loadEditData:1010-1013` fills the four `existing*Ids` while `:995-1009` builds the drafts with no id; `saveMinionDrafts:1947-1953` deletes-all/recreates-all. Both collections need the fix; the sentence implied one
- **H2 find: the "baseline full, draft ids absent" state is re-created by every successful submit** (`:1790-1793`), so it is reachable in **create mode** via Next → Back → Next, not only on edit-mode revisit. And its consequence is *churn plus a dirty check that can never fire*, not data loss — a wrong 5a passes a content-preservation test. Genuine destruction needs a path that fills the baseline and leaves the drafts empty, which is only reachable via 5b attach
- **H3 find, the big one: `MonsterListItemResponse` carries counts, not content, and no minions** (`core/models.ts:191-205`). So attach-a-monster cannot build a diffable draft from the picked option — it needs `getById` + `getByMonster` + a `getById` per minion, a 1+1+N fan-out, against a UX that specifies commit-on-pick with instant card. Unspecified: during-fetch, fetch-failure (card says `Attacks: 4`, composer shows zero), and pressing Next in that state
- **Check the payload, not just the entity.** Design docs describe entities; contracts describe payloads, and that is where the silence concentrates. `models.ts` was the single highest-yield file this pass
- **H5 pattern worth remembering: a two-branch ternary dispatch is a silent-fallthrough shape.** `membershipPersisted:1173` resolves `'locations' ? … : bystanders`; adding two collection members makes both land on the bystander baseline with no compile error. A doc flagging the function's *name* (§7.7b) does not fix its dispatch
- Rosalina's §§14–16 and arch §§7.6–7.7 now carry per-phase *rulings* appended after the fact. Read the latest numbered sections first — the top-of-file status line names the revision but the rulings are where the behaviour actually changed
