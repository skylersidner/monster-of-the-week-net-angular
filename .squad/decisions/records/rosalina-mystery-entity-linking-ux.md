### 2026-09-19: Mystery Entity Linking — Wizard Roster + Composer, Generalised to All Four Entities (UX design, advisory)
**By:** Rosalina (Designer)

**What:** Produced `docs/updates/mystery-entity-linking-ux.md`, the UX/visual half of connecting existing Monsters/Locations/Bystanders to a Mystery (Yoshi's `docs/updates/mystery-entity-linking.md` covers the data/API half). Recommended pattern for every entity phase in the wizard: **a roster of summary cards above a single active composer**, with a compact "add an existing one" strip between them. The pencil on a roster card pulls that entity into the composer; the loaded card takes `bg-accent-subtle border-accent` plus a literal `Editing` micro-label, and the composer header reads `Add a {Noun}` / `Editing “{name}”` with footer verbs `Save {Noun}` / `Save Changes` + `Cancel`.

**The finding that shapes everything:** this pattern already ships, for minions, at `mystery-create-monster-phase.html:148-372` — Luigi built it from my 2026-08-31 minion design. So the work is not "design a re-edit affordance," it is "lift the shipped one to Monster, Location and Bystander, add one attach strip, extend one modal." All per-entity differences fit in one column of one table (badge token, secondary `<small>` line, composer fields, extra control, attach source, modal variant).

**Judgment calls:**

1. **Attach strip, not a second card.** Yoshi §5.3 proposes a second bordered card above the add-new card; at `md:w-[42%]` two stacked bordered cards read as two equally-weighted forms at the exact moment the user is least sure which to use. The strip reuses today's location summary-row class string (`bg-surface-sunken border border-default rounded-md … px-3 py-2`), giving two tiers instead of three: light strip = pick existing, heavy card = author new. Single-select, commit-on-pick, no Add button (a third accent-ish control would compete with `+ Add Another X` and `Next →`). Hidden entirely when the catalogue is empty; `emptyText` when it is merely exhausted.
2. **Removal modal: one component, three copy variants.** Extend `ConfirmDeleteModalComponent` (already extended three times the same way) rather than writing a second dialog. Variants: never-persisted (`Cancel · Remove`, empty permanence note — matches the shipped `pendingRemoveNote()` logic exactly); persisted-and-sole (`Cancel · Detach · Delete`); persisted-and-shared (same buttons, plus the other mysteries listed in the existing `[items]` input, which is passed `[]` everywhere in the app today and exists for precisely this). `Delete` stays rightmost and `bg-danger`; `Detach` is outline-accent immediately left of it — outline-vs-filled reads as safe-vs-destructive faster than two filled hues. Copy says "Changes take effect when you continue to the next step," **not** "This cannot be undone," because at read time it isn't true yet (dispositions execute at phase submit).
3. **Membership edits inside a form never confirm.** Unchecking a mystery chip on a location's edit form is a reversible form edit; raising the modal there would train dismissal on a dialog we need read.
4. **Monster picker for minions copies *both* halves of `minion-create.html:14-30`** — the `isMonsterLocked()` prose line for a one-monster roster, the select for 2+, plus its existing "A minion must belong to a monster." error sentence. First field of the composer, not last: it is the minion's parent and every other field is meaningless without it.
5. **Mystery chips use `bg-badge-mystery`, not the weapon-tag chip.** `search-results.ts:81-85` already establishes amber as the Mystery domain colour app-wide; indigo would put an accent-coloured chip in a form for a non-accent concept. Otherwise `MysterySelectComponent` is `WeaponTagSelectComponent` verbatim.

**Two explicit disagreements, both filed as open questions rather than silently overridden:**

- **Against Yoshi §4.4** — membership chips should *not* be `.entity-link` anchors. The form is frequently dirty and no `CanDeactivate` guard covers the entity detail/edit pages, so a link out of a live form control is a data-loss trap. If the navigation is wanted, it belongs in a separate read-only "Appears in: …" line. (Yoshi conceded this in rev 3; it is no longer an open question.)
- **Against Skyler's own framing** — recommend offering `Detach` whenever the entity exists in the catalogue (`id !== null`), not only when it is in 2+ mysteries. Under the M:N model an unattached entity is a first-class, reachable state (the create pages produce them, the flat lists show them), so "keep it, just not here" is always valid; making the only non-destructive escape appear and disappear based on invisible state is confusing. His literal rule is the named conservative fallback.

**Architecture consequences of Skyler's "any entity editable in the wizard" (§10 of the doc), flagged for Yoshi:**

- His two-value `origin: 'authored' | 'attached'` no longer works, because `attached` meant "never PUT this entity's fields." Narrow rather than drop the safety property: **an attached entity is never written unless the user explicitly edited it this session** — which needs a third state. Critically, "edited" must mean *committed a differing change via `Save Changes`*, not *loaded into the composer*, or cancelling out of an attached entity silently marks it dirty.
- Drafts need a **stable client key**: the minion composer's monster picker cannot use a server ID (roster monsters may have `id: null`), `track $index` re-animates every row when one is removed, and `removeMinionDraft` already documents the index-shift hazard.
- Drafts need `mysteryIds` carried through (the data is already on the three `…ListItemResponse` DTOs), and the wizard needs one `mysteryService.getAll()` so the modal can *name* the other mysteries. A bare count doesn't let anyone choose between Detach and Delete.
- "In baseline but no longer in the list" stops meaning "unlink" — it now means whatever the modal decided, so removal needs a disposition argument the store holds until submit.

**Live accessibility defects found in the shipped minion roster** (they quadruple if replicated as-is, so they are requirements, not polish): activating the pencil **unmounts the pencil** (it is replaced by the static `Editing` span), orphaning keyboard focus to `<body>` — fix with the `wizard-layout.ts:47-60` idiom (`afterNextRender({write})` + `tabindex="-1"` composer heading + `focus({preventScroll:true})`), which also announces the mode change without needing `aria-live`. Action buttons carry only a generic `title="Edit minion"` and need `aria-label` including the entity name. `ConfirmDeleteModalComponent` has `role="dialog" aria-modal="true"` and nothing else — no initial focus, no trap, no Escape, no focus restore, hardcoded `id="modal-title"`; with a third consequential button that is no longer acceptable, and initial focus must land on `Detach` (or `Cancel`), never `Delete`. Separately flagged `CustomSelectComponent`'s wrong ARIA (`role="listbox"` over plain `<button>` children, no `aria-activedescendant`, no Escape) as pre-existing but newly load-bearing, since the attach strip makes it the sole entry point to a new capability.

**No new visual language.** Every class string in the doc already ships; §13 maps each need to the exact existing file and line to build on.

**Open for Skyler (9, in the doc):** most important are #1 (widen Detach's availability) and #2 (do Locations/Bystanders keep today's stay-open composer, or collapse like minions and pay one extra click per item in the app's most repetitive flow?).

The surviving reason is **write amplification**, and it is entity-dependent in a way I never separated: a flat Location costs one no-op `PUT`, while a monster under the shipped delete-all/recreate-all cycle has all eight sub-resource collections deleted, recreated and re-keyed on a `Next` the user never touched. **Update 2026-09-20 (post-Phase-5a reconciliation). I withdrew my own §16.4 remedy. Diagnosis right, remedy wrong.**

- **Ruling: accept the shipped baseline form (`persistedForRemoval`), one predicate for all four collections.** I had asked for a *separate* minion predicate keyed on `id !== null`. Withdrawn.
- **The deciding argument is Luigi's, and it is a UX argument I should own rather than concede as architecture: the modal's confirm label is a promise about what will happen.** `Delete` promises destruction; a bare `Remove` promises a local discard. The dialog and the drain ask the same question about the same row, so **a second predicate is a mechanism for them to disagree** — symmetrically and silently. Dialog `Delete` + drain-as-discard → user believes it's gone, it reappears next visit. Dialog `Remove` + drain-deletes → user believes they undid a click, the entity is destroyed. **Either way the modal lied about its own button**, which is far worse than the naming untidiness I was fixing.
- **My real objection was the *name*, and the rename fixed it.** `persistedForRemoval` names the **question** ("would removing this draft change anything on the server?") instead of the mechanism; that question is genuinely identical across all four even though the baseline holds memberships for three and rows for the fourth. "One name for two referents is the defect" was the right diagnosis; a second predicate was the wrong cure.
- **One argument neither Yoshi nor Luigi made, which settles it beyond preference:** I justified `id !== null` on "minions are never attached" — but that is a **contingent** fact, protected only by §2.5/§6.3 being obeyed. **Predicating a destructive button on a convention is weaker than predicating it on data.** If minion attach were ever added, `id !== null` would silently start offering `Delete` for a mis-clicked attach — the exact §7.1 bug, reintroduced in the one collection where I'd argued the shortcut was safe. The baseline form degrades gracefully; mine doesn't.
- **Kept the protective note but reattached it to the *question*.** A reviewer who remembers "`id !== null` is dangerous" still needs to know why minions looked different — so the note now says the two forms *agree* for minions (never attached ⇒ id only becomes non-null by saving) and that **observational identity is why the minion case is safe, not a licence to implement it differently.**
- **Folded in, from Luigi's Phase 5a weapon-tag fix:** `POST /attacks` answers *before* tags are assigned, so seeding the baseline from the create response records `weaponTags: []` against a draft that has one, and the row compares dirty **for ever** — re-PUTting and re-assigning on every submit. Added to §10.1 as a general rule, because it's the failure a baseline diff is uniquely prone to: **the baseline must be what the server ended up holding, not what the first call returned.** Any multi-call save (create-then-assign, create-then-link) has a window where the first response is already stale, and seeding from it makes the diff wrong in the quiet direction — not an error, just work redone every save. **Mirror of §17.2:** there, two sources that usually agree; here, one source sampled at the wrong moment.
- **Stale reference cleared:** §1's composer-state row cited `MysteryCreateDraftState`, now deleted outright; also corrected `editingDraftIndex` → `editingDraftKey` per §10.2. (My doc has no §5.5 — the "generalise the composer from one to four" reference is Yoshi's, not mine.)

**Update 2026-09-20 (Phase 5b; §17 of the doc). Attach-a-monster can't work like attach-a-location, because the payload is different.**

- **Root asymmetry, verified:** `LocationListItemResponse` carries everything `LocationDraft` needs, so `attachLocation` builds its draft straight from the picked option with **no request** (`store.ts:1269-1287`). `MonsterListItemResponse` carries counts and **no minions**, so a monster needs `getById` + `getByMonster` + `getById` per minion — 1+1+N — before the card has anything real to show.
- **Adopted Peach's position (hold the card) — but the deciding reason is different from hers, and the difference matters.** Not "don't show a half-monster" but: **a roster row must be a complete draft, because every consumer depends on it.** The dossier renders a block per monster, the minion composer's parent picker offers roster monsters, the removal modal discloses what a row takes with it, and the submit diff reads a row's collections as user intent. A loading row forces a *what-if-incomplete* branch into **all four** — and one of them silently destroys sub-resources. **Making completeness an invariant deletes four branches instead of adding them.**
- **This is also §11's answer rather than a departure from it.** §11 refused to split the roster by origin because origin shouldn't change what a row can do. A loading row can't be edited, can't meaningfully be removed, and can't be a minion's parent — **a second class of roster row, which is exactly what §11 refused.**
- **Commit-on-pick survives; the feedback moves to the strip.** §3's rejection of browse-panel/modal was about space, dossier connection, and not adding a confirm step — none of which this touches. **What §3 was actually protecting is feedback, not literal zero latency.** So: busy state on the select (disabled, picked name, spinner + "Loading “X”…", copying the shipped `app.html:47-49` treatment), roster untouched; on success the card appears complete; on failure an inline `text-danger text-sm` *in the strip*, not the footer error band which belongs to submit failures and sits a scroll from the action.
- **Structural rule that outlives this fix:** the roster card's counts must come from **the draft's own collections, never from `MonsterListItemResponse`'s `attackCount`/…**, or "card says Attacks: 4, composer shows none" becomes reachable again by any future path that loads them separately. **Same defect shape as §15.1** (a count derived from resolved *names* answering a question the *ids* already answered): **a summary and its detail must come from one source, not two that usually match.**

**Update 2026-09-20 (later) — two gaps in my §7 variants, found by Peach's Phase 4 acceptance criteria. Both were rules that were correct when written and stopped being *complete* when a new state appeared.**

- **G3 — the variant table keyed on `id`, which attach made wrong.** `id !== null` is true the *instant* an entity is attached, so attaching a location by mistake and trashing it a second later offered `Detach` (a no-op against a membership never created) and `Delete` (permanent destruction of a catalogue entity the user only meant to un-attach). **Ruling on the in-flight mystery lookup: one string, no "Still checking…".** Decoupling the list pages' loads created a third state — neither failed nor available. The decisive reason is not the one offered: **`pendingDelete` snapshots its copy at `requestDelete`, so a "Still checking…" dialog would say it forever** while the answer sat in a signal one layer away. **Phase 4 variants compose with the as-built modal, but four bindings must be explicit** (§14.2). (a) **`message` still defaults to `'This cannot be undone.'`** — `footnote`'s default changed, `message`'s did not, so a flat Location removal that passes no `message` silently renders a sentence §7.3 says is **false** in the wizard, where removal is deferred.
