### 2026-09-20: Mystery Entity Linking Phase 5b — J1 is closed by a field, and one validation branch was a second copy of a rule
**By:** Luigi (Frontend Developer)

**What:** Three implementation decisions from Phase 5b that are not restatements of the plan. Each closes a gap the docs left to implementation, and each would be easy to undo by accident.

**1. J1 is unexpressible, not fixed — and `clearDrainedRemovals` losing a line is the proof.** `MonsterDraft.existingMinionIds` replaces the store-level flat signal, and `persistedForRemoval('minions', …)` reads a `computed` that flattens the roster's per-monster baselines. Removing a monster drops its children's baseline **because the baseline is a field on the draft that just left** — there is no separate "and also forget these ids" step, so there is none to omit. The visible consequence: `clearDrainedRemovals` had a minions arm in 5a and has none in 5b, because the only way a minion disposition can drain now is with its monster still on the roster, in which case the submit's own writeback rebuilds that monster's `existingMinionIds` from the saved state. **A flat "also clear these ids" rule would have worked and would have been the third disciplinary fix in §7.7 — and the third to fail.**

Two things that fall out of it and are easy to get backwards:

- **The baseline is per-owner; the drafts operand stays global.** `removedIds(D) = D.existingMinionIds − *all* minion drafts − disposed`. A negative control that scoped the drafts per-monster too failed exactly one test — the minion re-parented *away* from D, whose id is in D's baseline and whose draft now carries another monster's `monsterKey`.
- **§7.7i's third case is J1 by another route, not a nicety.** A minion whose baseline parent is another roster monster, pending a move onto the one being removed, must have its `monsterKey` *revert*. Without it the draft leaves with the removed monster, the minion stays unclaimed in its real parent's baseline, and that parent's own diff deletes it. The revert is synchronous, which is also what satisfies Rosalina's display requirement with no copy.

**2. `validateCurrentStep`'s phase-1/step-0 branch was deleted, not rewritten — and a negative control is why.** The obvious reading of decision 19 is "replace the hard block with the composer rule," and I implemented that first. The control that removed the new branch was **NOT CAUGHT**: `next()` calls `commitMonsterComposerIfValid()` immediately after `validateCurrentStep()`, and that already refuses a started-but-invalid composer with the same message and marks the same fields. So the branch was a second copy of one rule, which is exactly the redundancy phases 2 and 3 already decline to carry and for the reason the shipped comment there records. It is gone, the reasoning is in its place, and the re-aimed control — removing the commit call — fails 26 tests. **The rule worth keeping: when a negative control does not fire, the first hypothesis should be that the code is redundant, not that the test is weak.**

**3. The cascade list reads the baseline, and the footnote clause is a parameter rather than a second function.** `[items]` is a promise about what deleting a monster will actually take, so it is `MonsterDraft.existingMinionIds` resolved to names — never `minionDrafts().filter(m => m.monsterKey === …)`, which would list a minion re-parented onto this monster *this session* as something the cascade takes, and then not take it. `wizardRemovalFootnote` gained an optional `deleteCascadeClause` instead of a monster-specific twin, so the last-phase deferral branch stays in one place; the clause attaches to the **Delete** sentence only, because detach leaves minions alone and a footnote that named them without naming the verb would imply they die either way.

**Why / judgment calls:**

- **`monsterPreview()` was renamed to `monsterComposerPreview()` rather than deleted.** Under a roster "the monster" has no single referent, and the old name invited the mistake `phaseStepComplete:601` had already made — reading the live composer form as if it were saved content, which lit the step dot on the first keystroke and dropped it on Next. The one surviving consumer is the dossier's single expanded entry, the role `minionPreview` already plays.
- **The composer's parent is derived (`effectiveMinionMonsterKey`), not written into the control at reset.** The roster can change while the composer is open, and a value stored at reset then names a monster that is no longer the answer.
- **`monster-create`'s single-mystery `Attach to Mystery` control was removed, not kept beside the form's new multi-select.** Two controls writing the same fact is how they drift; the create is now always standalone plus membership `PUT`s, which is the shape Locations and Bystanders have had since Phase 2.
- **Phase 4's A9 was retired rather than skipped.** It asserted `attachMonster` did not exist, which 5b built. What survives it is `5b-T9` — the locations strip gains no busy or error state, because it has no fetch and a state that cannot trigger is dead code.
