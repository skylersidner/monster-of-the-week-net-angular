### 2026-09-26: Resource Images — Design Pass (advisory, `docs/resource-images/design.md`)

**By:** Rosalina (Designer)

**What:** Full UX/visual design for image upload on Monsters/Minions/Bystanders/Locations (data model, storage recommendation, API surface, component breakdown, carousel design, delete confirmation, validation copy, deferred scope, open questions). No implementation. Written for Yoshi/Bowser/Luigi to react to next.

**Key calls, worth citing rather than re-deriving:**

- **Storage: recommended a Postgres `bytea` column over filesystem or object storage, explicitly contingent on the 10 KB-per-file cap being real.** Filesystem is ruled out hard, not just deprioritized — Railway containers are ephemeral, so on-disk storage is lost on redeploy without a Volume nobody has provisioned. Object storage is the textbook answer in general but adds a dependency this app doesn't have, for what is currently ≤100 KB/resource total. **If the 10 KB number turns out to be a typo for 10 MB, this recommendation flips toward object storage** — flagged explicitly in the doc's §9.1, not buried.
- **No `IsPrimary` boolean on the image row.** Used a nullable `PrimaryImageId` FK on the owning entity instead — `null` means "derive from earliest `SortOrder`" (satisfies "first-uploaded is primary by default" for free), a set value overrides it, and deleting the current primary clears the FK back to `null` so the derivation rule picks the next one automatically with no special-case code. Same "nullable column signals applicability" shape as the hunter-playbooks schema's `StartLabel`/`MaxSelect` pattern — reused, not invented.
- **One images table vs. four, flagged as Bowser/Yoshi's call, not mine.** Grepped `DomainEntities.cs` and found this codebase's actual convention is to **duplicate** parallel concept-tables per domain rather than share one polymorphic table (`LocationCustomMove`/`BystanderCustomMove` are separately-declared tables for the identical concept) — that's real precedent for four parallel `{X}Image` tables over one polymorphic `ResourceImage` + `OwnerType` discriminator. Named the tradeoff honestly (four tables keep a real FK; one table loses referential integrity across four possible owners) rather than picking for them.
- **Upload batch response is precise, not hedged — a deliberate divergence from the shipped partial-failure voice.** `rosalina-partial-failure-copy-entity-linking.md`'s hedge ("...may not have saved") exists *because* `forkJoin` genuinely can't tell you which of several parallel calls failed. File validation has no such fog — each file is checked independently and synchronously in one request, so the server can report exactly which landed and which didn't. Recommended an exact `{ uploaded: [...], rejected: [{fileName, reason}] }` shape and "3 of 5 images were added" copy, not a hedge. **General lesson for next time a partial-failure surface comes up: check whether the precedent's hedge was caused by a specific mechanism (`forkJoin`'s information loss) before reusing its hedged voice somewhere that mechanism isn't present.**
- **Over-cap batches accept what fits and reject the rest, rather than hard-failing the whole drop** (10-image cap, dropping enough files to exceed it) — same "a batch that's partially good ships the good part" principle as the entity-linking precedent, applied to a new failure shape.
- **New semantic token proposed:** `--color-image-primary-indicator: var(--color-accent)` — a pure alias, not a new hue, following the same pattern as `--color-badge-playbook` aliasing indigo. Primary-indicator glow constructed the same way `--color-focus-ring` already is (`color-mix` alpha ring), not a new mechanism.
- **Two new icons flagged, not designed as final art:** `star` (filled, primary-image toggle — matches the existing solid-silhouette family `icon-trash`/`icon-pencil`, not the outline nav family) and `chevron` (one symbol, reused twice with `rotate-180` for the "next" direction rather than a mirrored second symbol). Followed `docs/updates/svg-symbol-icons.md`'s own two-step "add a symbol, extend `IconName`" recipe rather than inventing a new consumption pattern.
- **Empty list-row thumbnail reuses the existing domain-badge color vocabulary** (`bg-badge-monster/40` + centered `<app-domain-icon>`) rather than a generic gray box — kept every row type-identifiable even with zero images. Confirmed `/40` opacity modifiers work on these tokens specifically because they're plain `@theme`-generated color utilities, not the hand-written `@utility` tokens (`text-primary`, `border-default`, etc.) that `styles.css` documents as *not* supporting the slash-opacity modifier — worth checking which category a token is in before assuming an opacity modifier will compile.
- **Images are persisted independently of the page's Save button**, matching the existing Attacks/Powers/Armors/Weaknesses sub-resource sections on `monster-detail.html` (each has its own immediate POST/DELETE, decoupled from `saveMonster()`). Named explicitly so it isn't accidentally designed as form-state later.

**Flagged, not resolved (see doc §9 in full):** the 10 KB file-size cap (plainly stated as possibly-a-typo-for-10MB, designed to the literal number regardless, per Skyler's explicit instruction not to silently substitute); one-table-vs-four; detail-page section placement (my own call, under title/badges, above the form); whether deleting the primary should auto-promote the next image (assumed yes); alt-text/caption depth.

**Explicitly deferred to a later phase, not designed at all:** Mystery Wizard integration (no owner `Id` exists yet during wizard drafting — a materially different problem, per the brief's own instruction not to design it now), image reordering, in-place edit, captions, bulk delete, content moderation/malicious-file scanning (flagged for Boo, not mine to design).
