### 2026-08-02: Theming Plan — `on-*` Naming Convention Applied to All Fill/Text Token Pairs
**By:** Yoshi (Architect)
**What:** Renamed every `-bg`/`-text`-suffixed token in the Token Catalogue (`docs/theming/theming-plan.md`) to extend the `on-*` convention already used for `--color-on-accent`/`--color-on-danger`, per Skyler's decision ("I think extending the 'on' naming convention is fine"):
- `--color-toast-success-bg` / `--color-toast-error-bg` → `--color-toast-success` / `--color-toast-error` (fill) + `--color-on-toast-success` / `--color-on-toast-error` (text-on-fill, newly added to the catalogue — previously implied but not explicitly catalogued)
- `--color-badge-{domain}-bg`/`-text` → `--color-badge-{domain}` + `--color-on-badge-{domain}`, for all six badge rows (mystery, monster, minion, bystander, location, archetype)
- `--color-weapon-chip-bg`/`-text` → `--color-weapon-chip` + `--color-on-weapon-chip`
- `--color-weapon-chip-border` → `--color-weapon-chip-line` (deliberately **not** folded into `on-*` — see Why)

Replaced the "Pending decision — awaiting Skyler" subsection with a "Resolved (2026-08-02)" subsection in the same location, and updated every reference across the Overview status paragraphs, Phase 1 (toast bullet, now stating final class names instead of hedging as "illustrative/provisional"), Phase 3 (badge pattern description), Phase 4 and Phase 5 (archetype badge bullets). Synced `docs/theming/dark-theme-palette.md`'s Token Value Table (split each combined bg/text row into one row per token, matching how `--color-on-accent`/`--color-on-danger` already had dedicated rows), Badges section, and Accessibility Notes to the new names — Rosalina's actual color values and contrast math are untouched, only names changed.

**Why:** Tailwind v4 generates a utility name by concatenating the family prefix onto the *entire* remainder of a `--color-*` token's name, with no parsing of trailing property words — `--color-toast-success-bg` compiled to `bg-toast-success-bg`, not the intuitive `bg-toast-success`, which would have silently produced an unstyled element (no build error) if used as originally drafted. The `on-*` convention was already established in this same catalogue for exactly this "fill + text-on-fill" shape, so extending it (rather than inventing a second convention, e.g. dropping only `-bg`) keeps one naming rule for one relationship shape. The weapon-chip border is the one exception: `on-*` specifically models "text/icon sitting on top of a filled surface," and a border is a third, independent role that doesn't fit that relationship — so it's renamed to drop the property word (`-line`) without being forced into `on-*`, which would misdescribe it.
