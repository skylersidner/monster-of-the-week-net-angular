### 2026-08-06: `CustomSelectComponent` Gets a Generic `size: 'default' | 'compact'` Input; `WeaponTagSelectComponent` Gets `compact` to Suppress Its Internal Label
**By:** Luigi (Frontend Developer)

**What:** Fixed misalignment/height mismatch between the weapon-tag dropdown and its sibling plain `<input>`s in the two compact inline attack-row forms in `mystery-create-monster-phase.html` (monster attacks + minion attacks). `WeaponTagSelectComponent` now accepts `@Input() compact = false` — when true it skips its internal `<span>Weapon Tags</span>` label and shrinks the selected-tag chip row, matching a bare-input row with no external `<label>`. `CustomSelectComponent` (the shared dropdown underneath — also used by monster/minion type pickers and the theme picker) gets a generic `@Input() size: 'default' | 'compact' = 'default'`, toggling an `.is-compact` class that overrides the trigger's padding/font-size/radius/border to match this app's standard compact-row input styling (`px-[0.6rem] py-[0.4rem] text-sm rounded-md border-strong`). Only the two mystery-wizard call sites opt into `[compact]="true"`; the other 4 `app-weapon-tag-select` usages (monster/minion create/detail, vertical labeled-field pattern) are untouched by default.

**Why:** The component's fixed `flex flex-col` stack (chips → label → trigger) is correct for labeled vertical forms but wrong for compact inline rows with no external labels — the internal label had no equivalent in the sibling inputs, so it pushed the trigger down and out of alignment. Made the trigger-sizing knob generic on `CustomSelectComponent` rather than a weapon-tag-only hack, since every other `app-custom-select` consumer might reasonably want the same compact variant later.

**Gotcha for anyone writing specs against this:** mutating a plain `@Input()` directly on `componentInstance` *after* the initial `fixture.detectChanges()`, then calling `detectChanges()` again with no intervening signal write, does **not** reliably re-render in this app (zoneless — no `zone.js` in `package.json`). Verified via a debug `{{ size }}` interpolation that kept showing the stale value. Use `fixture.componentRef.setInput('propName', value)` instead — it goes through Angular's real binding-update path and works correctly. A previously-passing spec that looked like it disproved this (`component.searchable = true; fixture.detectChanges();`) only worked because a later `button.click()` in the same test wrote to a signal (`isOpen`), which force-triggered the *actual* re-check that also happened to pick up the earlier `searchable` mutation.
