### 2026-09-20: Mystery Entity Linking Phase 5a — the diff's follow-up owns the baseline, and the minion predicate is the baseline form
**By:** Luigi (Frontend Developer)

**What:** Three implementation decisions from Phase 5a that are not restatements of the plan. Each closes a gap the docs left to implementation, and each would be easy to undo by accident.

**1. `SubResourceService.afterSave` returns the saved row, not `void` — and whatever it emits becomes the new baseline.** The plan treats the weapon-tag sub-diff (§5.4, `5a-U8`) as a follow-up call that runs after a row is created or updated. Implemented that way literally, it is a live defect: `POST /api/monsters/{id}/attacks` answers *before* its tags are assigned, so the create response stored as the baseline holds `weaponTags: []` while the draft holds a tag. `isDirty` then reports that attack as changed on **every** subsequent submit, re-PUTting it and re-POSTing the same tag for ever — the exact churn 5a exists to remove, surviving inside the one collection that has a follow-up call. The follow-up knows what the server now holds, so it says so: it returns `{ ...saved, weaponTags: <the draft's selection, resolved> }`. This was caught by `5a-U2` in **create mode** and by nothing in edit mode, which is the second time this phase that create mode has been the sharper test.

**2. The minion persistence predicate is the baseline form, not `id !== null`.** UX §16.4 asks for a separate minion predicate on `id !== null`; architecture §7.7b says the baseline implementation is the right question for all four collections and only the *name* was wrong. The two documents still disagree, and Skyler's standing instruction was to take the baseline form if the ruling had not landed. So: one method, `persistedForRemoval(collection, id)`, an exhaustive `switch` over the baseline signals, with both meanings documented on it — for locations and bystanders the baseline holds *memberships*, for minions it holds *rows*. For minions the two forms are observationally identical, because a minion is never attached (UX §2.5) and its id can only become non-null by being saved, and the store sets `existingMinionIds` from exactly those saves and from hydration. **The reason to prefer one implementation is not tidiness:** the modal and the drain ask this question about the same row, and a second predicate is a way for the button the user pressed and the request that gets issued to disagree.

**3. `draftState` was deleted rather than grown.** It was a `computed<MysteryCreateDraftState>` with a single consumer — a test asserting its own shape — and 5a would have required widening both it and its interface for every field the upsert adds. F4 (draft persistence) does not exist and is not scheduled. The test was rewritten against the store signals it was proxying, and the interface went with it.

**Why / judgment calls:**

- **A stub that cannot represent "unchanged" cannot test a diff.** Every sub-resource double in this repo returned a bare `{ id }` — correct while every submit deleted and recreated the lot, and actively misleading against a diff. All of them now echo the request into the response, and each create mints a fresh id; a fixed id makes two rows indistinguishable to the diff and would let a genuine mis-identification pass. This is the 5a-specific form of Toad's "fake repositories must mirror real return semantics".
- **`removalRequest`'s dispatch became a `switch` alongside `persistedForRemoval`'s.** §7.7g only names the latter, but the former was the same nested-ternary shape over the same closed union, and it is the one that decides destroy-versus-unlink. Adding a fifth collection should fail the build in both places.
- **The `'minions'` member of `PendingRemoval` refuses `'detach'` at the type level** rather than accepting it and ignoring it. A minion has no mystery membership, so the disposition does not exist; encoding that means a caller reaching for it fails to compile instead of recording something the drain has to decide what to do with.
- **Verification note for whoever reviews the tests:** the duplicate-minion-delete hazard (§7.7c, `5a-M5`) is caught **only** by the exact-call ledger. A positive "the minion was deleted" assertion passes with two `DELETE`s, which is the failure mode — and only the drain's copy maps 404 to success, so the second one fails the whole phase.
