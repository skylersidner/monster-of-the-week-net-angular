### 2026-09-26: `line-clamp-*` and an explicit `display` utility silently conflict on the same element
**By:** Luigi (Frontend Developer)
**Requested by:** the coordinator's live-browser (Playwright) verification of a locations/bystanders roster truncation fix, which caught this in the same change that introduced it.

**What:** When converting a `truncate` element to a Tailwind `line-clamp-*` element, any co-occurring `block`/`inline`/other explicit `display` utility on that element must be removed. `truncate` has no `display` of its own — it needs a `block`-level box for its `white-space: nowrap` + `text-overflow: ellipsis` to have a bounded width, so pairing it with `block` is normal and necessary. `line-clamp-*` is different: it *is itself* a `display: -webkit-box` declaration. Leaving `block` alongside it (`class="... block line-clamp-2"`) puts two single-class, equal-specificity `display` rules on the same element, and the one Tailwind happens to emit later in the compiled stylesheet wins the cascade — in this codebase's build, `.block` (line 589) is emitted after `.line-clamp-2` (line 583), so `.block` won and the clamp was silently inert: `-webkit-line-clamp: 2` stayed set as a computed property, but with `display: block` it never took effect, so `clientHeight === scrollHeight` and the full text always rendered regardless of length.

**Why this is worth a record and not just a fixed typo:** it is exactly the failure mode that survives an ordinary review. The class-name diff looks correct (`truncate` → `line-clamp-2`, everything else untouched). No Tailwind build warning or lint catches it — both classes compile fine individually. No jsdom-based spec catches it — jsdom doesn't run real layout, so `clientHeight`/`scrollHeight` are meaningless there regardless. It is only visible in a real browser's *computed* style (`getComputedStyle(el).display`, and `clientHeight` vs `scrollHeight` on text long enough to need clamping), which is why it took a live Playwright check against a real page to surface, not the existing spec suite (which the same change had already run green against, because no spec in this codebase asserts on rendered clamp height — see `mystery-create-phase4.spec.ts`/`mystery-create.spec.ts`, still legitimately silent on this).

**The general rule:** `truncate` needs an explicit `display: block` (or similar) alongside it; `line-clamp-*` supplies its own and must not be paired with one. Treat any `truncate` → `line-clamp-*` swap as a two-part edit — swap the class *and* drop the display utility that `truncate` needed and `line-clamp-*` doesn't — not a one-word substitution.

**How it was verified (no login/DB credentials were available or sought for this):** fetched the running dev server's actual compiled `styles.css` (`curl http://localhost:4200/styles.css`) to confirm the real cascade order (`.line-clamp-2` line 583 sets `display:-webkit-box`; `.block` line 589 sets `display:block`), then drove a static two-element fixture through the repo's own `playwright` devDependency (run from inside the Angular project directory — Node's ESM resolver won't find a workspace-installed package from a script sitting outside it). Result: element with `block` removed → `clientHeight 38 < scrollHeight 115` (clamped); element with `block` still present → `clientHeight 115 === scrollHeight 115` (not clamped, reproducing the bug from real computed layout, not from class-name inspection).

**Where fixed:** `mystery-create-locations-phase.html` and `mystery-create-bystanders-phase.html`, both line 23 — `class="text-muted block line-clamp-2"` → `class="text-muted line-clamp-2"`.
