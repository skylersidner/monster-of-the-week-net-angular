### Hunter Playbooks — PDF formatting-preserving extraction pipeline (2026-08-26)
**By:** Bowser (Backend Developer / DevOps)
**What:** Recommend `pdfjs-dist` (Mozilla's PDF.js), run from a standalone Node script tree at `tools/pdf-extract/` (own `package.json`, not added to `src/web`'s), as the extraction technique for populating the `<b>`/`<i>`/`<ul>`/`<li>` HTML-subset `DescriptionText` fields from the source PDF. Technique: resolve each PDF text item's actual embedded font (`WarnockPro-Bold`/`-It`/`-Regular` for this document) per page via `page.commonObjs.get(fontName)` after `getOperatorList()`, classify bold/italic from the resolved font name, merge into contiguous "runs," and splice those runs into the plain text this project already produces via `pdftotext -layout` (kept as the authoritative text/column-layout source — pdf.js is only ever used for the narrower "which spans are bold/italic" question, not full text/layout reconstruction).
**Why:** `pdftohtml` isn't installed in this environment (this machine's poppler build only ships `pdftotext`) and there's no usable Python (Store-stub shims only; the one real Python found, pgAdmin's bundled interpreter, is another app's private dependency and wasn't touched). `pdftohtmljs` (the npm package Skyler flagged) turned out to just shell out to `pdf2htmlEX`, a native binary not installed and without a simple Windows path. `pdfjs-dist` needed no new installs beyond `npm install` in an isolated tool directory, has zero native dependencies, and gives ground-truth style detection (reads the PDF's own embedded font selection) rather than a rendering heuristic. Validated against the concrete acceptance test (Crooked/Background/Hoodlum) exactly. Full writeup, including a real false-positive (cross-column text collision) found and fixed via x-range column scoping, in `docs/hunter-playbooks/pdf-extraction-pipeline.md`.
