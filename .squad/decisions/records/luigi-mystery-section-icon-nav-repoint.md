### 2026-08-08: Repoint MysterySectionIconComponent's domain kinds onto the nav's icon-nav-* symbols
**By:** Luigi (Frontend Developer)

**What:** `MysterySectionIconComponent`'s domain kinds (`mystery`, `monster`, `minions`, `locations`, `bystanders`) now render via `<use href="#icon-nav-{key}">`, reusing the exact same sprite symbols as the left toolbar nav (`DomainIconComponent`), instead of their own separate `icon-mystery-{kind}` symbols. `countdown` and the 6 countdown-stage kinds (day/shadows/sunset/dusk/nightfall/midnight) are untouched — they keep their own `icon-mystery-{kind}` symbols, since there's no nav equivalent for those. The 5 now-orphaned symbols (`icon-mystery-mystery/monster/minions/locations/bystanders`) were deleted from `icon-sprite.component.ts`. `MysterySectionIconComponent` itself was kept as the wrapper at every call site (mystery-create's tracker/dossier/phase templates, `mystery-detail.html`, `mystery-create.store.ts`'s `phases` array) — not swapped for `<app-domain-icon>` — so its per-context sizing (`--mystery-section-icon-size`, 16px inline vs 32px in mystery-detail headings) is untouched; this was an art-only change.

**Why:** The two icon sets were deliberately drawn differently during the original Phase 4 sprite migration (`docs/updates/svg-symbol-icons.md`), but that inconsistency read as an unintended visual mismatch once both sets existed side-by-side (e.g. the mystery-detail header icon vs. the sidebar nav icon for the same domain looking different). A prior investigation mapped every call site and confirmed no other code references the 5 orphaned symbol IDs; product owner then decided to unify on the nav's art rather than keep both hand-drawn sets. Implemented via a small `DOMAIN_KIND_TO_NAV_KEY` lookup inside `mystery-section-icon.ts` (mirroring `domain-icon.component.ts`'s existing `SINGULAR_ENTITY_TYPE_TO_NAV_KEY` pattern) rather than a blind string-concat, to handle the singular/plural mismatch (`mystery`→`mysteries`, `monster`→`monsters`) cleanly. `stroke-linecap`/`stroke-linejoin="round"` on the wrapper `<svg>` were left as-is (not made to match `DomainIconComponent`'s missing linecap attrs) — those attributes apply to whatever path data the `<use>` pulls in, so the nav art still renders with rounded caps inside this component without any copy.

**Verification:** `ng test --include "src/app/features/mysteries/**/*.spec.ts"` — 4 files / 15 tests green, including `mystery-detail.spec.ts`'s 14-count and `mystery-create.spec.ts`'s count assertions on the `app-mystery-section-icon` tag (they assert element counts, not `href` values, so they're unaffected by which symbol the internal `<use>` now resolves to).
