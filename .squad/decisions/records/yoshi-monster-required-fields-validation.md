# Monster Required-Field Validation — Architecture Decision

**By:** Yoshi (Architect)
**Date:** 2026-08-06

**What:**
- Field decisions: `Monster.Name` and all five sub-resource `Name` fields (`MonsterAttack`/`MonsterPower`/`MonsterArmor`/`MonsterWeakness`/`MonsterCustomMove`) should be genuinely required — all six are already implicitly assumed non-blank everywhere they're rendered (unguarded template interpolation throughout `monster-detail.html`/`monsters-list.html`), just not enforced end-to-end today. `Description`/`SpecialDescription` fields stay optional (always `@if`-guarded, no DB length cap). `MonsterTypeId`/`MonsterArchetypeId` are already fully required and correctly enforced at every layer including the service layer — the one real gap there is purely client-side (see below). `HarmCapacity`/`Harm`/`HarmSoak` are structurally always-present (non-nullable ints) but have no server-side non-negativity guard — recommended `[Range(0, int.MaxValue)]`, a new category Mystery's all-string field list never raised.
- Judgment call (explicitly invited by the task): **Monster's four sub-resource types are in scope for this same pass**, not deferred to a separate follow-up. Reasoning: identical gap shape (live-verified blank-Name persists on all five create-sub-resource endpoints), zero incremental FK-existence work needed (each already correctly checks only its parent's existence), and `UpsertCustomMoveRequest` is shared cross-domain infrastructure — fixing it here closes the same gap for Minion/Location/Bystander custom moves as a free multiplier.
- Recommended mechanism: unchanged from Phase 1, applied not redesigned — `[param: Required]` (+ `[param: MaxLength(255)]`, pending Skyler) on six `Upsert*Request.Name` params in `Contracts/ApiContracts.cs`; **zero `ServiceResult<T>`/service/repository/controller changes needed** — confirmed live that `MonsterService.CreateAsync` (both overloads) and `UpdateAsync` already check `MonsterTypeExistsAsync`/`MonsterArchetypeExistsAsync` symmetrically and never 500 on a bad/missing/zero-value FK, unlike Mystery's pre-fix `AdventureTypeId`. This is the legitimate "audit found nothing to fix" outcome Phase 1 predicted for Monster specifically.
- One concrete, non-optional UI bug found and flagged for a direct fix (not a product question): `MonsterFormComponent`'s `monsterTypeId` control has no `Validators.required` while the structurally identical `monsterArchetypeId` control on the next line does — the component's own spec file asserts touched-state for `name`/`monsterArchetypeId` after an invalid submit but never for `monsterTypeId`, which is why the gap went uncaught. Every other layer (DB, service) already treats `MonsterTypeId` as required; there's no internally-consistent reading of "leave it optional" here.

**Why:**
- Live-verified (not just read the code) that the blank/whitespace-`Name` gap reproduces identically across all six Name fields — `POST /api/monsters` and all five sub-resource create endpoints return `201`/`200` and persist `name: ""` for both `""` and `"   "` input, while `null` correctly 400s via `[ApiController]`'s existing implicit-required inference (same free mechanism Phase 1 found, no explicit attribute needed for the null case).
- Live-verified Monster's FK-existence checks three separate ways (`Guid.Empty` via omitted field, empty-string, and a syntactically-valid-but-nonexistent id) and confirmed none of them 500 — re-confirming, not just trusting, Phase 1's prediction that Monster already follows the correct pattern, important because a whole new `CreateAsync` overload was added to `MonsterService.cs` by the Standalone Creation Phase 1 initiative *after* Phase 1's cross-domain spot check ran, and needed independent re-verification that it inherited the correct shape (it did).
- Live-reproduced a genuine, unhandled `500` from a 300-character Monster Name (DB `HasMaxLength(255)`, zero DTO/client guard) — a stronger version of Phase 1's `Concept`-length finding, since here it's on the *required* field itself rather than an optional one, and it spans six fields (Monster + 5 sub-resource types) rather than one. This is why my lean on the `[MaxLength(255)]` bundling question is stronger than Phase 1's lean on `Concept`.
- `HarmCapacity`/`Harm`/`HarmSoak` surfaced a category Mystery's field list never had occasion to raise: an `int` is always "present" (no null-vs-missing question exists for a non-nullable value type) but can still be domain-invalid (negative harm). This is still a presence/shape question resolvable with `[Range]` at the DataAnnotations layer, not an existence question needing a DB round-trip — the same two-layer split from Phase 1, just applied to a numeric field for the first time.

**Open questions left to Skyler:** bundle `[MaxLength(255)]` alongside `[Required]` on all six `Name` fields plus a matching `maxlength="255"` HTML attribute (my lean: yes, stronger case than Mystery's `Concept` — this one live-reproduced an actual 500 on a required field); add `[Range(0, int.MaxValue)]` to the three harm-related ints (my lean: yes, same file/mechanism already being touched); should `MonsterArmor.SpecialDescription` become required when `IsSpecial` is `true` (my lean: no, leave uncoupled — parallel to Phase 1's declined Countdown-completeness gate); should the Monster feature adopt Mystery's asterisk required-field-indicator convention (my lean: no strong opinion, reads as a Rosalina/UX backlog item, not an architecture call).

## Revision — Skyler's 4 Answers Resolved (2026-08-06)

**By:** Yoshi (Architect)
**Date:** 2026-08-06

All 4 answered: (1) bundle `[MaxLength(255)]`/`maxlength="255"` — yes, matches lean; (2) `[Range(0, int.MaxValue)]` on the three harm ints — yes, matches lean; (3) `MonsterArmor.SpecialDescription` required when `IsSpecial` — **yes, but diverges from the "leave uncoupled" lean and is scoped UI-only** (Angular conditional validator, no server DataAnnotations change — same reasoning as Phase 1's FluentValidation decline: no clean single-attribute way to express cross-field conditional-required server-side); (4) adopt the asterisk required-field convention — yes, applied to every required field across all Monster forms, including the now-conditionally-required `Special Description`.

Implementation split two ways: **Bowser** (backend-only — `ApiContracts.cs` DataAnnotations, no service/repository/controller changes, same "already correct" FK-existence outcome as the original analysis) and **Luigi** (frontend — `monsterTypeId` required-validator bug fix, `maxlength` attributes, asterisk convention rollout, conditional `specialDescription` validator). Full scope in `docs/updates/monster-required-fields-validation.md`'s revision section.
