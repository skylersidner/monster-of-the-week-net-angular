### 2026-08-01: Theming Architecture — Semantic Token Mechanism, Not `dark:` Sprinkling (Phased Plan Written, Not Implemented)
**By:** Yoshi (Architect)
**What:** Designed and documented (in `docs/theming/theming-plan.md`) the architecture and phased rollout for light/dark theming, decoupled from the already-completed Tailwind v4 migration. Key calls:
- **Semantic CSS-custom-property token layer** (`--color-surface`, `--color-text-primary`, `--color-accent`, etc., defined in `@theme` and overridden per-scope in a `.dark { ... }` block), not a mechanical `dark:`-variant pass added next to every existing literal Tailwind utility class. Reasoning: Tailwind v4's `@theme` values compile to real CSS custom properties referenced via `var()`, so token-backed utilities repaint automatically under a `.dark` ancestor class with zero per-element `dark:` pairing — and a future 3rd theme becomes a palette-only addition (one more selector block) rather than another unbounded round of class-list growth.
- **Manual toggle wins over `prefers-color-scheme`-only**, because the brief requires a Settings-page override; OS preference is retained only as the seed value for first-visit (no stored preference), via a `'light' | 'dark' | 'system'` preference type (not a plain resolved boolean) so "explicitly follow the OS" stays a re-selectable choice.
- **`.dark` class applied to `<html>`**, not `<body>`/component-scoped — required so an inline pre-paint `<head>` script (FOUC prevention) can set it before `<body>` exists; Angular's emulated encapsulation is a non-issue since Tailwind utilities are already global regardless of component (per the original migration's own notes).
- **CSR confirmed** (no `provideClientHydration`, no `server` builder) — FOUC prevention requires an inline synchronous `<head>` script mirroring the persistence-read/system-seed logic, not just an Angular initializer, since Angular-side init only runs after the bundle loads/executes.
- **`localStorage` persistence now**, behind a narrow read/write seam inside `ThemeService`, not a backend per-user setting — matches the app's current no-auth/no-user-model maturity; swap point is isolated for when auth ships.
- **Settings view placed in `pages/settings/`**, not `features/settings/` — matches the `dashboard`/`data-admin` convention (single cross-cutting app-level view, direct `loadComponent` route) rather than the domain-vertical `features/*` convention (own `*.routes.ts`, CRUD/detail shape).
- **Phasing mirrors the original Tailwind migration's cadence and Goal/Risk/Files/Inspection-Points structure**: Phase 0 infra (dark-inert, pixel-identical) → Phase 1 shell + user menu + new Settings view (highest risk, wraps every page) → shared components → simple detail pages → list pages → medium/admin pages (including the two nth-child table-striping remnants that hardcode raw hex outside Tailwind) → wizard last (highest functional risk) → cleanup sweep + palette swap-in.
- **Type badges (5 domains) get dedicated token names**, not reuse of generic danger/success/accent roles — they're fixed legend colors, not state colors, and are called out as an easy silent miss in any dark-mode pass.
- No dark-palette color values were chosen — every token ships with its current light value as a placeholder; the `.dark` override block is a structural no-op until Rosalina's real dark fills land in the final phase.

**Why:** The Settings-view requirement forces a real, persistent, user-controlled theme state, which rules out a media-query-only approach. Given the codebase was *just* migrated to literal Tailwind utilities everywhere, the real architectural choice was whether to double every color class with a `dark:` pair or to introduce one token indirection layer — tokens cost a comparable one-time re-pointing pass but make every future theme (there was explicit signal a 3rd theme shouldn't be architected out) a zero-template-risk palette change, which the `dark:`-sprinkle approach cannot offer at any scale.
