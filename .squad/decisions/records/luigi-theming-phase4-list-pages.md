**Judgment calls, in scope-priority order:**

1. **`minions-list.scss` doesn't exist — the plan's Files-changed line ("+ its SCSS stub") is a false lead, same shape as Phase 0's `page-layout.spec.ts` false lead.** Minions have no delete button (no `DELETE /api/minions/{id}` endpoint, noted in my own earlier history) and no `:hover:not(:disabled)` guard, so there was never a stub to create. Confirmed via `ls`, not assumed.
2. **`monsters-list.scss` had ~90 lines of dead, pre-migration legacy CSS I removed.** The file still carried unused class names (`.monster-list`, `.monster-info`, `.type-badge*`, `.monster-actions` — none appear in the actual template, which is Tailwind-utility-only) plus a **second, duplicate** `.action-btn:hover:not(:disabled) { background: #f3f4f6; }` / `.action-btn:disabled` block, left over from before the original Tailwind migration reduced this file to the documented 4-line stub (`docs/tailwind-migration-plan.md` line 664-676) — a step that was apparently never actually completed for this file, unlike its sibling `minion-detail.scss`. This wasn't cosmetic: the duplicate rule sits *after* the `@apply`'d one in source order, same specificity, so it was winning the cascade. Left alone, it would have permanently pinned this button's hover to a literal `#f3f4f6` in both themes, silently defeating my `bg-surface-hover` repoint the moment `.dark`'s value diverges in Phase 7. Deleted the dead code, kept only the two live rules, matching the file's own documented intended shape and `minion-detail.scss`'s precedent. Verified negative-control: reverting `@reference` to `"tailwindcss"` reproduces `Cannot apply unknown utility class 'bg-surface-hover'`.
3. **Mystery's "adventure type" badge (`bg-amber-100 text-amber-700`, `mysteries-list.html`) is deliberately left as a literal, not tokenized.** It's functionally a type badge but isn't part of the Tailwind migration's documented Type Badge Pattern (that pattern's own "Used in" list omits `mysteries-list`), and the theming plan is explicit that `--color-badge-mystery` stays reserved/unused until a real feature needs it. Did not invent a value for it, per this task's own instruction.
4. **Mysteries-list's "Create something new..." button (`bg-blue-700 hover:bg-blue-800 text-white`) re-pointed to `bg-accent hover:bg-accent-hover text-on-accent`.** This is a genuine shade shift (`blue-700`→`indigo-600`), not a same-value repoint — no token holds the exact `blue-700` value, and the Token Catalogue's `--color-accent` role ("Brand/primary action color... buttons") is the correct semantic home for a page's primary CTA, matching the identical `bg-indigo-600 hover:bg-indigo-700` button already re-pointed the same way in Phase 1's shell. **`dashboard.html` (Phase 5) has the byte-identical `bg-blue-700 hover:bg-blue-800` button** ("Open mysteries") — flagging so Phase 5 applies the same fix for consistency rather than rediscovering it.
5. **Mysteries-list's edit/delete action-button hover colors (`hover:bg-violet-100 hover:text-indigo-600` / `hover:bg-red-100 hover:text-red-600`) re-pointed to `hover:bg-accent-subtle hover:text-accent` / `hover:bg-danger-subtle hover:text-danger`.** The delete pairing is an exact-value repoint (`red-100`/`red-600` are literally `--color-danger-subtle`/`--color-danger`). The edit pairing is a small shade shift (`violet-100`→`indigo-50`, i.e. `accent-subtle`) since no `violet` token exists and the paired hover-text (`indigo-600`) was already the accent color — reads as the same pre-existing minor inconsistency (a violet wash paired with indigo text) resolved toward the accent family, not a new one introduced. This is the app's only edit-hover-color button; the four other list pages have delete-only actions.
6. **`bystanders-list.html`/`locations-list.html`'s delete buttons keep a *neutral* hover, not a danger-red one, per the plan's explicit instruction** — their `hover:bg-gray-100` → `hover:bg-surface-hover`, not `hover:bg-danger-subtle`. This preserves an existing minor UX inconsistency (delete doesn't visually warn on hover here, unlike `mysteries-list`) rather than silently "fixing" it — out of this phase's stated scope.
7. **`search-results.ts`'s `DOMAIN_BADGE_CLASSES` map: Monster/Minion/Location/Bystander → their badge tokens; Mystery stays the literal `bg-amber-100 text-amber-700`** (reserved token, same reasoning as #3). Re-pointing Minion here is a genuine value convergence, not just a repoint: the search-results Minion badge previously used a bespoke `orange-100/orange-800` (chosen in Phase 4c specifically because no shared minion-badge token existed yet — see my own history note from that work) and now uses the exact same `--color-badge-minion` fill (`#fde8d8`) every other minion badge in the app uses. Closes that earlier-flagged inconsistency as a side effect.
8. **`text-red-800` error-message banners left untouched on all five pages + search-results**, consistent with the precedent set in Phase 3 (identical literal on ~9 pages spanning every phase; explicitly Phase 7's sweep responsibility, not scoped per-phase).
