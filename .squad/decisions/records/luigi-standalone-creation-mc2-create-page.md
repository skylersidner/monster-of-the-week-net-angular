### 2026-08-05: Standalone Creation Phase 2 MC-2 — `MinionCreateComponent`, Two Routes, Two Entry Points
**By:** Luigi (Frontend Developer)

**What:** Built `features/minions/pages/minion-create/` (`minion-create.ts` + `.html` + `.spec.ts`, no `.scss`) per `docs/updates/standalone-creation-phase2-minions.md` resolved decisions 5-10, with Skyler's confirmed **Option C** for Open Question 1: both entry points ship. One component, two route registrations — `minions.routes.ts` gains `{ path: 'new' }` ahead of `{ path: ':minionId' }`, and `monsters.routes.ts` gains `{ path: ':monsterId/minions/new' }` ahead of `{ path: ':monsterId/minions/:minionId' }`. Entry points added on `minions-list.html` (`routerLink="/minions/new"`) and in `monster-detail.html`'s Minions section (`['/monsters', monster()!.id, 'minions', 'new']`), both reusing `monsters-list.html`'s "+ Add Monster" CTA classes verbatim. The 4 sub-resource draft panels and the `create → switchMap(saveSubResourceDrafts) → always navigate` orchestration mirror `monster-create.ts` 1:1, substituting `MinionService`'s create methods.

**Why / judgment calls:**

1. **Monster resolution is a single `routeMonsterId` signal, set inside the `paramMap` `switchMap`, with the whole page branching off `isMonsterLocked()`.** This reuses `minion-detail.ts`'s existing param-presence-driven pattern rather than inventing a second mechanism. The same `forkJoin` that loads minion types and weapon tags also loads the monster context, branching within itself: `lockedMonster: monsterId ? getById(monsterId) : of(null)` and `monsters: monsterId ? of([]) : getAll()`. So the locked route never fetches the full monster list and the top-level route never does a single-monster lookup — asserted in the spec both ways, because a wasted list fetch on the locked path would be silent.

2. **`monsterControl` keeps `Validators.required` unconditionally, but `onCreate` consults the route param first.** Clearing the validator in locked mode would have been dead machinery: the control is never rendered and never read there. `effectiveMonsterId()` returns the route param if present, else the dropdown value if non-empty, else `null` — a single place where "which monster" is decided, so neither branch can drift.

3. **The dropdown bail-out sets *both* a control-touched inline message and the page-level `errorMessage`.** `MinionFormComponent` emits `save` without knowing the dropdown exists, so `onCreate` is the last line of defence. Marking the control touched drives the message directly under the picker (where the user's attention needs to go), while `errorMessage` renders in the page's existing error slot near the top (where the other failure states already appear). Bail-out happens before `isSaving.set(true)`, so nothing flickers and no service is touched.

4. **Navigation is always `/monsters/:monsterId/minions/:newId`** (decision 9), including from the top-level entry point, using the `monsterId` resolved at submit time rather than the created minion's `monsterId` field. Both are the same value; using the local one keeps the navigation independent of the response shape.

5. **Draft-panel markup came from `minion-detail.html`, the control affordances from `monster-create.html`.** Same rule as MC-1: field markup (`w-full` inputs, `text-xs` weapon chips, `last:border-0`) is taken from the page in this domain, not from the Monster sibling, so the two minion pages look identical. The `×` remove button and the `disabled:cursor-not-allowed disabled:opacity-70` submit classes come from `monster-create.html`, since those belong to the draft/batch model rather than the domain. Consequence, same as Monster: no `.scss` needed, because the `×` button dodges the `:hover:not(:disabled)` compound selector that is the only reason `minion-detail.scss` exists.

6. **The "no dropdown when locked" spec assertion needed a scoped query.** `By.directive(CustomSelectComponent)` matches three different things on this page: the page's monster picker, `MinionFormComponent`'s minion-type picker, and the one `WeaponTagSelectComponent` wraps on the attack draft form. A bare query would have found one regardless and the assertion would have passed vacuously. The helper filters out anything with an `app-minion-form` or `app-weapon-tag-select` ancestor. Worth remembering for any future create page: shared widgets make `By.directive` queries non-unique, exactly the way token CSS classes made Playwright selectors non-unique in the theming phases.

7. **Route-ordering coverage extended, not duplicated.** `minion-create.spec.ts` asserts both orderings (`'new'` before `':minionId'`, and `':monsterId/minions/new'` before `':monsterId/minions/:minionId'`); the pre-existing `'new' < ':monsterId'` assertion stays where it is in `monster-create.spec.ts`.
