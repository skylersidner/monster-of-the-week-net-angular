### 2026-08-18: Simple Authentication — Minimal Public-Web Gate, Designed as a Stepping Stone Under `docs/authentication-update/`
**By:** Yoshi (Architect)
**Requested by:** Skyler Sidner — smallest thing that puts the app on the public web behind a login, without foreclosing the robust plan. Design docs only, no code.

**What:**

1. **Cookie authentication used directly, with no Identity framework.** `AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme).AddCookie(...)` plus hand-written `AuthController` actions. Decisive fact: cookie auth is in the `Microsoft.AspNetCore.App` shared framework, so this adds **zero authentication packages** — the only new reference in the whole plan is `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore`. Everything Identity supplies (PBKDF2 hasher, lockout, `DataProtectorTokenProvider`, user/role store, seven tables, a `MotwDbContext` base-class change) maps onto features the owner explicitly excluded. Both mechanisms produce the same artefact — a Data-Protection-encrypted ticket validated by the same `CookieAuthenticationHandler` — which is what makes the later migration cheap and the Angular side write-once. Three other alternatives recorded and rejected in `architecture.md` §1.1 (Identity now; BCL `Rfc2898DeriveBytes` hashing; HTTP Basic; an env-var shared secret with no user row).

2. **Credentials in a new four-column `app_users` table** (`id`, `username` unique, `password` plaintext, `created_at`), hand-inserted, never seeded from code. Two naming calls made purely for migration cost: **`app_users` not `users`** (the robust plan's decision #5 maps Identity's user table to `users`, so distinct names make the later migration create-alongside-and-drop rather than rename-and-widen), and **`password` not `password_hash`** (a column name that asserts a property it doesn't have outlives whoever wrote it).

3. **API gating is three lines and touches zero controllers.** `SetFallbackPolicy(RequireAuthenticatedUser)` fails closed across all **107** actions across **7** controllers — re-counted against the current tree today (12/12/29/31/7/14/2, unchanged from 2026-08-08). Four `[AllowAnonymous]` opt-outs: `login`, `me`, `/health/live`, and the SPA fallback. No `[Authorize]` attribute anywhere; no roles; no `owner_id`.

4. **Best finding, and the one that would break a deployment: `MapFallbackToFile("index.html")` is an *endpoint*, so the fallback policy gates it — producing an unrecoverable bootstrap deadlock.** Deep links `401` before any HTML is served, so the browser never loads the app that would have let the user log in. And `/` keeps working, because `UseDefaultFiles` serves `index.html` from static-file *middleware* which never reaches endpoint authorization — so the failure reads as intermittent and route-dependent rather than as a missing `AllowAnonymous`. The same middleware-vs-endpoint distinction is why the JS/CSS bundle stays publicly downloadable, which is correct for a CSR SPA but worth stating.

5. **Single-origin hosting decided now, not deferred.** Cookies don't work cleanly across origins, and deferring means deploying into whatever shape the host makes easiest — frequently the third-party-cookie topology the design cannot tolerate. Adopts the robust plan's decision #2. Worked out the minimum in-repo shape (`UseDefaultFiles`/`UseStaticFiles`/`MapFallbackToFile`, the `wwwroot` publish step, `UseForwardedHeaders`, CORS made Development-only) and **stopped there** — hosting provider, TLS, domain, secret storage, production Postgres, backups and CI/CD are flagged as a separate focused pass, the same line the robust plan drew around its Phase 6.

6. **Adopted the two-shell route pattern even for a single login page.** The constraints it encodes are structural, not proportional to the page count: traced the single-route alternative and it still needs an empty-path landing route for the logged-out case and still needs guards returning `false` rather than a `UrlTree` — i.e. it reproduces both of Luigi's 2026-08-15 findings from scratch. Re-deriving a route shape that already cost a review cycle gives its defects a second chance.

7. **`architecture.md` §5 is an itemised two-way forward-compatibility table** — 19 rows that carry forward byte-for-byte (cookie options, Data Protection persistence, fail-closed policy, `400 { code }` contract, both interceptors' `/api/auth/` exemption, the route shape, `AuthService` signals, single-origin hosting, the dev proxy), and 13 rows that change, each with the shape of the change rather than a hand-wave. Everything in the robust plan's Phase 2 (ownership) is a pure addition with nothing in its way.

8. **Two mitigations adopted now for hazards that are benign now.** (a) The cookie `Events` overrides are written as *mutation*, never assignment — harmless with a bare `AddCookie`, a silent security hole the moment `AddIdentityCookies()` lands and the assignment discards `OnValidatePrincipal`. (b) `login` returns `400 { code }` rather than `401`, plus both interceptors skip `/api/auth/`, deliberately redundant — a `401` would be swallowed by the session-expiry handler and the login form would silently report nothing.

9. **Plaintext password stated as an analysed, accepted risk, not apologised for.** The real exposure is password reuse via a database backup, not application compromise; the one non-optional control is a password unique to this app; and the upgrade trigger is stated as a *condition* (a second account, or data worth losing) rather than "revisit later." Noted the one genuine operational upside: plaintext is the only storage format from which a rehash is possible without user involvement.

**Why:** The owner wants to use the app from anywhere now and does not want to redo foundational work later. That makes "how much of the robust plan can this pass ship *unchanged*" the governing question, not "what is the least code." Copying the robust plan's mechanism-independent values verbatim and re-deriving only where the mechanism genuinely differs is what keeps the forward-compat list short and checkable.

**Open for Skyler (`open-questions.md`):**
- **#1 — login identifier, and the only place this design contradicts a standing decision.** The owner said "username"; the robust plan's resolution #17 / decision #6 settled on **email**. Recommended `username` (all of that plan's reasoning is about enrollment/reset/Profile flows that don't exist here), with the exact later churn itemised — and flagged that answering "email" instead makes that entire forward-compat row disappear. **Cheap now, a contract change afterwards.**
- **#2 — is Sign out in scope?** Recommended yes: the dead link already exists at `page-layout.html:111`, a public session with no browser-side exit is a real gap, cost is ~20 lines, and it carries forward unchanged. It is the one thing in the design beyond the literal ask.
- **#3 — does the owner's existing local game data need to reach production?** Not an auth question, but it sits in the path of "so I can start using the app." No recommendation on mechanism; flagged that moving it *before* the robust plan's `NOT NULL owner_id` migration is materially simpler than after.

**Verification done (per the architecture-scan-completeness convention):** Globbed the whole of `src/api/**` and `src/web/**/src/app/**` and re-verified every claim the robust plan's 10-day-old §0 inventory made, rather than citing it. All still accurate. Two facts it didn't carry that mattered here: **`Program.cs:9–10` hard-throws when `Cors:AllowedOrigins` is absent** (a production startup failure under a topology that doesn't use CORS at all — needs the whole CORS block made Development-only), and the Angular build emits to `dist/monster-of-the-week-web/browser` with **no `wwwroot/` in the API project**. Also found a real reduction in the robust plan's own deferred Phase 6 work: with the dev proxy making development same-origin, `apiBaseUrl` is `''` in both environments, so `environment.prod.ts` and `angular.json` `fileReplacements` are simply not needed for a same-origin deployment.

**Docs written:** `docs/simple-authentication-update/README.md`, `architecture.md`, `phases.md`, `open-questions.md`. **No file outside that directory was modified** except this decision record and `.squad/agents/Yoshi/history.md`. No application code was written or changed.

### Revision, 2026-08-18 (same day) — Skyler's three answers folded in

**1. Login identifier settled: email, overriding my recommendation.** *"The email IS the username, always."* Applied throughout — `app_users.email` with a unique index, `LoginRequest(string Email, …)`, `CurrentUserResponse(Guid Id, string Email)`, `IUserRepository.FindByEmailAsync`, an `email` form control, `CurrentUser.email`. **This removes the only conflict this design had with `docs/authentication-update/`** (its resolution #17 / decision #6), and the forward-compat table changed shape as a result: §5.2 lost its "login identifier" row entirely and §5.1 gained two — the login contract/component/`AuthService.login()`, and the issued claim set (`ClaimTypes.Name` = email, which is what Identity produces too since the robust plan sets `UserName = Email`). The override was the better call: every artefact that would have churned sits on the *contract* boundary, which is where churn costs most. Two small consequences added, both normalisation rather than validation: case-insensitive lookup (`lower()` both sides — the row is typed by hand, so a casing mismatch would otherwise be a login failure with nothing to read) and `type="email"` on the input (free, and it cannot block submit because Angular's `FormGroupDirective` puts `novalidate` on the host form).

**2. The `MapFallbackToFile` fail-closed gap now has a worked fix, not a flag — new `architecture.md` §2.3.** Skyler's premise (the shell is public; the Angular app renders its own login view; anonymous visitors fetching `index.html` and the bundles is expected) collapsed it to **one `.AllowAnonymous()` on one endpoint**. The write-up is built around the mechanism rather than the attribute: `UseStaticFiles`/`UseDefaultFiles` are *middleware* that short-circuit before authorization ever runs, so assets and `/` are anonymous by construction; `MapFallbackToFile` is an *endpoint* and is the only piece the fallback policy touches — which is exactly why the bug presents as intermittent (`/` works, `/login` and every deep link `401`) rather than as an obviously missing attribute. Three things fell out: **(a)** a second-order gap I'd missed — the fallback registers at `Order = int.MaxValue` with `{*path:nonfile}`, so a *misspelled* `/api` path is answered with `index.html` and a `200`, the same success-shaped-failure family as the `/health/live` + `responseType:'text'` trap and strictly more reachable under single-origin hosting; closed with `app.Map("/api/{**rest}", () => Results.NotFound())` at default order, deliberately **not** `AllowAnonymous` so anonymous gets `401` and authenticated gets `404`. **(b)** An explicit re-argument that the Angular `canMatch` guard is **not** made redundant by the server serving the shell unconditionally — a two-column table of what each mechanism catches that the other cannot; deleting the guard doesn't break access control, it produces a visible flash of the full signed-in chrome plus seven lazy bundles downloaded for nothing, and the interceptor structurally cannot cover the first navigation while the guard structurally cannot cover mid-session expiry. **(c)** An `index.html` caching note, since content-hashed bundles are safe to cache forever and the file that names them is not.

**3. Single-origin hosting confirmed** — §4.1 reworded from "must be decided now" to settled, with the consistency between the two answers stated explicitly: single-origin is *what makes* the shell and the API the same server, which is why one `AllowAnonymous` is the whole of the fix.

**Consistency pass done:** every `§N.N` cross-reference resolves to a real heading after §2.2–§2.5 were renumbered; the only surviving "username" mentions are the owner's quote, the resolution record, and assertions that no username concept exists; the `Program.cs` middleware-order block, both risk registers, and the verification checklist all updated (six new checklist items, three new risk rows).

**Still needs Skyler — two carried over plus one new:**
- **#2 (carried over, unanswered): is Sign out in scope?** Recommendation stands (include it). Worth noting the coordinator's "all three answered" covered a different three than my open-questions file, so this was not in fact ruled on.
- **#3 (carried over, unanswered): does existing local game data need to reach production?** Only needed before the deployment itself, but flagged that moving it *before* the robust plan's `NOT NULL owner_id` migration is materially simpler than after.
- **#4 (new): is a 24-hour sliding session long enough?** Raised because confirming "the app renders its own login view on 4xx" makes mid-session expiry a designed-for path rather than a hypothetical — and **this app has no draft persistence anywhere** (`MysteryCreateStore.init()` reads a route-snapshot `:id` once; no `localStorage` save), so a lapse with the create wizard open loses the current phase's work. Pre-existing gap, not introduced here, but session expiry adds a second way to trigger it. Recommended keeping 24h (matches the robust plan's decision #27 verbatim; sliding expiry means it only bites overnight; and a longer window means proportionally longer life for a copied cookie, which matters more here because this pass has **no revocation mechanism at all**). Confirm-or-override, one-line config change, not a blocker.

### Closing revision, 2026-08-18 (same day) — final three resolutions; plan closed with no open questions

**#2 Sign out — in scope, confirming the recommendation. And parsing the confirmation sentence surfaced the best finding of the pass.** Skyler's *"we will need it for when a session expires and it's easy enough to enable a UI button to expire it manually/intentionally"* conflates **two different mechanisms** — the automatic `401`-interceptor bounce when a session lapses on its own, and the manual button that ends a *live* session. Both were already designed; separated into a two-column table in `architecture.md` §3.4 so an implementer can't read the button as the expiry handler. Tracing the approved feature against decision #9 then exposed a real silent dead end: **`POST /api/auth/logout` is authenticated, so clicking Sign out on an already-expired session returns `401` — and both interceptors skip `/api/auth/` by design, so nothing handles it.** `AuthService.logout()` must clear the signal and navigate from its `error` path as well as `next`, or Sign out is **inert in exactly the case the owner named it for.** Two independently correct decisions combining into a silent failure — same shape as Luigi's blocking findings on the robust plan. Now a named Phase 2 step, a risk-register row, and a verification-checklist item (expire the cookie in devtools, click Sign out).

**#3 Existing local data — does not reach production.** Recorded as decision #18 and in `architecture.md` §4.3 as **a decision rather than an absence**, because an unexplained gap invites someone to fill it. Carried forward the one fact that matters if reversed: moving data *before* the robust plan's `NOT NULL owner_id` migration is materially simpler than after.

**#4 Session lifetime — 24h confirmed unchanged, draft-loss consequence knowingly accepted.** Kept the risk-register row marked **accepted** rather than deleting it, with an explicit instruction that **no draft-persistence work should be proposed on the strength of it** — a live-looking risk with no mitigation is exactly what gets helpfully "fixed" later. "Accepted" and "absent" are different states and collapsing them loses the owner's decision.

**Swept my own hedges, not just the stakeholder's.** A doc with zero open questions but three "optional / if wanted / say the word" phrases still reads as unresolved. Decided each and moved them into "decided by reasoning, not asked": the `/api/{**rest}` catch-all is now **in scope, not optional** (one line against a silent failure); the constant-time password comparison is now an explicit **decline with reasoning** rather than an offer (it defends nothing when the value is plaintext at rest, and shipping it would imply more safety than exists); Sign out lost its "say the word and it comes out."

**Added a review gate** naming Luigi (Phase 2 in full), Bowser (Phases 0/1/3), and Boo (**optional, owner's call** — `.squad/ceremonies.md` triggers `security-review` on "handles auth"; if it runs, only §2.3's anonymous surface and §6's plaintext trade-off are worth his time, not the parts the owner excluded by instruction).

**Final state: 4 docs, 1,405 lines, 18 decisions, all four questions resolved.** Every `§N.N` cross-reference verified against a real heading; decision numbering contiguous 1–18; no residual "username," no residual open/hedge framing. **Nothing about this design still needs Skyler.** The only two things between it and a deployment are deliberately outside it and already scoped that way: the infrastructure pass (`architecture.md` §4.3 — and `SecurePolicy.Always` means there is no working deployment without real TLS) and the optional security-review ceremony.
