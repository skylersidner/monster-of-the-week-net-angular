### 2026-09-20: Mystery Entity Linking Phase 5b — acceptance criteria, and one finding that belongs in the design rather than in a test

**By:** Peach (Product Owner / Business Analyst)

**What:** 5b's criteria are at **`docs/updates/mystery-entity-linking-acceptance-phase-5b.md`**. It **supersedes §4 of `mystery-entity-linking-acceptance-phase-5.md`**, which was a twenty-row sketch written before the roster's shape settled; §3 of that doc (the 5a criteria, now shipped and verified) stands unchanged and is not restated. Third acceptance artifact, same three-voice ownership rule.

**Why a sibling again rather than an edit:** the 5a criteria are now cited as the record of what was tested (`5a-U1` killed the delete-all/recreate-all mutant on key rotation alone; `5a-P5` was the one criterion with no coverage anywhere until Toad closed it). Rewriting that file to grow one section would put a verified record at risk for no gain.

**Six findings. None needs Skyler** — all six are internal correctness or consistency questions with no product choice inside them. One of them should change the design before Luigi starts.

**J1 — removing a monster makes the minion diff destroy its minions. This is a design change, not a test.** Three individually correct rules compose into the opposite of what detach promises:

- §7.7d drops a removed monster's minion drafts from the roster and records one disposition, for the monster.
- §7.7f drops every pending `'minions'` disposition whose parent left the roster.
- `idsToRemove` (`mystery-create.store.ts:1975-1992`) computes: baseline, minus drafts, minus **disposed**.

A persisted minion whose monster was removed is in `existingMinionIds`, not in `minionDrafts()`, and — because §7.7f just dropped its disposition — not in the disposed set. So it lands in `removedIds` at `:1914` and `saveMinionDrafts` fires a blind `minionService.delete()`. **That path has no 404 handler**; `removalRequest`'s `catchError` (`:2074`) is drain-only and deliberately so.

Under **detach** the minions are genuinely destroyed everywhere, which is the exact opposite of what §6.4 and the modal copy promise. Under **delete** the cascade already destroyed them, so the blind delete 404s and fails the whole phase — non-deterministically, since the drain and the minion diff are concurrent `forkJoin` siblings (`:1772-1775`).

**The root cause is the useful part: §7.7f's fix is what opened the second door.** Dropping the disposition removed the only thing excluding that id from the diff. `idsToRemove`'s exclusion set and `stillTheRostersBusiness`'s drop rule are the same fact in two places and they now disagree. The missing rule already exists one level over — when a monster leaves the roster, its minions' ids must leave `existingMinionIds`, which is precisely the bookkeeping `clearDrainedRemovals` performs for drained removals (`:2086`, consumer 2). The drop path needs the step the drain path has. **→ Yoshi, into §7.7, before `submitPhase1` is rewritten.**

**J2 — `MinionDraft` has no baseline parent, so `5b-K4` ("a re-parent fires only when the parent changed") is unimplementable as specified.** §6.4 adds `monsterKey` and nothing else; the draft (`:190-213`) records which monster a minion points at *now* and never which one it came from. That leaves only an unconditional `moveToMonster` per persisted minion per submit — and that verb **moves** rather than adds, so a call against a stale id silently relocates rather than failing (Bowser's caveat). Issuing it N times per submit maximises exposure to a `localKey → monsterId` resolution bug and turns a user-visible consequence into a background write. Recommend the draft carry the parent it was hydrated or last saved with, written in the same step as `id` and the four sub-resource baselines. **→ Yoshi, one field.**

**J3 — two completeness mechanisms and §6.5 discusses one.** `phaseComplete` is the phase bubble, correctly analysed. `phaseStepComplete` (`:585-611`) is the per-**step** dots, and its phase-1 step-0 entry (`:601`) reads `monsterPreview()?.name` plus `monsterValue()?.monsterArchetypeId` — both being retired with the single-monster shape, with no roster meaning specified. The consistent answer is `monsterDrafts().length > 0`, matching the three other optional collections. Note that UX §16.2's "do not gate the phase-1 tracker dot on monster count" is about the **phase bubble**; reading it as covering the step dot yields a permanently lit dot, which is the conflation worth preventing. **→ Yoshi, with Rosalina confirming the step dot reads as content-presence.**

**J4 — "removing a monster takes its minions" silently doesn't hold for a minion re-parented onto it this session.** Move M from A to B, remove B, Next: M's draft leaves with B, the re-parent was never submitted, so M is still on A and alive. Defensible — removal operates on server truth — but the rule's plain reading predicts the opposite. **Closest of the six to needing Skyler and still not one**, because both behaviours are coherent and the difference is only visible in a sequence nobody performs deliberately. Needs the criterion to assert the actual outcome so the first person to hit it doesn't file it. **→ Yoshi, one sentence.**

**J5 — `monsterPreview()` has four consumers, §6.5 names one.** It is also the *contents* of the dossier's monster block (`mystery-create-dossier.html:75, 83, 96, 109`) and is read by `phaseStepComplete:601`. Two files, four consumers. **→ Yoshi, accuracy fix.**

**J6 — edit-mode hydration now fans out per monster with no error isolation.** `hydrateMonsterDraft` is 1+1+N and `loadEditData` will call it once per monster; a three-monster, two-minion-each mystery is twelve requests before paint. Volume is accepted (F7). The error behaviour should be **decided rather than inherited**: all-or-nothing is correct and the partial-roster alternative must not be chosen, for §17.4's reason — a roster missing a monster is a roster whose diff treats "nothing" as the user's intent, and the mystery's own edit surface is the worst place for that. Extend the hydrate-then-commit invariant from attach to edit-mode load explicitly. **→ Yoshi, one sentence in §6.6.**

**Method note, third pass running.** J1, J2, J3 and J5 all came from the store and the templates; none is visible from either design document, and neither document is wrong about any of them. The recurring shape is now specific enough to name: **a fix that removes a record also removes whatever that record was incidentally protecting** (J1), and **a type gains the field the new feature needs but not the baseline the existing mechanism needs** (J2, and H1/H2 before it). Both are invisible from the design side because the design describes the new behaviour and the code holds the old invariant.
