### 2026-08-02: Theming Phase 5 — Medium Pages & Admin, Judgment Calls

**By:** Luigi (Frontend Developer)

**What:** Phase 5 of `docs/theming/theming-plan.md`: re-pointed `mystery-detail.html` (+ `.scss`), `monster-detail.html` (+ `.scss`), `dashboard.html`, `data-admin.html` (+ `.scss`), `weapon-tag-admin.html` (+ `.scss`) onto tokens, including the two admin tables' `nth-child` row-striping remnants (the plan's final decided form: `var(--color-surface)` odd / `var(--color-accent-subtle)` even) and the `monster-detail` archetype badge.

**Judgment calls, in scope-priority order:**

1. **Admin table *header* fill has no token role, and I mapped it to `bg-accent-subtle` — the same token as the even rows.** `bg-[#e8eefb] text-[#1e293b]` on `<th>` is a pale indigo wash with dark bold text. `--color-accent-subtle` (light `indigo-50` = `#eef2ff`) is a near-exact light-mode match for `#e8eefb`, and it's the same reasoning Rosalina used for the even rows (a pale blue/indigo wash, not really "sunken"). `--color-surface-sunken` was the alternative and is worse in both themes: light `slate-50` is nearly white against the white odd rows and loses the blue tint entirely. The cost is that the header fill now equals the even-row fill; accepted because headers are distinguished by bold weight plus a bottom border, and the two were already very close (`#e8eefb` vs `#dbeafe`). `text-[#1e293b]` (slate-800) → `text-primary` (slate-950) is a small deliberate darkening, consistent with every other `text-primary` repoint in this rollout.
2. **`text-[#a10808]` validation/load-error text in the two admin templates → `text-danger`; `text-red-800` error banners elsewhere left alone.** This looks inconsistent within one phase but is deliberate. `text-red-800` is the app-wide error-banner literal on ~9 pages, explicitly deferred to Phase 7's sweep since Phase 3 — Phase 7's grep ("`text-` followed by a Tailwind color name") **will** find it. `text-[#a10808]` is an *arbitrary-hex* class that Phase 7's grep as currently written would **not** find, it lives only in the two files this phase already rewrites, and `dark-theme-palette.md` explicitly routes field-level validation text through `--color-danger`. Light-mode shade shift `#a10808` → `red-600` is real and flagged. **Recommend Phase 7's sweep description be widened to also grep arbitrary-value color classes (`bg-[#...]`, `text-[#...]`, `border-[#...]`), not just Tailwind palette names** — that's a genuine hole in the sweep as specified.
3. **Dashboard's "Open mysteries" button (`bg-blue-700 hover:bg-blue-800 text-white`) → `bg-accent hover:bg-accent-hover text-on-accent`**, per my own Phase 4 flag — byte-identical markup to `mysteries-list`'s create button, so it gets the byte-identical fix. Same genuine `blue-700`→`indigo-600` shade shift, same reasoning (`--color-accent` is the correct role for a page's primary CTA).
4. **Dashboard's skeleton-loader bars (`bg-gray-200`) → `bg-surface-hover`.** No "neutral fill" / skeleton token exists. `--color-surface-hover`'s light value is *literally* `gray-200`, so this is a pixel-exact light-mode no-op, and its dark value (`slate-700`) reads as a clearly-visible bar on a `slate-900` card. The role name says "hover," which is a stretch — but the plan already declined to proliferate near-duplicate neutrals (see the `--color-accent-muted` deferral), and inventing `--color-skeleton` for two `<div>`s seemed worse than reusing the neutral that already holds the exact value. Flagging in case Rosalina/Yoshi prefer a dedicated token or a rename of `--color-surface-hover` to something role-neutral (e.g. `--color-surface-neutral`).
5. **`monster-detail`'s sub-resource list dividers (`border-[#edf1f8]`) → `border-default`.** `#edf1f8` is one step *lighter* than `--color-border`'s light value; no lighter border token exists. Same category as Phase 3's `border-slate-200`→`border-strong` shift — a deliberate, documented convergence onto the catalogue's border role rather than an invented token.
6. **`mystery-detail`'s adventure-type badge (`bg-amber-100 text-amber-700`) left as a literal**, exactly as `mysteries-list.html` was in Phase 4 — `--color-badge-mystery` stays reserved, no value invented. Verified live: it is the *only* measured element on any of these five pages that does not change between themes, which is correct by design, not a miss.
7. **`monster-detail`'s inline weapon-tag chips → `bg-weapon-chip` / `border-weapon-chip-line` / `text-on-weapon-chip`.** All three light values are exact matches for the literals they replace (`#eef2ff`/`#c7d2fe`/`#4338ca`) and converge this hand-rolled chip onto the same tokens `weapon-tag-select.component.html` already uses (Phase 2) — a consistency fix as a side effect. `--color-weapon-chip-line`'s first-ever *template* consumer with a `border-` utility.
8. **Three of the four Phase-5 `.scss` files have no `@apply` at all, so their `@reference` change is inert.** `mystery-detail.scss` holds only two custom-property declarations; `data-admin.scss` / `weapon-tag-admin.scss` read tokens directly via `var()` in a plain `nth-child` rule. I still changed all three to `@reference "#styles.css";` per the plan's literal instruction — consistent convention, zero output, and it means a future token-backed `@apply` in any of them won't fail the build. Consequence for verification: the `@reference` negative control is only demonstrable on `monster-detail.scss` (the one file with real `@apply` lines) — done, and it reproduces `Cannot apply unknown utility class 'bg-surface-hover'` exactly.
9. **Dead-CSS check on all four `.scss` files: nothing found.** All four are already the small post-migration stubs; every selector in them (`.action-btn`, `.action-btn--delete`, `.heading-with-icon`, `.countdown-stage-label`, `.records-table`) matches live markup, and no selector appears twice, so there is no repeat of the `monsters-list.scss` cascade bug from Phase 4. One near-miss worth recording: the class-emission checker flags `countdown-list` (in `mystery-detail.html`) as emitting no CSS rule — it is **not** dead markup, it's a test hook used by `mystery-detail.spec.ts`'s `.countdown-list app-mystery-section-icon` selector. Same category as `.sidebar-mobile`/`.api-modal` in Phase 0; don't delete it in Phase 7's sweep.
