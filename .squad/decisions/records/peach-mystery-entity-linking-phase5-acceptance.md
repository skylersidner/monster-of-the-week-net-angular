### 2026-09-20: Mystery Entity Linking Phase 5 — acceptance criteria as a sibling doc, split 5a / 5b

**By:** Peach (Product Owner / Business Analyst)

**What:** Phase 5's acceptance criteria are at **`docs/updates/mystery-entity-linking-acceptance-phase-5.md`**, split so 5a and 5b can each be judged when they land. The Phase 4 doc (`mystery-entity-linking-acceptance.md`) stays Phase-4-scoped and unmodified; its §6 line "monsters and minions — Phase 5" is discharged by the new file.

**Why a sibling rather than an extension:** 5a and 5b ship separately and each needs a standalone "is this done?"; the Phase 4 doc is now cited by architecture §3.2 as the origin of decisions 15 and 16, so it is a record as much as a checklist and rewriting it would blur that; and a second acceptance artifact keeps the three-voice ownership rule (Yoshi = how, Rosalina = how it looks, me = what must be true) rather than adding a fourth voice.

**One criterion is load-bearing and should be written first.** `5a-U1`: record a monster's sub-resource ids, press Next with nothing edited, re-read them — every id unchanged. It needs no request interception, survives any refactor of how the calls are batched, and fails on the most likely wrong implementation of 5a. Its companion `5a-U2` (no sub-resource writes at all when nothing changed) is a ledger assertion and cannot be substituted by an outcome assertion, for the reason §8 of the doc gives: every failure 5a exists to prevent produces the *right end state* by the wrong route.

**The Phase 4 expectation inverts in 5a, and it is flagged in both directions.** Phase 4's AC-A6 says assert values, not the absence of a `PUT`, because a no-op PUT is correct there. After 5a, "no writes when nothing changed" is the assertion — **for monsters and minions only.** Locations and Bystanders keep Phase 4's behaviour (decision 9 is monsters-and-minions only), so 5a must not "fix" AC-A6.

**Six findings, routed:**

1. **H1 — "minions are already safe and show what right looks like" (architecture §5.2, rev 9) is true of the minion *row* and false of the minion's *sub-resources*.** `loadEditData` fills each `MinionDraft`'s four `existing*Ids` (`mystery-create.store.ts:1010-1013`) while building that draft's four sub-resource arrays with no id (`:995-1009`), and `saveMinionDrafts` deletes-all-and-recreates-all (`:1947-1953`) exactly as the monster path does. 5a converts both collections; the sentence currently implies only one needs care. **→ Yoshi, one corrected sentence.**
2. **H2 — the hazard state is re-created by every successful submit, and its consequence is churn, not destruction.** `submitPhase1` refreshes the baselines from the saved responses (`:1790-1793`) while the drafts still carry no id, so the state is reachable in **create mode** (Next, Back, Next) with no edit mode and no attach involved. And under a 5a diff the delete set and the create set are both "all of them" — content survives, every key rotates, and the dirty check can never fire for hydrated content. A 5a shipping this passes a content-preservation test and delivers neither of its purposes. Genuine outcome (ii) needs a path that fills the baseline and leaves the *drafts* empty — which is H3. **→ Yoshi (scoping correction), Toad (why 5a-U1/U9 are phrased as they are).**
3. **H3 — the biggest unspecified thing in 5b.** `MonsterListItemResponse` carries counts, not content, and no minions (`core/models.ts:191-205`). So attach-a-monster cannot populate a diffable `MonsterDraft` from the picked option; it needs `getById` plus `getByMonster` plus a `getById` per minion — a 1+1+N fan-out — while UX §3 specifies attach as commit-on-pick with the card appearing immediately. Three unspecified states: during the fetch; if the fetch fails (roster card says `Attacks: 4`, composer shows zero, same screen); and pressing Next in that state, which is quiet but leaves the user editing a monster they can only partly see. **My position, as input not decision: the card must not enter the roster until its subtree is in hand** — a monster card that under-reports its contents is the one display error here that leads a user to destroy data by hand. **→ Rosalina (interaction + failure copy), Yoshi (whether attach may fan out, and whether a card may precede its subtree).**
4. **H4 — §7.7d and §7.7e don't compose when a minion's deletion outlives its monster.** Delete a minion, then remove its monster: the minion's draft leaves the roster with its parent, so §7.7e's "drop dispositions whose id is in the current drafts" no longer protects it. Under a monster **detach** — which the modal says leaves minions untouched — the pending minion deletion still drains and destroys that minion in every other mystery. Cheap fix available, same shape as §7.7e: when a monster leaves the roster, drop its minions' dispositions too. **→ Yoshi.**
5. **H5 — `membershipPersisted`'s dispatch is a silent-fallthrough ternary** (`:1173`): `collection === 'locations' ? … : existingBystanderIds()`. Adding `'monsters'` and `'minions'` makes both resolve to the bystander baseline with no compile error, on the path that decides whether a destructive button appears. §7.7b flags the *name*; the dispatch is a separate problem and renaming does not fix it. Make it a `switch` with a `never` default. **→ Luigi / Yoshi.**
6. **H6 — phase 1 drains inside the monster save chain** (`:1768-1800`), so a failed monster save skips the drain; phases 2 and 3 drain as a `forkJoin` sibling regardless. 5a makes a confirmed minion deletion hostage to the monster save, and 5b's decision 19 removes the monster save entirely. The drain should move out **unconditionally**, not only for the empty-roster case §6.5 already names. **→ Yoshi, one line.**

**Method note, since it reproduced last time's result:** three of the six came from reading `mystery-create.store.ts` and `core/models.ts`, not the design documents. Neither document is wrong about any of them; both are silent. Contract shapes (`MonsterListItemResponse` carrying counts rather than content) are where the silence concentrates, because a design doc describes the entity and the code describes the payload.
