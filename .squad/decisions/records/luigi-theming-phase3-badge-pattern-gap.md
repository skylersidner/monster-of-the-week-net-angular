### 2026-08-02: Theming Phase 3 — "Type Badge Pattern" Goal Text Doesn't Match Its Own File List
**By:** Luigi (Frontend Developer)

**What:** Phase 3's Goal states it "establishes the type badge token pattern... in one place before it's reused across every list page in Phase 4." I checked all three of Phase 3's files (`bystander-detail.html`, `location-detail.html`, `minion-detail.html`) for an existing rendered type badge to re-point onto `--color-badge-{domain}`/`--color-on-badge-{domain}` — **none of the three has one.** Each shows its type as a plain `<app-custom-select>` form field ("Bystander Type" / "Location Type" / "Minion Type"), not a colored pill. The actual badge markup (`bg-blue-100 text-blue-800`, `bg-green-100 text-green-900`, the minion `#fde8d8`/`orange-800` pair) lives only in the three corresponding **list** pages (`bystanders-list.html`, `locations-list.html`, `minions-list.html`) — all Phase 4 files — plus `monster-detail`/`monsters-list`'s archetype badge (Phases 4/5) and `search-results.html` (also Phase 4).

**What I did:** Did not invent new badge UI on any of the three Phase 3 pages — that would be new-feature scope, not a re-point, and isn't in Phase 3's own "Files changed" list. Re-pointed only what's actually present in scope: the Detail Form Pattern (input/textarea borders → `border-strong`, focus states → `focus:border-accent`/`focus:ring-focus`, save/add buttons → `bg-accent`/`text-on-accent`, the "Saving.../{{activeMutation()}}" status line → `text-primary`) across all three pages (5 forms total in `minion-detail.html`), plus `minion-detail.scss`'s `@reference` fix and its two `@apply` rules (`bg-gray-100` → `bg-surface-hover`, `bg-red-100 text-red-600` → `bg-danger-subtle text-danger`). Left `text-red-800` (error banner) untouched in all three — that literal is used identically on ~9 other pages spanning every later phase and is explicitly Phase 7's sweep responsibility, not scoped to any single earlier phase. Left the sub-resource entity-card wrappers, list-item dividers, weapon-tag chip, and muted description text in `minion-detail.html` untouched — out of the "form/label/input/button" scope, and `monster-detail` (Phase 5) is where the equivalent, more-thorough sub-resource-grid treatment is explicitly planned for the structurally-identical pattern.

**Why it matters:** Phase 4's own text ("List Page / List Item Card / Action Button / Type Badge patterns' token equivalents") is internally consistent with what I found — it's Phase 4 that owns the *only* existing badge instances, not Phase 3. Recommend correcting Phase 3's Goal sentence to drop the "establishes... in one place" claim (or reframe it as "the badge tokens are already defined per the Catalogue; Phase 4 is their first real consumer") so a future reader doesn't go looking for a badge in these three files and conclude one was missed.
