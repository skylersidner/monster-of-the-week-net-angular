### Hunter Playbooks — real limitation found in the splice-formatting technique: mixed-styling repeated phrases (2026-08-28)
**By:** Bowser (Backend Developer / DevOps)
**What:** While extracting The Hex's Rotes explanation (page 29), found a genuine limitation in `tools/pdf-extract/splice-formatting.mjs`'s forward-only sequential substring matching: when the same phrase repeats multiple times within one text block and only *some* occurrences are actually bold/italic in the source (a plain occurrence sandwiched between two styled ones), the matcher has no way to know "skip this occurrence, it's unstyled" — it matches the next literal substring occurrence regardless of styling, which can land on the wrong one. Concretely: page 29's explanation paragraph has three "use magic" substrings, but only the 1st and 3rd are bold in the source; the automated splice correctly matched the 1st, then matched the run list's 2nd entry against the *plain* 2nd occurrence instead of the truly-bold 3rd. Verified directly against the raw `pdf.js` item dump and hand-corrected that one paragraph's HTML rather than trusting the automated output — documented in `tools/pdf-extract/build-hex-review.mjs`'s header comment and a dedicated `restCorrectionNote` field in `hex-review.json`, kept visibly distinct from every other splice-derived field. Separately (same pass), also found and fixed a related-but-different bug: splitting one continuous flow across multiple independent `splice()` calls that all share the same full runs.json lets a run already consumed by an earlier call match again in a later, unrelated call — fixed by manually partitioning the runs array per paragraph before calling `splice()`.
**Why:** This is the first genuine limit found in the splice *technique* itself (not a column/section scoping mistake, which every prior false positive in this pipeline has been). Every future pass needs to know: whenever a phrase repeats 2+ times within a text block being spliced, and that block has ANY bold/italic styling on occurrences of that phrase, verify the placement against the raw `dump-page.mjs` item dump before trusting the automated splice output — don't just eyeball the final joined string for plausibility, since a wrong-but-plausible-looking match is exactly the failure mode here. This doesn't invalidate the splice technique generally (single-occurrence and uniformly-styled-repeat cases remain safe and have been the overwhelming majority of every pass so far) — it's a narrow, identifiable edge case worth a specific checklist item, not a reason to distrust the whole pipeline. Full detail, including the exact mechanism and both bugs, in `docs/hunter-playbooks/pdf-extraction-pipeline.md`'s "Twelfth pass" section.

**Update (2026-08-28, seventeenth pass / "Sixteenth pass" in the pipeline doc — The Monstrous):** the cross-call-run-leakage bug (this doc's second bug, not the mixed-styling one) recurred, confirming it's a general risk rather than a Hex one-off, via a *different* triggering mechanism. On page 38's 7 "Monster Breed Suggestions" entries, sharing one unscoped runs list (7 entries × 4 runs, in stream order) across 7 `splice()` calls let an EARLIER, textually-repeated run ("Curse", present verbatim in every entry) match and advance the forward-only cursor within a LATER entry's own text before that entry's own name-run — which appears EARLIER in that entry's own text — could ever be reached. Only entry 1 escaped by luck of being first; entries 2-7 silently lost their bold names on the first attempt (the 3 italic sub-labels still matched fine, masking the bug from a shallow glance — worth noting since a partial-success case like this is easy to miss). Hex's version was triggered by a repeated *plain* word reappearing in later prose; this one by an earlier *run* in the list matching inside later, unrelated text. Same fix both times: partition into one scoped runs subset per call, never share one runs.json across multiple `splice()` calls covering structurally-repeated content. With 2 independent occurrences via 2 different mechanisms, this is now a standing checklist item for this pipeline, not a Hex-specific edge case — before calling `splice()` in a loop or from multiple call sites against the same section, always scope its runs argument to just that call's own content. Full detail in `docs/hunter-playbooks/pdf-extraction-pipeline.md`'s "Sixteenth pass" section.
