# Standalone Creation Phase 3 (Locations) — Architecture Decisions

**By:** Yoshi (Architect)
**Date:** 2026-08-05

**What:**
- **Backend work needed: yes**, mirroring Monster's Phase 1 gap exactly. `Location↔Mystery` is genuinely M:N via a `MysteryLocation` bridge table (no `MysteryId` FK on `Location` at all — confirmed at the entity), and the existing `POST /api/mysteries/{mysteryId}/locations` always requires and links a mystery, same shape `MonsterService.CreateAsync` had pre-Phase-1. New `CreateAsync(UpsertLocationRequest)` overload + `POST /api/locations`.
- **Location has no interactive sub-resources — the entire draft-array/batch-submit design problem from Phases 1/2 doesn't apply.** `Location`'s only child collection is `CustomMoves`, and `location-detail.ts` renders it fully read-only today (no add/edit/delete UI at all, despite full CRUD existing on the backend) — same "backend supports it, frontend never built UI for it" shape already established for Monster's and Minion's custom moves, reconfirmed independently for Location. The create page is a single 3-field form, one API call, no batching, no partial-failure case.
- Mystery-scoping (optional dropdown, defaults blank) and the entry-point choice (top-level `/locations` list only, no second entry point) are **reused directly from Monster's Phase 1 answers**, not re-asked — Location's relationship to Mystery is the identical bridge-table M:N shape, not merely similar.
- Shared `LocationFormComponent`, extracted from `location-detail.ts` (confirmed immediate-mutation, single `update()` call — same "share only when submission models match" justification as both prior phases), wired into `location-detail.ts` in the same phase (third time this exact shape of decision has come up; Skyler answered it the same way twice already, so it's decided directly rather than reopened a third time).
- **Zero open questions for Skyler** — every fork this phase could plausibly have had resolves to a verified fact (schema shape, existing UI scope, precedent already set) rather than a judgment call.

**Why:**
- The task explicitly warned not to assume Location's shape from Monster's or Minion's docs — verified fresh: entity definitions (`Data/Entities/DomainEntities.cs`), `LocationsController.cs`/`LocationService.cs`/`ILocationService.cs` in full, `location-detail.ts`/`.html` and `locations-list.ts`/`.html` in full, `core/location.ts`, and the request/response contracts in `core/models.ts`. Two of the three central questions (sub-resource shape, entry-point fork) came out *differently* from Phases 1/2 as a result — worth remembering that "this domain looks structurally like the last one" is a hypothesis to check per-domain, not a default to assume, even three phases into the same initiative.
- Generalized a principle worth naming for future phases: **when a new phase's underlying relationship shape is structurally identical (not just similar) to an already-decided phase's shape — confirmed at the entity/contract/controller layer, not just "seems the same" — re-deriving or re-asking the same question is redundant, not more careful.** Applied this to decline reopening mystery-scoping, entry-point placement, and the detail-page-rewire timing question, all citing Monster's/Minion's already-settled answers for the identical shape of decision rather than re-presenting them as fresh forks.
- Declined to introduce a `mystery-detail.html`-scoped "Add Location" entry point even though it would have been cheap to build, specifically to avoid a new cross-domain asymmetry — Monster's Phase 1 already deferred the equivalent entry point for the identical relationship shape; building it now for Location only, without also retroactively adding it for Monster, would create an inconsistency between two domains with identical relationship shapes rather than resolve one.
- Flagged explicitly, for whoever writes the Bystander phase next, that `Bystander` looks structurally identical to `Location` at a glance (M:N to Mystery, a `CustomMoves`-only child collection) but that resemblance is exactly the kind of assumption this phase was told not to make about Location itself — the next phase needs its own fresh verification, not a copy of this doc's conclusions.
