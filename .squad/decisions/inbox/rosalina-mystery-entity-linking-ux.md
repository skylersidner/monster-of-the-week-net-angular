### 2026-09-19: Mystery Entity Linking — Wizard Roster + Composer, Generalised to All Four Entities (UX design, advisory)
**By:** Rosalina (Designer)

**What:** Produced `docs/updates/mystery-entity-linking-ux.md`, the UX/visual half of connecting existing Monsters/Locations/Bystanders to a Mystery (Yoshi's `docs/updates/mystery-entity-linking.md` covers the data/API half). Recommended pattern for every entity phase in the wizard: **a roster of summary cards above a single active composer**, with a compact "add an existing one" strip between them. The pencil on a roster card pulls that entity into the composer; the loaded card takes `bg-accent-subtle border-accent` plus a literal `Editing` micro-label, and the composer header reads `Add a {Noun}` / `Editing “{name}”` with footer verbs `Save {Noun}` / `Save Changes` + `Cancel`.

**The finding that shapes everything:** this pattern already ships, for minions, at `mystery-create-monster-phase.html:148-372` — Luigi built it from my 2026-08-31 minion design. So the work is not "design a re-edit affordance," it is "lift the shipped one to Monster, Location and Bystander, add one attach strip, extend one modal." All per-entity differences fit in one column of one table (badge token, secondary `<small>` line, composer fields, extra control, attach source, modal variant).

**Judgment calls:**

1. **Attach strip, not a second card.** Yoshi §5.3 proposes a second bordered card above the add-new card; at `md:w-[42%]` two stacked bordered cards read as two equally-weighted forms at the exact moment the user is least sure which to use. The strip reuses today's location summary-row class string (`bg-surface-sunken border border-default rounded-md … px-3 py-2`), giving two tiers instead of three: light strip = pick existing, heavy card = author new. Single-select, commit-on-pick, no Add button (a third accent-ish control would compete with `+ Add Another X` and `Next →`). Hidden entirely when the catalogue is empty; `emptyText` when it is merely exhausted.
2. **Removal modal: one component, three copy variants.** Extend `ConfirmDeleteModalComponent` (already extended three times the same way) rather than writing a second dialog. Variants: never-persisted (`Cancel · Remove`, empty permanence note — matches the shipped `pendingRemoveNote()` logic exactly); persisted-and-sole (`Cancel · Detach · Delete`); persisted-and-shared (same buttons, plus the other mysteries listed in the existing `[items]` input, which is passed `[]` everywhere in the app today and exists for precisely this). `Delete` stays rightmost and `bg-danger`; `Detach` is outline-accent immediately left of it — outline-vs-filled reads as safe-vs-destructive faster than two filled hues. Copy says "Changes take effect when you continue to the next step," **not** "This cannot be undone," because at read time it isn't true yet (dispositions execute at phase submit).
3. **Membership edits inside a form never confirm.** Unchecking a mystery chip on a location's edit form is a reversible form edit; raising the modal there would train dismissal on a dialog we need read.
4. **Monster picker for minions copies *both* halves of `minion-create.html:14-30`** — the `isMonsterLocked()` prose line for a one-monster roster, the select for 2+, plus its existing "A minion must belong to a monster." error sentence. First field of the composer, not last: it is the minion's parent and every other field is meaningless without it.
5. **Mystery chips use `bg-badge-mystery`, not the weapon-tag chip.** `search-results.ts:81-85` already establishes amber as the Mystery domain colour app-wide; indigo would put an accent-coloured chip in a form for a non-accent concept. Otherwise `MysterySelectComponent` is `WeaponTagSelectComponent` verbatim.

**Two explicit disagreements, both filed as open questions rather than silently overridden:**

- **Against Yoshi §4.4** — membership chips should *not* be `.entity-link` anchors. The form is frequently dirty and no `CanDeactivate` guard covers the entity detail/edit pages, so a link out of a live form control is a data-loss trap. If the navigation is wanted, it belongs in a separate read-only "Appears in: …" line. (Yoshi conceded this in rev 3; it is no longer an open question.)
- **Against Skyler's own framing** — recommend offering `Detach` whenever the entity exists in the catalogue (`id !== null`), not only when it is in 2+ mysteries. Under the M:N model an unattached entity is a first-class, reachable state (the create pages produce them, the flat lists show them), so "keep it, just not here" is always valid; making the only non-destructive escape appear and disappear based on invisible state is confusing. His literal rule is the named conservative fallback.

**Architecture consequences of Skyler's "any entity editable in the wizard" (§10 of the doc), flagged for Yoshi:**

- His two-value `origin: 'authored' | 'attached'` no longer works, because `attached` meant "never PUT this entity's fields." Narrow rather than drop the safety property: **an attached entity is never written unless the user explicitly edited it this session** — which needs a third state. Critically, "edited" must mean *committed a differing change via `Save Changes`*, not *loaded into the composer*, or cancelling out of an attached entity silently marks it dirty.
- Drafts need a **stable client key**: the minion composer's monster picker cannot use a server ID (roster monsters may have `id: null`), `track $index` re-animates every row when one is removed, and `removeMinionDraft` already documents the index-shift hazard.
- Drafts need `mysteryIds` carried through (the data is already on the three `…ListItemResponse` DTOs), and the wizard needs one `mysteryService.getAll()` so the modal can *name* the other mysteries. A bare count doesn't let anyone choose between Detach and Delete.
- "In baseline but no longer in the list" stops meaning "unlink" — it now means whatever the modal decided, so removal needs a disposition argument the store holds until submit.

**Live accessibility defects found in the shipped minion roster** (they quadruple if replicated as-is, so they are requirements, not polish): activating the pencil **unmounts the pencil** (it is replaced by the static `Editing` span), orphaning keyboard focus to `<body>` — fix with the `wizard-layout.ts:47-60` idiom (`afterNextRender({write})` + `tabindex="-1"` composer heading + `focus({preventScroll:true})`), which also announces the mode change without needing `aria-live`. Action buttons carry only a generic `title="Edit minion"` and need `aria-label` including the entity name. `ConfirmDeleteModalComponent` has `role="dialog" aria-modal="true"` and nothing else — no initial focus, no trap, no Escape, no focus restore, hardcoded `id="modal-title"`; with a third consequential button that is no longer acceptable, and initial focus must land on `Detach` (or `Cancel`), never `Delete`. Separately flagged `CustomSelectComponent`'s wrong ARIA (`role="listbox"` over plain `<button>` children, no `aria-activedescendant`, no Escape) as pre-existing but newly load-bearing, since the attach strip makes it the sole entry point to a new capability.

**No new visual language.** Every class string in the doc already ships; §13 maps each need to the exact existing file and line to build on.

**Open for Skyler (9, in the doc):** most important are #1 (widen Detach's availability) and #2 (do Locations/Bystanders keep today's stay-open composer, or collapse like minions and pay one extra click per item in the app's most repetitive flow?).

**Update 2026-09-19 — reconciled against Yoshi's rev 3. Two of my calls corrected; I agree with both.**

1. **My "don't write an unedited attached entity" is accepted in substance, rejected in mechanism — rightly.** The *reason* I gave was dead on arrival: I argued it from "attaching must never mutate the attached object," but Skyler wants mutation and writing identical values back is not a mutation. The surviving reason is **write amplification**, and it is entity-dependent in a way I never separated: a flat Location costs one no-op `PUT`, while a monster under the shipped delete-all/recreate-all cycle has all eight sub-resource collections deleted, recreated and re-keyed on a `Next` the user never touched. It is also **shipped behaviour, not something attach introduces** — `submitPhase2` already `PUT`s every draft with `id !== null` on every phase transition, touched or not (`mystery-create.store.ts:1323-1327`). The mechanism is a **baseline snapshot on the draft, compared row-by-row at submit**, not the third `origin` state or `edited: boolean` I proposed. Two reasons it wins, the second of which is my own objection turned against me: a stored flag desyncs when someone edits and reverts; and my hardest caveat — *a cancelled edit must not count as an edit* — enforces itself for free, because a cancelled edit leaves the draft equal to its baseline by construction. Per-row also beats per-entity (renaming a monster shouldn't rewrite eight sub-resources). **Lesson worth keeping: I turned a correctness property into interaction semantics.** "Edited means committed-not-loaded" was a rule a user could never see and a reviewer would have had to memorise, and it would have leaked into copy eventually; a structural store-layer answer leaves the UI unchanged, which is the tell that it's the right layer. `origin` drops out of the submit decision entirely and survives only as display metadata — which §11 already recommends not displaying. **One dependency:** row-by-row comparison is contingent on Yoshi's New Question 1 (sub-resource upsert). If Skyler declines it, delete-all/recreate-all stays, a per-row diff can't express "leave this attack alone," and per-draft dirty tracking becomes load-bearing again — caveat and all.
2. **Factual correction: this app *does* have an unsaved-changes guard.** `features/hunters/pages/hunter-create/hunter-draft.guard.ts` is a `CanDeactivateFn` whose own comment calls it "the app's first," registered at `hunters.routes.ts:15`, paired with a `window:beforeunload` `@HostListener` at `hunter-create.ts:134`. My chips-as-links conclusion is unaffected and Yoshi has conceded it, but the true claim is narrower — **no guard covers the entity *detail* pages** — and the correction *upgrades* the "Appears in: …" follow-up from "needs a guard invented" to "has a shipped pattern to copy." **Lesson: I generalised "I didn't find one in the surfaces I read" into "this app has none."** I read the wizard and the entity detail/create pages; the guard lives in the hunter feature, which I had no reason to open. A negative claim about the whole app needs a repo-wide grep, not an inference from the pages in scope — the same failure mode as the `fill="currentColor"` mistake of 2026-09-18.

**Update 2026-09-19 (later) — Skyler answered all seven of Yoshi's questions; three land here and one grew the modal design.**

- **My OQ1 answered in my favour over his own earlier rule:** Detach is offered whenever the entity exists in the catalogue, not only when it is in 2+ mysteries — conditioned on the modal stating how many other mysteries it belongs to. **OQ7 answered yes** (fetch the mystery list, so the modal names them). These are not in tension: variant (C) states the count in the sentence and lists the names beneath it, so naming does not replace counting.
- **His answer 7 (extend the detach/delete modal to non-wizard lists/details) is a real scope addition, and auditing it produced the most useful finding of this pass.** Two things: (1) **`Detach` requires a mystery context, and only the wizard has one** — on `/locations` there is no "this mystery" to detach from, so the list-page variant is two buttons, not three; what the list pages gain is the *usage disclosure*, not the third button. (2) Of the fourteen `<app-confirm-delete-modal>` call sites, **only three need anything** (`monsters-list`, `locations-list`, `bystanders-list`). `monster-detail`/`minion-detail` modals are for sub-resources, which have no membership; `location-detail`/`bystander-detail`/`monster-detail` have no entity-level delete button to extend at all; hunters/mysteries/playbooks/minions have no membership. The one surface that genuinely wants the full three-button treatment — `mystery-detail`, the only non-wizard page with a mystery context — has **no remove affordance to extend**, so I filed it as new **OQ10** and recommended *not now* rather than quietly widening the change set.
- **Correcting my own earlier error, which mattered:** I wrote that `[items]` "is passed `[]` everywhere in the app today." Wrong — **`monsters-list.html:50-51` already passes minion names with a swapped `[message]`**, which makes it the shipped precedent for this whole treatment rather than a greenfield input. That matters because his answer 5 (confirm minion cascade on monster delete) is therefore *already true on the monsters list*; what is new is doing it in the wizard roster. It also forced the real design call: a monster removal answers two different questions at once — *where is this used* (drives Detach vs Delete) and *what gets destroyed* (drives Delete vs Cancel) — and those cannot share one list. `[items]` keeps its shipped cascade meaning; a new `usage`/`usageMessage` pair renders above it. Also found that `permanenceNote` only renders *inside* the `items.length > 0` branch (`confirm-delete-modal.component.html:18-20`), so it silently vanishes for a flat Location with no cascade — exactly the common case; render it unconditionally and rename it `footnote`, since it now carries button guidance too.
- **Answer 6 (minions always travel with an attached monster) fixed a subtlety I would otherwise have got wrong:** the cascade sentence attaches to **Delete only**. Detach leaves the minions alone, because they travel with the monster rather than with the membership. The footnote has to say so or it implies minions die either way.
- **Answer 1 resolved my §10.1 dependency favourably:** sub-resource upsert approved and dirty-tracking explicitly endorsed, so the "if declined, the flag semantics come back" branch is dropped. Dirty-tracking survives as Yoshi's baseline-snapshot row-by-row diff — an **optimisation against write amplification, not a correctness guard**.
- **Copy call worth keeping:** wizard variants say *"2 **other** mysteries"*; the list-page variant says *"2 mysteries"*, because on a list page there is no current mystery for the others to be other than. One word, and getting it wrong makes the count read as off-by-one.

**Update 2026-09-19 (final) — Skyler answered the six remaining questions; the design is settled and nothing is outstanding.**

- **OQ2 "Yes, collapse after save"** — all four entities, no exception for the flat ones. Recorded in §2.3 *with the cost named as accepted rather than absent*: adding four locations in a row now costs four extra clicks it didn't before, and the exception is a one-line change if it ever grates.
- **OQ3 "Roster rows can grow"** — the strip→card upgrade for Locations/Bystanders is approved.
- **OQ4 "Detach and Delete is fine. I understand the risk, but it's not a concern for me."** Written up as a risk **presented, understood and accepted**, not one judged absent, with both mitigations (relabel to `Unlink`; move `Delete` out of the rightmost slot) kept on file as the first thing to revisit if a misclick is ever reported. Worth doing deliberately — an accepted risk recorded as "fine" loses the reasoning that would make a future reversal cheap.
- **OQ5 "No, don't display on the roster card"** — attached, authored and widely-shared entities all render identically. Consistent with the no-warnings position; sharing is disclosed at the one moment it changes a decision (the removal modal). Side effect worth noting for Luigi: with `origin` neither driving the submit diff (see the rev-3 update above) nor displayed, **it may not need to exist as a field at all.**
- **OQ8 "Include Escape closes and restores focus as part of this scope"** — now specified implementably in §8.7 (template ref on the trigger, `@HostListener('keydown.escape')` so the searchable variant's input is covered too, early-return when already closed, `stopPropagation` + `preventDefault`, clear `searchTerm`, refocus trigger) with Toad cases. **The early return and `stopPropagation` are load-bearing and the reason is cross-cutting:** once the confirm modal also closes on Escape, a select *inside* that modal must swallow the first Escape and let the second through. Get either wrong and the dropdown takes the whole dialog down with it. Yoshi is placing this in Phase 3. The component's remaining ARIA gaps (`role="listbox"` over non-`option` children, no `aria-activedescendant`, no arrow keys) were **not** in the ask and are listed as a follow-up so the fix isn't mistaken for conformance — it makes the control *dismissable*, which is the part this feature depends on.
- **OQ10 punted, with instruction: "Make note of it for things to follow up on after the final phase."** Given a durable home as **§12.1**, not left as a struck-through question. Yoshi keeps the master follow-up list; §12.1 holds the design-side items and cross-references his rather than duplicating them. The asymmetry preserved in writing: `mystery-detail` is the only non-wizard page with a mystery context, so it's the only place outside the wizard where Detach is meaningful, yet it has no remove affordance to extend — which makes it the natural pair to his Phase 5 "attach from mystery detail," and the two should be designed together, because **a page that can attach but not remove is worse than one that does neither.**
- **OQ9 was never Skyler's** and is restated in place as Luigi's implementation-time call (shared components vs. four agreed copies), explicitly non-blocking, so it isn't misread as an unanswered question.

Status line now reads **"Settled — ready for implementation."**

**Update 2026-09-19 (post-Phase 3) — two of my claims were wrong in implementation. Corrected in place with the reasoning, since the wrong versions both read as safe.**

1. **The footnote default.** I wrote that keeping `permanenceNote`'s `'This cannot be undone.'` default "still works for every current caller." It does not: because that input never rendered (the bug I found), call sites had been passing the sentence as **`message`** instead, using `message` *as* the footnote. Rendering the footnote unconditionally while keeping the default prints the sentence **twice**. Default must be `''`; Luigi caught it and filed it. **The count in the shipped code comment and spec (`confirm-delete-modal.component.ts:64`, `.spec.ts:154`) says seven and undercounts — it is ten.** Seven pass the sentence explicitly (`playbook-admin`, `bystanders-list`, `hunters-list`, `locations-list`, `hunter-detail`, `minions-list`, `monsters-list`); **three more pass no `message` at all and inherit its default, which is the same sentence** (`mysteries-list.html:42-47`, `monster-detail.html:236-241`, `minion-detail.html:206-211`). Same fix either way, so nothing shipped wrong, but the comment's number is off and those three are the easy ones to miss. Also recorded: `monsters-list` *with* minions genuinely did render that line before (items was non-empty, so the old conditional footnote fired), so that branch needs an explicit footnote to keep it — only the no-minions branch would have doubled. **Root cause worth keeping: I characterised a default from the component's side of the boundary without checking what callers passed into the adjacent input. Same class as assuming `[items]` was unused — twice now, so it is a pattern, not a slip. When a fix changes *whether* a block renders, every caller's other inputs are in the blast radius.**
2. **The call-site count is thirteen elements across twelve template files, not fourteen and not twelve.** `hunter-create.html` is the only page with two (`:57` switch, `:69` discard). My original "fourteen" came from a `files_with_matches` grep — **that counts files, not elements**, and included the component and its own spec, neither a call site. A later recount also said fourteen by reading the closing `></app-confirm-delete-modal>` tags at `monster-detail.html:241` and `minion-detail.html:211` as second elements; they are the same elements closing. Count with an opening-tag pattern. The audit's conclusion (three surfaces need work) is unaffected either way.

**Ratified with one change — the mystery-fetch failure case.** Luigi suppresses the usage block entirely rather than defaulting to "isn't used by any mystery," reasoning that a false zero on the highest-consequence destructive action is worse than no claim. I agree with the reasoning and **overrode the treatment**: once users learn the modal always reports usage, an *absent* block reads as "used nowhere" exactly as a false sentence would — same wrong inference, quieter, and unfalsifiable from the user's side. Specified instead `usageMessage = "Couldn't check which mysteries use this {noun}."` with empty `usage`, footnote unchanged, **confirm button left enabled** (a network blip must not block a legitimate delete). One string, no new input, and it converts an invisible failure into a visible one on an irreversible action.

**Also folded in as confirmations, not corrections:** the as-built input surface is now recorded in a new §7.7 as the contract the remaining phases code against (`usageMessage`/`usage` new, `message`/`items` unchanged and keeping the cascade meaning, `permanenceNote`→`footnote` unconditional with `''` default, `secondaryLabel` + `(secondary)` output); render order asserted as an **ordered list of blocks** rather than presence checks, which is right because order is load-bearing; initial focus on secondary → Cancel → never confirm. `shared/mystery-usage.ts` centralising the sweep copy is a better call than I specified in one respect worth naming: **it takes the count from the resolved-names array rather than from `mysteryIds`**, so "2 mysteries:" followed by two bullets is an invariant rather than a coincidence — I had left that gap by implying the count came from the IDs. And a typing gotcha for §8.7: `$event` on a `keydown.escape` **pseudo-event** must be typed `Event`, not `KeyboardEvent`, or `TS2345`.

**New requirement identified during Phase 3: §8.6, focus after the composer collapses.** `Save Changes` and `Cancel` unmount their own buttons exactly as the pencil does, so focus is orphaned to `<body>` on the way *out* of the composer just as it was on the way in. **Filed into §8.6, not §12.1** — deliberately, because the argument that got the other three a11y items scheduled ahead of everything applies identically: it is a defect in the *already-shipped* composer and replicating the composer quadruples it. §12.1 is for work deferred past the whole feature; this is work the feature makes worse. Items 1 and 6 should be treated as one pair — entry and exit of the same focus contract, and fixing only one lets a keyboard user into the composer but not out. OQ2's "always collapse" also killed the two-branch version of this item; there is one path now.
