### 2026-08-04: Mystery Create Wizard — Bug 2 (Duplicate Entities on Phase Revisit) Design
**By:** Yoshi (Architect)

**What:** Confirmed and broadened the root cause, and specced the fix, for `MysteryCreateStore`'s "revisiting a completed phase re-submits it" bug (`docs/theming/found-bugs.md` Bug 2). Root cause: the store already has a complete per-entity ID-tracking mechanism for create-vs-update branching (`mysteryId`, `editingMonsterId`, `editingMinionId`, `existingMonster*Ids`, `existingMinion*Ids`, `existingLocationIds`, `existingBystanderIds`) — but it is only ever populated by `loadEditData()`, i.e. only when the wizard was opened in whole-mystery edit mode via a route `:id`. In the create-new-mystery flow these signals stay empty/null for the entire session, even after a phase's first successful submit, so every subsequent submit of that phase (via jump-back-then-Next) branches into a fresh `create()`/`POST` instead of `update()`/`PUT`. This is not phase-1-specific: `submitPhase0()`'s branch is gated on `this.isEditMode() && existingId`, not just `existingId`, so **phase 0 has the same bug** — revisiting the concept/hook/overview/countdown steps and pressing Next again creates a second Mystery row and silently reassigns `mysteryId` to it, orphaning the first. The doc's repro (monster phase) is real but is one instance of a pattern present on all four phases.

Recommended fix (generalize the existing per-entity-ID pattern to also populate on create, not just on edit-load; no new paradigm):
- `submitPhase0`: drop `isEditMode() &&` from the branch condition — key off `existingId` (`mysteryId()`) alone. Always `this.mysteryId.set(mystery.id)` after save (currently only set `if (!isEditMode())`).
- `submitPhase1`: keep the existing `editingMonsterId()`/`editingMinionId()` branch conditions as-is (already correct in shape) but set `editingMonsterId`/`editingMinionId` immediately after each save resolves, in both create and update flows — not only in `loadEditData()`. Restructure `saveThreatCollections`/`saveMinionCollections` to return the created records (keyed `{attacks, powers, weaknesses, armors}` via `forkJoin`, not a flattened `unknown[]`) so `existingMonster*Ids`/`existingMinion*Ids` can be set from the real IDs after every submit. Sub-item create/delete stays delete-all-then-recreate-all (unchanged) — per-item PUT isn't wired for attacks/powers/weaknesses/armors at the Angular service layer (`MonsterService`/`MinionService` have no `update*` methods for these, matching the pre-existing gap Yoshi already logged for `MinionService` during Phase 8 minions planning), so that's not a viable smaller diff here.
- `submitPhase2`/`submitPhase3`: type the raw `apiService.post(...)` calls to their real response types (`LocationDetailResponse`/`BystanderDetailResponse`, both already exist and have `.id`) instead of `unknown`, and set `existingLocationIds`/`existingBystanderIds` from the created IDs after every submit. Widen `runBatch<T>(requests: Observable<T>[]): Observable<T[]>` (currently hardcoded to `unknown`) to carry the type through.
- No change to `isPhaseAccessible()`/`jumpToPhase()` (already correct) and no guard added to `next()` — once every phase's submit is a true ID-keyed upsert, resubmission of an unchanged phase is a harmless idempotent PUT, and resubmission of a phase the user *did* edit after revisiting correctly updates the same row instead of creating a duplicate. This also resolves the doc's own edge case (edit phase 1, go back to phase 0, come forward again) for free, without dirty-checking.
- Rejected the doc's direction 1 (skip resubmission if nothing changed): doesn't cover the "user actually edited a completed phase and revisits" case, which the fix needs to support anyway, and adds real complexity (snapshot + diff of reactive form state) for a case the ID-keyed upsert already handles for free.
- `isEditMode` stays whole-mystery/route-scoped exactly as today (governs `isPhaseAccessible()`'s free-navigation short-circuit, the final "created"/"updated" toast, and `loadEditData()`'s bulk hydration) — not repurposed or merged with the per-entity ID tracking. They're genuinely different concepts (session-level "am I editing an existing mystery" vs. entity-level "does this specific row exist yet").

**Why:** The correctness mechanism this bug needs (upsert-by-ID, branch on presence of an ID) already exists in the codebase and is already the established pattern (`submitPhase0`'s `isEditMode()`/`existingId` branch, `submitPhase1`'s `editingMonsterId()` branch) — the bug is a wiring gap (these signals are edit-mode-load-only), not a missing mechanism. Generalizing the existing pattern to also populate on first create is the smallest correct fix, stays inside the phase-level-submission architecture already decided in `.squad/decisions.md` (2026-07-21 entries), and avoids introducing a second, competing "has this changed" state-tracking mechanism alongside the ID-based one already in place.

**Known pre-existing, out-of-scope items surfaced during this review (not part of this fix):**
- Locations/bystanders use "unlink from mystery" (not hard delete) on resubmit, by design — `LocationDetailResponse`/`BystanderDetailResponse` carry `mysteryIds: string[]`, confirming these are genuinely many-to-many/reusable entities, not mystery-owned like monster sub-items. Post-fix, revisiting phase 2/3 with edits will still unlink-old+create-new (not true per-row PUT), leaving the old row orphaned-but-undeleted in the flat `/locations`/`/bystanders` catalog. This already happens today in edit mode; the fix doesn't add it, just extends existing behavior to the create-flow revisit case. A true per-row diff/PUT would need `LocationDraft`/`BystanderDraft` to carry an `id`, which is a bigger structural change — flagged as a possible future improvement, not required for this bug.
- No mid-wizard state persistence exists at all (`init()` runs once from a route-snapshot `:id`, no localStorage/sessionStorage draft save) — a page reload after phase 0 has already created a Mystery row today loses `mysteryId` entirely and would create an unrelated second Mystery on next submit, before and after this fix. Unrelated to the ID-upsert gap; flagged as a separate, real gap for Skyler to decide is in/out of scope for this bug's fix.
- Clearing the minion name field on a phase-1 revisit (to "remove" a previously-created minion) is currently a no-op — `submitPhase1` only skips *creating* a minion when the name is empty, it never deletes an existing one. Whether "un-populate the minion field" should delete the minion is a product question, not decided here.
- Dev-DB duplicates already produced by this bug (per the found-bugs.md doc) are explicitly not this fix's responsibility to clean up.
