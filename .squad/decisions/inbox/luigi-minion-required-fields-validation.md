**Why / judgment calls:**

1. **No new layout bug to fix, because I checked the label class before writing markup.** Monster's original mistake was writing a bare sibling span (`Name <span class="text-danger">*</span>`) against a `grid font-medium gap-1` label and only catching the CSS Grid auto-placement bug after Skyler reported it. Since `minion-form.html`'s labels use the identical grid class, I used the wrapper-span form from the first edit — confirmed correct live before calling it done, not inferred from the class name alone.
2. **The wizard's minion-phase labels are `display: block`, matching the monster-phase labels already audited during the Monster wizard follow-up** — confirmed by reading `mystery-create-monster-phase.html` (the minion phase lives inside this same file, gated on `store.currentStep() === 1`, not a separate `mystery-create-minion-phase.html` — no such file exists). Since this pass adds no asterisks there, the block-vs-grid distinction didn't end up mattering for any new markup, but was checked anyway before assuming it was safe to skip.
3. **`minionAttackForm.harm` got both `Validators.required` and `Validators.min(0)`, not just `Validators.required`,** because it had zero validators beforehand (matching `monsterAttackForm.harm`'s identical pre-fix state, which got the same two-validator fix in the Monster pass) — the doc's "add `Validators.required`" wording undersells what was actually missing; verified against the live file rather than trusting the doc's line-number paraphrase.
4. **Test coverage for the asterisk/maxlength convention added to `minion-form.spec.ts` only**, mirroring `monster-form.spec.ts`'s own pattern (`label.querySelector('span.text-danger')`, `input.maxLength`) — not duplicated into `minion-create.spec.ts`/`minion-detail.spec.ts`, matching Monster's precedent of only adding the conditional-required/conditional-asterisk-toggle specs to the page-level spec files (those two specs were not re-added here since Monster's originals already established the pattern and this is a mechanical port, and existing `minion-create.spec.ts`/`minion-detail.spec.ts` didn't have gaps analogous to the `specialDescription`-toggle one that needed covering before this pass — that coupling is new here, so I did check whether equivalent specs existed for Monster's armor forms and ported the same two per page, see Files below).
5. **`mystery-create.store.spec.ts` needed no changes** — checked first (per the doc's own "Bowser/Luigi" implementation-scope note and my own prior Monster-pass precedent of checking this file before editing the store): every existing test already sets explicit non-zero `harmCapacity`/`harm`/`harmSoak` values for the minion forms, so tightening the validators didn't flip any existing assertion.
