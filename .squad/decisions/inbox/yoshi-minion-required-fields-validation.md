# Minion Required-Field Validation — Architecture Decision

**By:** Yoshi (Architect)
**Date:** 2026-08-06

**What:**
- Field decisions: `Minion.Name` and four of five sub-resource `Name` fields (`MinionAttack`/`MinionPower`/`MinionArmor`/`MinionWeakness`) should be genuinely required via `[Required, MaxLength(255)]` on their `Upsert*Request` DTOs. The fifth (`MinionCustomMove`, via the shared `UpsertCustomMoveRequest`) is **already fixed** — Phase 2's "free multiplier" prediction confirmed live, zero new backend work needed there. `MonsterId`/`MinionTypeId` are already fully required and correctly enforced at the service layer (existence-checked, live-verified to never 500) — no backend gap on either FK, matching Monster's own "audit found nothing to fix" outcome. `HarmCapacity`/`Harm`/`HarmSoak` (non-nullable ints) get `[Range(0, int.MaxValue)]`, same category Phase 2 established for Monster.
- **New finding this phase, not present in Mystery/Monster**: `Minion.Name`'s blank/whitespace gap was already closed server-side, but via a hand-rolled `string.IsNullOrWhiteSpace` check inside `MinionService.CreateAsync`/`UpdateAsync` — exactly the "manual validation helper in the service" mechanism Phase 1's Architecture Discussion explicitly declined in favor of DataAnnotations. It only catches presence, not length (the live-reproduced 500-on-oversized-name gap still exists on this field), which is the substantive reason to still touch it. Recommended: add `[Required, MaxLength(255)]` to the DTO and remove the now-redundant hand-rolled check.
- Confirmed live, not assumed: `MinionFormComponent`'s `minionTypeId` control (`shared/minion-form/minion-form.ts:38`) has no `Validators.required`, identical bug shape to Phase 2's already-fixed `MonsterFormComponent.monsterTypeId` — a bug fix, not a product question. Its own spec file's touched-state assertions stop one field short of covering it, same reason the gap went uncaught in both cases.
- Confirmed Minion has already been through its own standalone-creation pass (`docs/updates/standalone-creation-phase2-minions.md`, shipped) — `MinionFormComponent`/`minion-create.ts`/`minion-detail.ts` all exist and work; Minion's sub-resource *forms* (attack/power/armor/weakness, both create-draft and detail-immediate variants) are already fully `Validators.required`-guarded client-side, no gap there. Also confirmed `docs/updates/multi-minion-support.md` is still genuinely parked — only its independent MM-1 (`DELETE /api/minions/{id}`) shipped; the list-of-minions wizard rework (MM-2/MM-3) never landed, so the wizard's minion-Name field still uses a conditional-required computed-signal hack by design, out of this pass's scope.

**Why:**
- Live-verified against the running dev API (docker compose postgres + already-running dotnet instance), same rigor as Phase 1/2: blank/whitespace/null `Name` on `Minion` itself (400/400/400, the first two via the hand-rolled check); blank `Name` on all four unfixed sub-resource create endpoints (200, silently persists `""`) and already-fixed custom-move endpoint (400, correctly rejects both blank and whitespace); 300-char `Name` on `Minion` and `MinionAttack` (unhandled 500 on both); negative `HarmCapacity` (201, persists -5); FK existence for both `MonsterId` (route param, 404 clean on bad/empty/nonexistent) and `MinionTypeId` (payload field, 400 clean on bad/empty/nonexistent) — none 500. All test data created and deleted during verification, confirmed gone via follow-up 404.
- Cross-checked Luigi's relayed claim about `minionTypeId` directly against `minion-form.ts`/`minion-form.spec.ts` rather than taking it on his word — confirmed exactly as described.
- Re-confirmed (not assumed) that the wizard's minion-side harm fields (`minionForm.harmCapacity`, `minionAttackForm.harm`, `minionArmorForm.harmSoak`) are still missing `Validators.required`, a gap Luigi already found and explicitly deferred during the Monster-phase wizard follow-up — flagged as a genuinely open bundling question rather than assumed either way, since the wizard's store is normally outside this initiative's per-domain scope.
