### 2026-08-03: Theming Phase 7 — Sweep, Palette Swap-In, and a Real Latent Bug Found by It

**By:** Luigi (Frontend Developer)

**What:** Final content phase of `docs/theming/theming-plan.md`. Part 1 swept the whole app for literal Tailwind color classes, arbitrary hex/rgb bindings, and dead CSS in every component `.scss` (per Yoshi's mid-project addition). Part 2 replaced `styles.css`'s `.dark {}` placeholder with Rosalina's real dark values from `dark-theme-palette.md`'s Token Value Table. Phase 8 (the FOUC inline script) is intentionally out of scope for this task.

**Biggest finding — not from the literal-class grep, from actually toggling `.dark` with real values:** 12 top-level page components (`monsters-list`, `minions-list`, `locations-list`, `bystanders-list`, `mysteries-list`, `monster-detail`, `minion-detail`, `location-detail`, `bystander-detail`, `mystery-detail`, `search-results`, `data-admin`) open with a bare `<section>` wrapper carrying no `text-primary` class. Every unclassed heading/paragraph on these pages was inheriting the browser's UA-default black `color`, never `--color-text-primary`. This was 100% invisible through Phases 0–6 because black is visually indistinguishable from `--color-text-primary`'s light value (`slate-950`) — it only becomes a real defect (black text on a near-black `slate-950` page) the instant real dark values land, which is exactly what Phase 7 does. `dashboard.html`/`settings.html` never had this bug (both explicitly carry `class="text-primary"` on their root `<section>` since they were written); the wizard doesn't have it either, because Phase 6 classed every text node individually rather than relying on inheritance. Fixed by adding `text-primary` to the same 12 root wrappers, matching the dashboard/settings convention already established. Confirmed via `getComputedStyle` before/after (`rgb(0,0,0)` → `oklch(0.984 0.003 247.858)`, i.e. `slate-50`) and a full two-theme visual pass.

**Why this belongs in Phase 7's history, not a separate bug ticket:** it's the direct, textbook shape of the risk Phase 7's own Goal text calls out — "budget a full visual pass across every page in both themes... since it's the first time the *real* dark palette... is visible anywhere." A grep-only sweep (Part 1) would never have found this, since there's no literal color class to grep for — the bug is an *absence* of a class. Recommend this stays a standing verification step for any future theme's rollout: after any palette swap-in, re-check every page's actual computed text/background colors, not just re-grep for literal classes.

**Other sweep findings, fixed:**
1. **12 identical `<p class="text-red-800">{{ errorMessage() }}</p>` error banners** (flagged and deferred since my own Phase 3 report) — all repointed to `text-danger`.
2. **`minion-detail.html`'s sub-resource cards** — explicitly deferred in Phase 3 (out of Detail-Form-Pattern scope at the time): `bg-white border-slate-200`→`bg-surface border-default`, `border-[#edf1f8]`→`border-default`, `text-gray-500`→`text-muted`, and the inline weapon-tag chip literal (`bg-indigo-50 border-indigo-200 text-indigo-700`)→`bg-weapon-chip border-weapon-chip-line text-on-weapon-chip` (converges onto the same tokens `monster-detail.html`/`weapon-tag-select` already use).
3. **`search-results.scss`'s `mark` highlight rule** (flagged since Phase 4) — `@apply bg-indigo-100 text-indigo-900` had no dedicated Catalogue token to move onto. Repointed to `bg-accent-subtle text-accent`: a translucent low-emphasis accent wash that stays visible over any dark-mode surface, versus `weapon-chip`'s flat near-black dark fill which would barely read as a highlight. `@reference` changed to `#styles.css` first, negative control re-run (reproduces the expected `Cannot apply unknown utility class` failure).
4. **`page-layout.html`'s mobile close-button icon** (`text-white`) → `text-sidebar`. A real miss, distinct from the MOTW-logo/"Soon"-badge `bg-white/20`+`text-white` instances, which are Rosalina's sanctioned, already-reviewed exception (Phase 1 open items #3, "translucent-white overlay lightens whatever's beneath it in both themes") and were deliberately left untouched.
5. **`search-results.ts`'s `badgeClasses()` fallback** (`?? 'bg-slate-100 text-slate-700'`, for an `entityType` outside the five known domains — practically unreachable since the type is backend-enum-constrained, but still a literal if it ever fired) → `bg-surface-hover text-primary`. No Catalogue token models a "generic/unrecognized" role; flagged as a role-stretch, same posture as Phase 5's admin `<th>`/skeleton-loader reuses.
6. **Dead-CSS sweep across all 10 component `.scss` files in the app: nothing found.** Every file already had zero dead selectors and the correct `@reference "#styles.css"` — Phases 1–6 left this cleaner than the brief assumed (the `monsters-list.scss` duplicate-rule precedent that motivated this sweep item was already fully cleaned up in Phase 4).

**Flagged, not fixed — out of scope for a theming sweep:** `monsters-list.html`'s delete button carries `action-btn action-btn--delete`, but `monsters-list.scss` only defines `.action-btn:hover:not(:disabled)` (neutral hover) with no `.action-btn--delete:hover:not(:disabled)` rule — so its hover is the generic neutral fill, not the red danger-tinted hover `minion-detail.scss`/`monster-detail.scss` give the equivalent button. Confirmed via `git log -p` this predates the Tailwind migration itself (the rule already didn't exist by the "phase 5: migrate all list pages to Tailwind CSS" commit) — not something this theming rollout introduced or broke, and not a color/dark-mode defect (the neutral hover works correctly in both themes, it's just not the intended red warning treatment). Left alone since adding new hover behavior is outside "sweep for stragglers" scope; flagging for whoever owns general UX consistency next.

**Palette swap-in:** single-file `styles.css` change exactly as Decision B promised — zero template risk. All 43 Token Catalogue entries confirmed present in both `:root` and `.dark` after the swap (the `@theme static` symmetry check). Contrast spot-checks used actual rendered pixels (canonicalized via the 1×1-canvas paint trick, since Chromium reports `oklch(...)` not `rgb(...)`), not hand-computed hex: minion `9.18:1`, bystander `8.08:1`, location `10.67:1` — all three of Rosalina's previously-unverified badge hues comfortably clear AA/AAA; monster (`8.42:1`) and mystery (`10.37:1`) cross-checked closely against her own hand-computed `~8.5:1`/`~10.4:1`, confirming the measurement methodology itself, not just the new numbers.
