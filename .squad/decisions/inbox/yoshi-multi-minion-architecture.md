### 2026-08-04: Multi-Minion Support — Architecture Plan
**By:** Yoshi (Architect)

**What:** Produced `docs/updates/multi-minion-support.md`, an architecture plan for attaching more than one minion to a monster, both in the mystery-create wizard and on monster-detail. Key calls:
- Wizard moves from a single `minionForm`/`editingMinionId` slot to `minionDrafts: signal<MinionDraft[]>`, where `MinionDraft` extends the `LocationDraft`/`BystanderDraft` `id: string | null` pattern with nested sub-resource collections + per-minion existing-ID baselines (minions have children, locations/bystanders don't — the shape isn't a direct copy). Editing is a single `editingDraftIndex: signal<number | null>` reusing the *existing* `minionForm`/4 sub-resource signals as "the active draft," with new `editMinionDraft`/`saveMinionDraftToList`/`removeMinionDraft` methods — stays inside the project's standing "signal arrays, not FormArrays" decision (`.squad/decisions.md`, 2026-07-21).
- `submitPhase1`'s minion branch generalizes the already-shipped Location/Bystander diff-upsert pattern (`idsToUnlink`/`backfillDraftIds`/`savedDraftIds`), substituting hard `delete()` for `unlinkFromMystery()` since minions are 1:N-owned, not M:N-shared.
- Monster-detail "Add Minion": recommended a lightweight inline stub-create form (4 fields) → `minionService.create()` → navigate to the already-complete `/monsters/:monsterId/minions/:id` detail page for sub-resources, rather than embedding a second full sub-resource-panel UI inline. "Remove Minion" added symmetrically.
- No shared component between the wizard's minion-form and monster-detail's add-minion form recommended — the two have fundamentally different submission models (phase-batched vs. immediate-per-action, both already established, competing conventions in this codebase) and this codebase doesn't otherwise extract shared form components for overlapping-but-not-identical domain fields even where overlap is much larger (monster/minion detail forms already duplicate ~90% of fields with no shared component).
- Item 4 (no in-place edit, "must delete+re-add") confirmed **solved as a side effect** of the `editingDraftIndex` mechanism above, not a separate phase — verified this claim rather than assuming it, since the task explicitly asked for that check.
- **Corrected a stale premise in the task brief**: Bug 2 (wizard duplicate-submission-on-revisit) is already fully fixed as of commit `e83eebb` (2026-08-04, current `HEAD`) — verified in the actual store code (`submitPhase0`'s `isEditMode()` guard is gone, `LocationDraft`/`BystanderDraft` already do true diff-upsert, minion-name conditional-required signals already exist). The brief said "not yet fixed"; `docs/theming/found-bugs.md`'s status line is stale in the same way and should be corrected by whoever picks this doc up next (not done here — out of this task's scope). This meant "should Bug 2 be bundled or deferred" wasn't an open question to answer — it's a solved prerequisite the multi-minion diff design builds directly on.
- Found a real, previously undocumented backend gap: no `DELETE /api/minions/{id}` endpoint exists anywhere in the stack (controller/service/repository all grepped, zero hits) — required for both the wizard (removing a previously-saved minion) and monster-detail (new "Remove Minion" action). Scoped as its own backend sub-phase (MM-1), mirrors `MonstersController`'s existing `DELETE api/monsters/{id}` shape exactly; no new migration needed since minion sub-resource tables are already `ON DELETE CASCADE` on `minion_id`.

**Why:** Reuses two already-proven patterns in this exact file (signal-array sub-items, ID-diff upsert) rather than inventing new state-management machinery for multiplicity; keeps the "batched wizard submission" vs. "immediate per-action mutation" split that's already architecturally load-bearing in this codebase (2026-07-21 phase-submission decision) intact rather than blurring it with a shared component; avoids duplicating `minion-detail.ts`'s already-complete, already-tested sub-resource CRUD a third time in the codebase.

**Docs:** `docs/updates/multi-minion-support.md`.

**The state model survived contact with the design, but not for free — three additions:**

- **`editingDraftIndex` cannot express Rosalina's collapsed composer.** "Roster non-empty, nothing being edited" and "roster non-empty, user clicked `+ Add Another Minion`" both have `editingDraftIndex() === null` and a non-empty roster. Added `composerOpen: signal<boolean>` with the invariant `editingDraftIndex() !== null ⇒ composerOpen()`. Rejected a discriminated-union state signal: more precise, but there is no tagged-union state anywhere in this store and every read site would need a `switch`. Also recorded that `composerOpen` **cannot** be derived from "composer is non-empty" — it would collapse the panel the user just opened.
- **My decision #10 went too far, and Rosalina's correction of it doesn't go far enough.** She says `minionSectionStarted()` survives "repurposed"; it must be **widened**, and the two holes are real silent-data-loss paths. (a) It excludes Name *by design* (see its own doc comment), so a name-only composer reports not-started; today that's caught late by `submitPhase1`'s `:1035` type guard, which **disappears** under the draft-list model, so the typed name would vanish with no error. (b) It reads only the form, never the four sub-resource signals — so a composer with two attacks and no name, which is literally the case her own §1.4 row 3 says must block, reports not-started today. Specified `composerDirty()` (widened to include Name + the four collections) and `composerValid()` (name && type), and kept the `phase === 1 && step === 1` branch of `validateCurrentStep()` with new semantics.
- **Auto-commit-on-Next needs one primitive and three call sites, not one.** Her §1.3 row 3 applies the same rule when starting a new draft while editing, so `commitComposerIfValid(): boolean` is called from `next()`, `editMinionDraft()` and `startNewMinionDraft()`, each aborting on `false`. Specified that it must run in `next()` synchronously *before* `submitCurrentPhase()`, not inside `submitPhase1`'s rxjs pipe — burying a state mutation inside a re-enterable async chain is the exact shape of the Bug 2 defect class this file just finished eliminating. **Accepted her rejection of my 2026-08-04 discard-confirmation modal** and withdrew it explicitly: commit-if-valid / block-if-not covers the same risk without a modal that fires on the step's most common interaction.

**Two hazards of the model that neither document stated, now written down as decision #12:** removing a roster card **invalidates `editingDraftIndex`** (clear when `=== i`, decrement when `> i`, or the next save silently overwrites a bystanding draft — the single most likely bug in MM-2); and the confirm modal's `[items]` must be read from `minionDrafts()[i]`, **never** from the live composer signals, which belong to a different minion whenever the user removes a card they aren't editing. Positional identity is only safe because Skyler declined reordering — noted with a client-side `key` as the escape hatch if that ever changes.

**Skyler's #4 (always confirm in the wizard) and #6 (no Remove Minion on monster-detail) do not collide** — different surfaces. Stated explicitly in decisions #7 and #12 so an implementer can't read one as cancelling the other.

**Dossier leak — audited the whole file rather than the one reported line.** `mystery-create-dossier.html:165` reads raw `store.minionWeaknesses()` inside a `minionPreview()` block; harmless today only because `minionPreview().weaknesses` *is* that signal (`:461`). Checked all 50+ `store.*()` reads in the file: the monster block (`:56-109`) is `monsterPreview()` at every one of its 15 reads, so **the mismatch does not recur there**; locations/bystanders read the draft arrays directly, which is correct by construction (no `*Preview()` computed exists for them). **Line 165 is the only occurrence.** Scoped as **MM-0** — first, alone, ahead of everything — because the fix is a *provable no-op today* and therefore riskless in isolation, whereas folded into MM-3 it is one indistinguishable line inside a template rewrite.
