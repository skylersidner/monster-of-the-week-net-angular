# Mystery Required-Field Validation — Backend Implementation

**What:**
- `UpsertMysteryRequest` (`Contracts/ApiContracts.cs`): added `[param: Required]` to `Name` and `[param: MaxLength(500)]` to `Concept`, matching `CreateAdventureTypeRequest`'s existing `[param: Required, MinLength(N)]` precedent in the same file.
- `IMysteryRepository`/`MysteryRepository`: added `AdventureTypeExistsAsync(Guid id, CancellationToken ct)`, mirroring `MonsterRepository.MonsterTypeExistsAsync`'s exact one-line `AnyAsync` shape.
- `IMysteryService.CreateAsync`/`UpdateAsync`: widened return type from raw `MysteryDetailResponse`/`MysteryDetailResponse?` to `ServiceResult<MysteryDetailResponse>`. Both methods now check `AdventureTypeExistsAsync` before writing and return `ServiceResult<MysteryDetailResponse>.Validation(...)` on failure — copied `MonsterService.CreateAsync`'s exact pattern. `UpdateAsync` also now returns `ServiceResult<...>.NotFound(...)` instead of `null` when the mystery doesn't exist (was previously a bare `null?` return the controller checked directly).
- `MysteriesController`: added the private `ToActionResult<T>(ServiceResult<T>)`/`ToErrorResult(ServiceError)` pair (own copy, not shared — matches `MonstersController`'s/`MinionsController`'s existing per-controller convention). `Create`/`Update` now route through it. Also refactored `UpsertCountdown` (pre-existing endpoint) to use the new `ToActionResult` helper instead of its own inline `switch` — same behavior, removes now-duplicated logic in the same file.
- New `MysteryServiceTests.cs` (didn't exist) with a stateful `FakeMysteryRepository` (backing `List<Mystery>`, mirrors `BystanderServiceTests`/`LocationServiceTests` conventions). Covers: `CreateAsync`/`UpdateAsync` return `Validation` when `AdventureTypeId` doesn't exist, `UpdateAsync` returns `NotFound` when the mystery doesn't exist, valid create/update still succeed and are retrievable via `GetByIdAsync`/`GetAllAsync`. Also added reflection-based tests asserting the `[Required]`/`[MaxLength(500)]` attributes are actually present on `UpsertMysteryRequest`'s constructor parameters (see Judgment calls below for why reflection, not `Validator.TryValidateObject`).

**Why:** Implements the locked, unconditional scope from `docs/updates/mystery-required-fields-validation.md`'s "Revision — Skyler's 4 Answers Resolved (2026-08-06)" section and `.squad/decisions/inbox/yoshi-mystery-required-fields-validation.md`. Closes two live-verified gaps: (1) blank/whitespace `Name` silently persisted as `""` (no `[Required]` existed), (2) a bad `AdventureTypeId` produced an unhandled 500 instead of a clean 400 (no FK existence check, `MysteryService.CreateAsync`/`UpdateAsync` didn't use `ServiceResult<T>` yet, unlike the same file's own `UpsertCountdownAsync`).

**Judgment calls / deviations:**
- `[param: Required]`/`[param: MaxLength]` on a record's primary-constructor parameter attach to the constructor `ParameterInfo`, not the generated property — by design, matching the codebase's own existing `CreateAdventureTypeRequest`/`CreateTypeRefRequest` precedent (explicit `param:` target). This means `System.ComponentModel.DataAnnotations.Validator.TryValidateObject` (plain property reflection) would **not** see these attributes and can't be used to unit-test them — ASP.NET Core's actual model-binding/validation pipeline for records does see constructor-parameter attributes (already verified live by Yoshi against `CreateAdventureTypeRequest`; not re-verified live here, out of scope for a backend-implementation pass with no integration-test harness in this repo). Wrote the attribute-presence tests against `ConstructorInfo.GetParameters()[...].GetCustomAttribute<T>()` instead, and additionally called the real `RequiredAttribute.IsValid(...)` on null/empty/whitespace values to confirm the actual attribute instance (not a re-implementation) rejects all three — this is the most precise thing a pure unit test can assert without standing up a `WebApplicationFactory`, which doesn't exist anywhere in this test project today and wasn't in scope to introduce.
- `MysteryService.UpdateAsync` used to return a bare `null` (not throw, not a `ServiceResult`) when the mystery id didn't exist; the controller checked `updated is null ? NotFound() : Ok(updated)` directly. Since the return type had to widen to `ServiceResult<T>` anyway for the `AdventureTypeId` check, folded the not-found case into `ServiceResult<T>.NotFound(...)` too rather than leaving a hybrid `ServiceResult<T>?` — this is a strict behavioral no-op (still a 404, same status code, controller logic just routes through `ToActionResult` now) but is a shape change from the doc's literal wording ("widen return type... to ServiceResult<MysteryDetailResponse>" — didn't explicitly call out the not-found path). Flagging since it's the one place I inferred rather than copied verbatim.
- Refactored `MysteriesController.UpsertCountdown` (pre-existing, not touched by the doc's scope) to use the new `ToActionResult` helper instead of its own inline `ServiceErrorType` switch. Not required by the doc, but the switch was now duplicated three times in one file the moment `ToErrorResult` was added for `Create`/`Update` — small in-scope cleanup, zero behavior change, easy to revert if unwanted.
- Killed a stale `dotnet run` dev-server process (PID holding `MonsterOfTheWeek.Api.exe` locked, blocking `dotnet build`) rather than redirecting build output to a scratch dir as a prior entry in this history did — this was very likely the same dev instance Yoshi's doc mentions using for live verification (`http://localhost:5225`), already idle/done with its job per the doc's "Status: Decisions locked" framing. Worth a lighter touch (output-redirect workaround) next time if a dev server might still be in active use.
