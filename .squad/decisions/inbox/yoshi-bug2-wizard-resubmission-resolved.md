### 2026-08-04: Mystery Create Wizard — Bug 2 Fix, Full Scope Resolved (Locations/Bystanders True Upsert + Minion Name Required)
**By:** Yoshi (Architect)

**What:** Skyler resolved all three open questions from the initial Bug 2 review (`yoshi-bug2-wizard-phase-resubmission.md`). This entry supersedes that file's "open questions" section with concrete design; the phase-0/1 root cause and fix described there stands unchanged.

1. **Locations/bystanders get a true per-row upsert**, not "unlink+recreate with orphan accumulation accepted." `LocationDraft`/`BystanderDraft` gain `id: string | null`. `submitPhase2`/`submitPhase3` diff the current draft array against a linked-IDs baseline (`existingLocationIds`/`existingBystanderIds`, kept — still needed as the *pre-submit* baseline, since removed drafts vanish from the array and have no other trace): PUT-update drafts with an id (via `LocationService.update`/`BystanderService.update`, both already exist), POST-create drafts with `id: null` (add `create(mysteryId, request)` to `LocationService`/`BystanderService`, mirroring `MonsterService.create(mysteryId, request)` — currently missing, the store bypasses the service and calls `apiService.post` directly), unlink baseline IDs no longer present in the draft array (add `unlinkFromMystery(mysteryId, id)` to both services, wrapping the existing `DELETE /api/mysteries/{mysteryId}/locations/{id}` endpoint the store already calls raw). Recommend also adding `getByMystery(mysteryId)` to both services to retire the last raw `apiService.get` calls in `loadEditData()` — full parity with `MonsterService`, no more raw `apiService` calls for locations/bystanders anywhere in the store. This uniformly replaces the `isEditMode()`-conditional path for locations/bystanders entirely: the same diff logic now handles both "editing an existing mystery" and "revisiting a completed phase in a new-mystery session" with one code path.
2. **Minion Name becomes conditionally required**: required only once the minion section has been "started" (any of Description/Type/Harm-Capacity-changed-from-default is non-empty/non-default), matching the fact that `submitPhase1()` already uses blank-Name as the sole "is a minion being added at all" signal — an entirely untouched minion section stays fully skippable. Implemented as derived `computed()` signals in the store (`minionSectionStarted`, `minionNameRequired`, `minionNameMissing`), not a static `Validators.required` on the FormControl (which can't express "required only if a sibling field has a value") and not an imperative cross-field FormGroup validator (available in Angular but inconsistent with this file's existing idiom — `phaseStepComplete` already derives exactly this shape of cross-field logic via `computed()` off `toSignal`-bridged form values). `validateCurrentStep()` gains a `phase === 1 && step === 1` branch (currently has none) that blocks `next()` when `minionNameMissing()`. Template (`mystery-create-monster-phase.html`, currentStep===1 block, minion Name field ~line 152) gets a conditional `*` and inline error, following Bug 1's established visual pattern exactly, gated on the new signals rather than `form.control.invalid`.
   - **Backend propagation**: `Minion.Name` (`DomainEntities.cs`) is already `required string Name` — non-nullable at the C#/EF Core/DB-column level, identical to every sibling entity (Monster/Location/Bystander). **No migration needed** — there was never a nullable-column gap. The actual gap is that nothing in the stack rejects an empty *string* (as opposed to null) — and that gap is universal across the whole backend (confirmed: zero `IsNullOrWhiteSpace`/name-blankness checks exist in any `*Service.cs` for any entity, required-ness today is enforced only by frontend Angular validators). Adding a blank-Name rejection is being scoped to `MinionService.CreateAsync`/`UpdateAsync` only (a 2-3 line `string.IsNullOrWhiteSpace(request.Name)` guard returning `ServiceResult<T>.Validation(...)`, mirroring the adjacent `MinionTypeId` existence check already in the same methods) — this closes the "someone calls the API directly with a blank Name" loophole for Minion specifically without inventing new backend validation infrastructure or auditing/expanding every sibling entity, per Skyler's explicit "point fix for Name only" scoping. The identical latent gap on Monster/Location/Bystander Name is real but explicitly out of scope here, flagged so it isn't rediscovered as new.
3. **Mid-wizard persistence gap: no action**, per Skyler's explicit call. Not part of this fix.

**Why:** Both expansions follow the same underlying principle as the original phase-0/1 fix: reuse the ID-presence-driven upsert pattern already established in this file (`editingMonsterId`/`submitPhase0`'s branch) rather than inventing a second mechanism, and keep validation logic in the same `computed()`-signal idiom this file already uses for every other cross-field/derived rule (`phaseStepComplete`, `monsterPreview`, etc.) instead of introducing Angular's imperative form-validator machinery for the first time in this file.
