# Monster Required-Field Validation — Backend Implementation

**What:**
- `Contracts/ApiContracts.cs`: added `[param: Required, MaxLength(255)]` to `Name` on all six records (`UpsertMonsterRequest`, `UpsertMonsterAttackRequest`, `UpsertMonsterPowerRequest`, `UpsertMonsterArmorRequest`, `UpsertMonsterWeaknessRequest`, `UpsertCustomMoveRequest`), matching `UpsertMysteryRequest`'s Phase 1 precedent and `CreateAdventureTypeRequest`'s original one in the same file. Added `[param: Range(0, int.MaxValue)]` to `UpsertMonsterRequest.HarmCapacity`, `UpsertMonsterAttackRequest.Harm`, `UpsertMonsterArmorRequest.HarmSoak`.
- No `MonsterService.cs`/`MonsterRepository.cs`/`MonstersController.cs` changes — re-confirmed by reading `MonsterService.cs` in full before touching anything that all three `CreateAsync` overloads/`UpdateAsync` already check `MonsterTypeExistsAsync`/`MonsterArchetypeExistsAsync` and return `ServiceResult<T>.Validation(...)` before any write, and every sub-resource create method already checks only `MonsterExistsAsync` (its one real FK). Matches Yoshi's live-verified claim exactly — the "audit found nothing to fix" outcome, not skipped verification.
- Extended `MonsterServiceTests.cs` (pre-existing file) with 21 new reflection-based tests: `NameRequestTypes`/`HarmFields` `[MemberData]` sources driving `[Theory]` tests across all six `Name`-bearing records and all three harm-related `int` fields — `RequiredAttribute.IsValid(...)` rejects `null`/`""`/`"   "` and accepts a real value; `MaxLengthAttribute.Length == 255` and `IsValid(...)` accepts a 255-char string but rejects 256; `RangeAttribute.IsValid(...)` rejects `-1` and accepts `0`/`int.MaxValue`. No new service-layer behavior tests were added (there's no service-layer guard to test — the fix is purely DataAnnotations, evaluated by `[ApiController]`'s model-binding pipeline before the service is ever called), following the exact same reasoning `MysteryServiceTests.cs` documented for why reflection against `ParameterInfo`, not `Validator.TryValidateObject` or a live service call, is the correct/only thing a plain xUnit test in this repo can assert without a `WebApplicationFactory` (still doesn't exist here).

**Why:** Implements the locked, unconditional backend scope from `docs/updates/monster-required-fields-validation.md`'s "Revision — Skyler's 4 Answers Resolved (2026-08-06)" section and `.squad/decisions/inbox/yoshi-monster-required-fields-validation.md`. Closes two live-verified gaps, both confirmed by Yoshi against a running dev instance before this pass: (1) blank/whitespace `Name` silently persisted as `""` on all six create endpoints (Monster + 5 sub-resource types); (2) a 300-character `Name` produced an unhandled `500` (Postgres `data too long for column`) rather than a clean `400` — worse than Phase 1's `Concept` gap since it sits on a required field, across six fields instead of one. `[Range(0, int.MaxValue)]` closes a third, previously-harmless-but-real gap: client-side `Validators.min(0)` exists at every call site with no server-side backstop.

**Judgment calls / deviations:**
- Generalized Phase 1's single-type `GetParameterAttribute<TAttribute>(parameterName)` helper (which hardcoded `typeof(UpsertMysteryRequest)`) into a two-parameter `GetParameterAttribute<TAttribute>(Type requestType, string parameterName)`, driven by `[MemberData]` `Type`-returning theories, rather than writing six near-duplicate copy-pasted test methods. This is a shape change from Phase 1's literal pattern (which the doc's test-scope note pointed to as "mirror it"), but the underlying technique — `ConstructorInfo.GetParameters()[...].GetCustomAttribute<T>()`, not `PropertyInfo`/`Validator.TryValidateObject` — is identical; only the parameterization changed, driven by six records needing the same three assertions instead of one record needing two. Flagging since it's an interpretation of "mirror the technique" rather than "copy the method signature."
- Did not add any test that calls `MonsterService.CreateAsync`/`CreateAttackAsync`/etc. with a blank `Name` and asserts a `Validation` result — unlike `MinionService`'s prior ad hoc `IsNullOrWhiteSpace` guard (a different, earlier fix predating this initiative's DataAnnotations pattern), `MonsterService` has and needs no such guard; blank-name rejection happens entirely in ASP.NET's model-binding pipeline before the controller action (and therefore the service) is ever invoked. A test that called the service directly with a blank name would incorrectly *succeed* (the fake repository has no validation of its own) and would misrepresent where the real fix lives — so it was deliberately omitted rather than added for coverage's sake.
- Confirmed `MonsterService.cs`'s FK-existence checks read exactly as Yoshi's doc describes (all three `CreateAsync`/`UpdateAsync` methods check both FKs before any write) by reading the full file, not just trusting the doc — no discrepancy found, no changes made.
