**Why / judgment calls:**

1. **`startWith` + `ngOnInit`, not a constructor field initializer or a cross-field `Validators` composed at the FormGroup level.** The doc's suggested approaches were both offered as options ("via a `valueChanges` subscription or a form-level cross-field validator"). Picked `valueChanges` because it's the pattern this codebase already uses for reacting to one control's changes and mutating another (`data-admin.ts:50`, structurally identical: subscribe in `ngOnInit`, `takeUntilDestroyed(this.destroyRef)`). `startWith(isSpecial.value)` makes the initial call-site emit synchronously during `ngOnInit`, so "including on initial form setup" (the doc's explicit ask) is satisfied without a separate one-off call that could drift from the subscription's own logic.
2. **`{ emitEvent: false }` on `updateValueAndValidity`.** Without it, revalidating `specialDescription` would re-emit its own `valueChanges`, which nothing here listens to, but is needless noise and a minor footgun for any future subscriber. `setValidators`/`updateValueAndValidity` don't touch the *value*, only validity/error state, so this doesn't risk masking a real value change.
3. **Test assertions for the conditional-required rule check `control.valid`/`control.validator`, not `monsterForm.invalid` end-to-end**, mirroring `monster-form.spec.ts`'s own style of asserting on individual controls (`controls.name.touched`, `controls.monsterArchetypeId.touched`) rather than only the form-level `.invalid` flag. Directly proves the validator toggles on and back off, not just that submission is blocked once.
4. **Asterisk-indicator specs added despite no prior precedent** (grepped `mysteries/**/*.spec.ts` for `text-danger`, found zero existing assertions of this kind anywhere in the repo). Added lightweight DOM-presence checks anyway — the doc explicitly asked for this coverage "if the existing spec style supports it," and simple `label.querySelector('span.text-danger')` assertions fit this codebase's existing `fixture.nativeElement.querySelector(...)` idiom (used throughout `monster-create.spec.ts`/`monster-detail.spec.ts` for testing submit-button state, form presence, etc.) with no new tooling.
5. **No `.scss` changes.** All 9 label/asterisk edits and both conditional-validator wirings are pure Tailwind-utility-class/template/TS changes; none of the 4 files touched (`monster-form.html`, `monster-create.html`/`.ts`, `monster-detail.html`/`.ts`) have or need a stylesheet edit for this pass.

**Follow-up fix (2026-08-06):** Skyler reported the asterisks wrapping onto their own line on the Monster form (edit and create both — confirmed it reproduces in both, not edit-specific despite how it was reported, since `monster-detail.ts` and `monster-create.ts`/`monster-create.html` all share the exact same broken markup shape).

**Root cause:** every one of the 10 asterisk-bearing `<label>` elements this pass touched uses `class="grid font-medium gap-1"` (CSS Grid, no explicit `grid-template-columns`, so `grid-auto-flow: row` with a single implicit column). Per the CSS Grid spec, *every* in-flow child of a grid container becomes its own grid item — including the anonymous box wrapping a bare text run. My original markup put `<span class="text-danger">*</span>` as a text-level sibling directly after the label's own text (`Name <span class="text-danger">*</span>`), which is exactly what `mystery-create-mystery-phase.html` does too — but that label is `display: block`, not `grid`, so its text and span stay in one inline formatting context. On the grid-display label, the "Name" text run and the asterisk `<span>` became two *separate* grid items, each auto-placed onto its own implicit row (with the `<input>`/`<textarea>`/`<app-custom-select>` becoming a third row) — the label text, the asterisk, and the input all stacked vertically instead of the label text and asterisk sharing a row above the input.

**Fix:** nested the label text and the asterisk `<span>` together inside one wrapping `<span>` so they form a single grid item (one row), leaving the input/textarea/custom-select as the grid's second row — e.g. `<span>Name <span class="text-danger">*</span></span>` — rather than reaching for a layout override (no `inline-block`/`display` hack; Mystery's label isn't actually `display: grid` at all, so there was no equivalent structure to copy for the input-stacking part — this fix keeps the intentional label-above-input grid stacking while giving the label text+asterisk a shared item). Applied to all 10 locations across the 3 files: 4 in `monster-form.html` (Name, Harm Capacity, Monster Type, Monster Archetype), 3 in `monster-create.html` (Name, Harm, Harm Soak, plus the conditional `@if`-gated Special Description asterisk), 3 equivalent in `monster-detail.html`. Existing specs (`label.querySelector('span.text-danger')`, `label.textContent.trim().startsWith(...)`) were unaffected by the added wrapper `<span>` — both are descendant/text-content queries, not shape-sensitive — so no spec changes were needed.
