### 2026-08-02: Theming — `@reference` Directive Is the Documented Mechanism; Recommend Subpath Import to Kill the Relative-Path Fragility
**By:** Yoshi (Architect)
**Requested by:** Skyler Sidner — independent verification of Luigi's `@reference "../../../styles.css"` fix in `header-search.scss`, formed from primary sources before reading Luigi's own investigation.

**What:**

1. **`@reference` pointed at the app's own stylesheet is exactly the documented, correct mechanism — not a workaround.** Tailwind's `/docs/functions-and-directives` page describes `@reference` precisely for "component-scoped or isolated CSS files" (its own examples: Vue `<style>` blocks, Svelte `<style>` blocks, CSS Modules) that use `@apply`/`@variant` but don't get the project's compiled CSS output. It gives the identical two-case contrast we're facing: `@reference "tailwindcss"` for "default theme, no customizations" vs. `@reference "../../app.css"` (a relative path to *your own* stylesheet) when you have custom theme tokens. `bg-accent` is exactly the second case. Luigi's fix matches the docs' own canonical example almost verbatim.

2. **Angular's silence is not a red flag — it's scope, not incompatibility.** Both `angular.dev/guide/tailwind` and `tailwindcss.com/docs/installation/framework-guides/angular` are bare 5-6-step global-setup walkthroughs (install packages, configure PostCSS, `@import "tailwindcss"` in one global file, `ng serve`, use classes on a `<h1>`). Neither mentions component-scoped styles, `@apply`, `@reference`, or theme customization *at all* — for any framework, not just Angular. That's consistent with Skyler's framing: Tailwind deliberately keeps this guidance framework-agnostic and centralized on the functions-and-directives page, because the underlying problem is identical wherever a component's stylesheet is compiled as its own isolated PostCSS context — Vue SFC `<style>`, Svelte `<style>`, CSS Modules, and Angular's `ViewEncapsulation.Emulated` (default) component `.scss` all share that shape. There is no genuine incompatibility in Angular's build model here: the Angular CLI's esbuild/PostCSS pipeline treats each component stylesheet as its own compilation unit the same way Vue's compiler does, which is exactly the scenario `@reference` was built for. If anything, the omission across *both* Angular docs (not just Angular's own) is evidence the gap is "advanced theming isn't in scope for a getting-started guide," not "Angular can't do this."

3. **The fragility complaint has a real, documented fix — Node.js subpath imports.** The same `@reference` docs page explicitly offers this as the alternative to relative paths: a `package.json` `imports` field entry (`{"imports": {"#app.css": "./src/css/app.css"}}`), then `@reference "#app.css"` in every component file regardless of its folder depth. **Recommend adopting this now**, before Phases 2-6 propagate `@reference "../../../styles.css"` (and its per-depth variants) across the remaining nine `.scss` files. One `package.json` edit replaces N hand-computed relative paths with one path-independent alias — directly answers Skyler's "breaks if a file moves" concern, since a file's relative depth from `styles.css` becomes irrelevant. This has zero interaction with Angular's build (it's resolved by Tailwind's own PostCSS import resolution, not by TypeScript/webpack path mapping), so no `tsconfig.json` or Angular builder change is needed — confirmed no `imports` field exists yet in `src/web/monster-of-the-week-web/package.json`.

**Agreement/disagreement with Luigi:** `.squad/decisions/inbox/luigi-theming-reference-directive-evaluation.md` does not exist yet — Luigi has not filed his empirical-verification note for this specific question at the time of this writing. His earlier `luigi-theming-token-utility-mechanism.md` (§6) already independently reached the same mechanical conclusion (`@reference "tailwindcss"` only loads Tailwind's stock theme; must repoint to `styles.css`; verified end-to-end via a probe build) — we agree completely on the mechanism and on it being a hard, loud (not silent) build blocker. His note does not address the fragility/subpath-imports question at all (it only documents that the relative path works, not whether a cleaner alternative exists) — that's the gap this note fills.

**Why:** Confirms the current fix direction is correct and non-hacky per Tailwind's own docs, while giving Skyler a concrete way to eliminate the specific complaint (hardcoded, per-file, depth-dependent relative path) without abandoning `@reference` itself.

**Recommendation for the plan doc (not yet applied — investigation only, per task scope):** Add a `package.json` `imports` alias (e.g. `#styles.css` → `./src/styles.css`) as an infra step ahead of Phase 2, and change every `@reference` line (including `header-search.scss`, already shipped) to `@reference "#styles.css"`.
