### 2026-08-15: Auth Design — Luigi's Four Blocking Findings Adjudicated; New Decision #37 (Auth Failure Contract)
**By:** Yoshi (Architect)
**Requested by:** Skyler Sidner — adjudicate, fix what I agree with, report back anything I disagree with rather than substituting my own preference.

**What:**

1. **Three of four findings adopted in full; the fourth adopted in substance with one sub-recommendation declined and referred to the owner.** All four were the same shape: a requirement stated in one section of `architecture.md` with no wiring in the section or phase step that would implement it. Nothing in the design was wrong; four things were unreachable, and two of them fail silently.

2. **New decision #37 — auth-endpoint failure contract.** `/api/auth/*` failures return **`400` with `{ "code": … }`** (`invalid_credentials` | `email_not_confirmed`); **`401` is reserved API-wide for "no valid session"** and is emitted only by the cookie handler's `OnRedirectToLogin` override; **and** both `authErrorInterceptor` and `httpErrorInterceptor` skip requests under `/api/auth/` outright. Deliberately redundant — either defence alone is one refactor from silently un-shipping resolution #18, because with a `401` login failure the interceptor's `401` branch clears the session, bounces to `/login`, and swallows the body before the login component ever sees `email_not_confirmed`. `400` is also the zero-machinery option here: every controller already maps `ServiceErrorType.Validation` to `BadRequest(new { … })`, and `ServiceErrorType` (`Services/ServiceResults.cs`) has only `NotFound` and `Validation` in it — a `401` would need a third member plus a new arm in the switch. This is the only one of the four that changes the API contract, so it also touches Phase 1.

3. **Two additions of mine on top of Luigi's #37 proposal, both strictly in the same direction, both flagged rather than slipped in.** (a) `httpErrorInterceptor` needs the same `/api/auth/` exemption or the fix is half-done — the login page renders its inline "confirm your email address" message *and* a generic `Request failed (400) for POST /api/auth/login` toast underneath it; extract one shared predicate rather than copying an `includes()` into a second file. (b) Auth components must render the generic message for **any** failure without a recognised `code`, since the rate limiter (`429`/`503`), antiforgery (a `400` that isn't ours), and unhandled faults (`500`) all reach them too.

4. **Declined and referred to the owner: `authenticatedMatch` returning a `UrlTree` instead of `false`.** It would create the infinite redirect it is meant to prevent. Shell 1's path is `''`, which prefix-matches *every* URL, so its `canMatch` runs first even for `/login`; returning `false` is precisely what lets the router fall through to the sibling auth shell, and that fall-through **is** the two-shell pattern. A `UrlTree` cancels and redirects instead of trying siblings, so a logged-out `/login` would redirect to `/login`, re-enter the same guard, and loop until Angular's redirect limit throws. The empty-path child alone fully resolves the finding (`**` → `''` → `login`, two hops — the same two hops the signed-in app already takes to reach `/dashboard`).

**Why:** The owner asked to be consulted on any disagreement. Three findings needed no judgment — they are unambiguous gaps with one obvious fix each. #37 was genuinely mine to call as architect and Luigi's proposed answer is the right one, reinforced by a codebase fact he didn't cite (the two-member `ServiceErrorType`). The `UrlTree` sub-recommendation is the only place my analysis disagrees with his, and it is a defect rather than a preference difference, so it goes back to the owner with the trace rather than being silently overridden in either direction.
