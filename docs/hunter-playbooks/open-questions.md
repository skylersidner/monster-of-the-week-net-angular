10. **New, raised by Skyler alongside the Q9 answer — should the playbook-consumption process itself be packaged as a reusable Claude Code Skill, or handled another way (a written procedure in `phases.md`, a wrapper script, something else)?** The process: read the PDF section → extract standard-section fields → self-verify against the known-artifact checklist → call the `PlaybooksController` API to create the record. Skyler explicitly asked for a directional recommendation on the mechanism, not a locked-in answer.

    **Recommendation: package it as a Skill (`.claude/skills/<name>/SKILL.md` or equivalent), with the mechanism decided now but the Skill's actual content deliberately *not* authored in this planning pass — it should be written and iteratively refined as Phase 4 executes, not before.**

    Reasoning:
    - **Reusability is the strongest argument, and it's a close match to what Skills are for.** Phase 4 (3 playbooks, done carefully) and Phase 8 (25 more, same process at scale) are exactly "the same named, invokable procedure, run by many separate bounded agent tasks" — the granularity this doc already recommended (one bounded task per playbook, `architecture.md` Section 4) means each of those 28 tasks needs to reliably discover and load the *same* instructions. A Skill is this environment's built-in mechanism for exactly that; a `phases.md` paragraph requires whoever launches each task to remember to find and paste the right section, which degrades in reliability across 28 separate invocations in a way a discoverable, named Skill doesn't.
    - **Honest limitation, stated directly**: a Skill does not *mechanically enforce* the self-verification checklist any more than a well-written procedure document would — it's still packaged instructions the agent has to actually follow, not a hard gate. The real advantage over "process documentation in a different file" is operational, not enforcement: reliable discoverability/loading per invocation, and a clean separation between `phases.md` (why — architecture and rationale, changes rarely) and the Skill (how — the exact step-by-step runbook, checklist, and API-contract reference, expected to be revised as Phase 4 surfaces real inconsistencies). That separation already matches this repo's convention of keeping planning docs, process/decision records, and operational content in distinct places rather than one file doing all three jobs.
    - **A wrapper script alone isn't sufficient**, and isn't the right frame to compare against a Skill — it could mechanically enforce a *narrow* slice (e.g. validate the extracted JSON's shape before the API call fires), but the actual judgment work (does this read correctly, is this pick-count right, is this a layout artifact) is exactly the kind of interpretation this doc's own "rejected alternative: a fully automated PDF-to-JSON parser" (`architecture.md` Section 4) already concluded shouldn't be automated away. If a small script proves useful for the mechanical tail end (the API call itself, or payload validation), it belongs as one step *inside* the Skill's procedure, not as a replacement for it.
    - **Not premature to decide the mechanism now; premature to write the content now.** Locking in the Skill's exact checklist/steps before Phase 4 has run once would repeat the same mistake this doc already avoided elsewhere (over-specifying Phase 5's bespoke-section schema from only 3 samples) — Phase 4's whole stated purpose, per the Q9 resolution above, is to discover what the repeatable pattern actually is. The Skill should be the direct, concrete artifact that pass produces, authored/refined across the 3 pilot playbooks, then used unchanged (or lightly extended) for Phase 8's 25. Propagated to `phases.md` Phase 4 (Skill authored/refined as part of this phase's deliverable) and Phase 8 (inherits it).
