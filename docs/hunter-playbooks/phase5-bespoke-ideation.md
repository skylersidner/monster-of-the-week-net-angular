Two things this table surfaces that Skyler's message (framed around Crooked alone) didn't have visibility into yet:

- **Chosen's "Fate" bundles three pick-groups**, all sharing a shape none of Crooked's three concepts have: **label-only, no description text at all** — just short tag phrases like "True love" or "Impossible love," nothing to explain them. This is a genuinely different shape from Background (title+description), Heat (description+blank), and Underworld (description+nesting). (The table row above lists these as three raw findings from the text, which they are — how they get *modeled* is a separate question, decided in Section 3 below: one `BespokeSection` with the three groups as mandatory nested categories, not three independent sections.)
- **Divine's Mission is the simplest observed shape** — flat pick-1, description-only, no title, no blank, no nesting. Divine's own Advanced Improvements list separately includes "Change your mission... or (with the Keeper's agreement) a new mission of your creation." **Correction, 2026-08-26 (see Section 5, Q4)**: this was originally read here as implying `HunterBespokeSelection` needs to support a wholly custom value with no predefined option. That's wrong scoping — the "mission of your creation" escape hatch is an *Advanced Improvement* (a level-up-time change), not part of the initial Mission pick at character creation, and Advanced Improvement selection tracking is its own not-yet-designed mechanism, out of scope per the original brief's "Leveling Up" skip. It doesn't affect this pass's `HunterBespokeSelection` design at all.

So across just 3 playbooks, there are (at least) **five distinct structural shapes**: title+description (Background), description+blank (Heat), description+nesting (Underworld), label-only pick-N (Chosen's tag groups), and flat description-only pick-1 (Mission). Whatever model gets picked needs to explain all five without inventing a special case per playbook.

## 2. Candidate approaches

### Approach A — Fully generic EAV (attribute-value) model

A generic `BespokeRuleAttribute` catalog (rows like `MinSelect`, `MaxSelect`, `HasBlank`, `HasSubOptions`, ...) + a bridge table linking which attributes apply to which rule type + generically-typed value storage. This is Skyler's own idea, taken to its most literal/maximal form.

- **Generalizes to unseen shapes**: best of the three — a wholly new attribute never seen before just needs a new catalog row, no migration.
- **Query/maintenance pain**: worst of the three. "Give me every rule with MaxSelect = 1" requires pivoting generic value rows back into a shape-shaped answer; nothing stops nonsensical combinations (e.g. `HasBlank = true` on a rule type with zero options) since the schema itself can't express which attributes are even meaningful together.
- **Precedent**: a hard break from this codebase's only established pattern for this kind of problem — the `MonsterArchetype`/`WeaponTag`-style normalized lookup+children shape this whole doc has used since Phase 2 is real typed columns per concept, never generic key-value rows. Worth being direct about this: it's a bigger precedent break than even the "no JSON columns" one already flagged for Hunter's instance-side data, not a smaller one.

### Approach B — Small number of named, first-class shapes

A `BespokeSection` (the umbrella concept: Playbook FK, Title, Description) + a `BespokeOption` table, either (B1) one shared options table with nullable columns only certain shapes populate, or (B2) genuinely separate tables per shape (`SimpleChoiceOption`, `BlankFillOption`, `NestedChoiceOption`, ...).

- **Generalizes to unseen shapes**: worse than A — a genuinely new shape needs a real schema change (new nullable columns for B1, a whole new table pair for B2). Acceptable in this doc's own already-established style (Phase 2's model itself is explicitly provisional pending validation against more playbooks), but worth stating plainly rather than glossing over.
- **Query/maintenance**: best of the three — ordinary SQL, ordinary joins, no pivoting.
- **Precedent**: B1 specifically is not just "matches the general codebase pattern" — it's the *exact same shape* this doc already used and validated for Gear in Phase 2 (`PlaybookGearCategory` with nullable `PickCount`/`IsOptional`, `PlaybookGearOption` shared across every gear category's varied content). That's real, in-doc precedent, not just a codebase-wide analogy.

### Approach C — Bounded hybrid: generic attributes only where the attribute set is genuinely small and closed, typed columns everywhere else

Directly answers Skyler's own uncertainty about where the line goes. A small number of cross-cutting, universally-applicable constraints (min-select, max-select) get real typed columns on `BespokeSection`/`BespokeOption` directly (see Section 3) — not a generic attribute+bridge mechanism, because there are only ever two of them and every shape uses the same two. The *option content itself* (title, description, nesting) stays in typed columns, never generic rows, because that's exactly where Approach A's query/integrity pain would land hardest and where B1's Gear precedent already shows a working alternative.

**This is closer to a refined B1 than a true "hybrid of A and B"** — worth being honest that Skyler's original framing (generic attribute table for min/max/blank) is being partly declined here, not partly adopted; see Section 4 for the specific reasoning on each of the three attributes Skyler named.

### Honest comparison

| | Generalizes to shapes not yet seen | Query/maintenance cost | Schema complexity for 3 known playbooks' worth of evidence |
|---|---|---|---|
| A — full EAV | Best | Worst | Lowest upfront, highest ongoing (every query pays the EAV tax forever) |
| B2 — separate tables per shape | Worst | Good, but fragmented (no single query surface across shapes) | Moderate, grows per new shape |
| B1 / C — shared table, nullable columns, bounded typed attributes | Middle | Best | Low, and (per Section 3) may not even need a shape-kind discriminator |

## 3. Recommended direction (provisional — react to this, don't rubber-stamp it)

A refined B1/C: one `BespokeSection` per bespoke concept, one shared `BespokeOption` table, no rigid "shape kind" enum at all — the shape emerges from which nullable fields are populated, the same way Gear's shape already emerges from `PickCount`/`IsOptional` rather than a `GearShapeKind` column.

```
BespokeSection
  Id, PlaybookId, Title, Description, EffectText (nullable — see below, added 2026-08-27)
  MinSelect, MaxSelect (nullable ints — "how many of my direct options must/may be picked")

BespokeOption
  Id, SectionId
  ParentOptionId (nullable, self-referencing — null = top-level option, set = nested under another option)
  Title (nullable — populated for Background-shape options, null for Heat/Underworld/Mission/Fate-tag options)
  DescriptionText (nullable — populated for Background/Heat/Underworld/Mission, null for Fate's tag-only options)
  MinSelect, MaxSelect (nullable — same meaning as the Section-level pair, but scoped to *this option's own children*, only populated on options that have any)
```

**`BespokeSection.EffectText`, added 2026-08-27 — real schema change, not another one-off concatenation.** Skyler called this correctly: Chosen's Fate and Changeling's Unknown Heritage both needed their Section-level prose split across two source-positioned blocks, and resolving that by concatenating into one `Description` a second time (after Fate) was papering over a real, recurring shape rather than modeling it. Named `EffectText`, not "Description2" (Skyler's own placeholder, explicitly open to a better name) — reasoning below.

**What the two blocks actually represent, checked against both cases rather than assumed**: `Description`'s role stays "the intro/framing that tells you what you're about to pick and why" — read once, at character creation. The second block's role, across both cases, is **what having made these picks means going forward, during ongoing play** — not a second framing statement, not restated pick-instructions. Concretely:
- **Changeling's Unknown Heritage**: the trailing paragraph is concrete, mechanical, ongoing — "The Keeper may introduce obstacles... you may need to act under pressure... mark experience... you may ask 'What do I learn about myself?'" — real rules that apply throughout play because you have these tags.
- **Chosen's Fate**: much thinner, but the same role — "This is how your fate will unfold. It's okay to pick contradictory tags: that means your fate is pulling you both ways" is a thematic (not mechanically concrete) statement about what having made these particular picks *means* for how the character's story plays out. Weaker than Changeling's version, but the same kind of content — consequence/follow-through, not framing.

**It does *not* consistently map to "block 1 vs. block 2" by source position** — this is the part worth stating plainly, since a naive read could assume it does. Fate's second source-position block also contains the literal pick-instruction sentences ("How You Found Out (pick one):", "pick two heroic and two doom tags") — those are **not** `EffectText`, and don't go in `Description` either; they're dropped from free text entirely, because they're fully redundant with the already-modeled `MinSelect`/`MaxSelect` fields on Fate's three category options (matches how every other Section's `Description` already omits restating its own pick-count in prose — Heat's `Description` doesn't repeat "pick at least two" either). `EffectText` is a semantic field (what does this content *do*), not a positional one (whichever text happened to print second) — the split criterion is role, not position.

**New degenerate case, decided by Skyler 2026-08-27 — a `BespokeSection` with zero `BespokeOption` rows is valid and expected, not an edge case to design around.** The Covenant playbook's "Covenant" ability (a fixed, always-active mechanical grant — "you have a knack for keeping allies safe... they return... at the start of the next mystery") has no picks at all, and was flagged as a genuine model-fit question rather than folded into a nearby ruleset's `EffectText` (the alternative considered and declined) or forced into a standard-section field that doesn't exist for this shape. **Skyler's answer**: model it as its own `BespokeSection` — Title "Covenant", `Description` = the full paragraph, zero `BespokeOption` children.

**Representation of "no picks here," resolved**: `MinSelect`/`MaxSelect` = **both `null`**, not `0`/`0`. These fields already mean "how many of my direct options must/may be picked" — when there are zero direct options, the concept doesn't apply at all, the same reasoning already used for `BespokeOption.MinSelect`/`MaxSelect` being null on any option with no children. `0`/`0` would misleadingly read as "pick zero of some real option set," when the correct read is "there is no option set to pick from." A consuming UI/API can derive "this Section is fixed-text-only, render `Description` with no pick control" directly from an empty `BespokeOption` child collection — no separate flag needed.

**Direct, easy-to-overlook consequence for the instance side**: a zero-option `BespokeSection` needs **zero `HunterBespokeSelection` rows**, ever. There's nothing to select, so nothing to record — the Hunter simply has the ability by virtue of the Playbook itself (the same shape as a `Required` Move, which likewise needs no per-Hunter selection record since it's unconditionally true for every Hunter of that Playbook). Worth stating explicitly so a future implementer doesn't go looking for a selection row that was never meant to exist.

**New field, approved by Skyler 2026-08-27 — `BespokeSection.FreeTextLabel` (nullable string), for a single player-authored value with no fixed option list at all.** The Gumshoe's "Gumshoe Code" is a third distinct shape, different from both the zero-option case above and `BespokeJournal` below: "With the agreement of the Keeper, pick a one-sentence Code that your Gumshoe adheres to. Example Codes: Murders must be punished. Monsters must be destroyed. ..." The "Example Codes" are explicitly illustrative, not a discrete option pool — the player writes their own sentence freely; nothing here is selected *from* anything.

```
BespokeSection
  Id, PlaybookId, Title, Description, EffectText, FreeTextLabel (nullable — new, 2026-08-27)
  MinSelect, MaxSelect
```

When `FreeTextLabel` is populated (e.g. `"Your Code"`), the Section has **zero `BespokeOption` rows** (`MinSelect`/`MaxSelect` both `null`, same representation as Covenant's zero-option case) and the UI renders a single free-text input labeled by that value instead of a pick control. `Description` holds the framing sentence plus the example codes as flavor text, not options. `EffectText` holds the consequence paragraph (Gumshoe Code's forfeit/bonus rules), same role split as everywhere else.

**Two alternatives considered and declined, reasoning stated so this isn't re-litigated later:**
- **Reuse `{{blank}}` inside `Description`, no new field.** Rejected because it would overload the token with a second, different meaning. Every existing use of `{{blank}}` marks a blank *inside an otherwise-fixed option's own text* (Heat's "A police detective, `{{blank}}`, has made it a personal goal..." — a fixed sentence with one fill-in slot). Gumshoe Code has no fixed sentence at all — the *entire value* is freely authored. Stretching `{{blank}}` to also mean "this whole Section is a free-text capture" would make the token ambiguous to any future reader (or authoring agent) without checking context each time. A dedicated field keeps `{{blank}}`'s existing meaning intact.
- **Reuse `BespokeJournal`.** Rejected as over-engineered for this case. `BespokeJournal` exists for *growing, repeating* content — multiple entries, each with multiple labeled fields, added throughout play (Curse-Eater's Consumed Magic). Gumshoe Code is the opposite: exactly one value, set once at character creation, never added to again. Modeling it via the full Journal apparatus (a template table plus a per-entry instance table) would be real unused structure for a single string.

**Instance side**: no new Hunter-side table needed. A Hunter's answer for a `FreeTextLabel` Section can live directly on `HunterBespokeSelection` (reusing the existing `FreeformText` column, with `BespokeOptionId` null for this one specific case — the only case where that FK is expected to be null, since there's no option being selected, just a value being recorded against the Section itself) rather than inventing a parallel table. Flagged here as the leading approach, not yet locked — worth confirming once Gumshoe Code is actually being authored in Phase 4, since `HunterBespokeSelection.BespokeOptionId` was deliberately made required (Section 4 below) precisely because every case seen until now attached to a real option; this is the first exception to that rule and deserves a second look before it's final.

**New parallel structure, approved by Skyler 2026-08-27 — `BespokeJournal`, for growing player-authored entries, not fixed-at-creation picks.** Curse-Eater's "Consumed Magic (Power, Downside)" is structurally unlike every bespoke ruleset modeled so far: those are all fixed picks from a predefined option list at character creation (`HunterBespokeSelection` referencing a `BespokeOptionId`). This is open-ended — the Keeper and player invent new "Power"/"Downside" entries live, repeatedly, throughout play. No predefined content exists at the template level, only a **field shape** (this playbook's journal entries always have exactly a "Power" field and a "Downside" field). Forcing this into `BespokeOption` would be a category error — `BespokeOption` rows are things a Hunter selects *from*, and there's nothing to select from here.

```
BespokeJournal
  Id, PlaybookId, Title ("Consumed Magic"), Description, EffectText (nullable — same Description/EffectText role split as BespokeSection, reused rather than inventing a third field shape)

BespokeJournalField
  Id, JournalId, Label ("Power" / "Downside"), SortOrder
```

`BespokeJournalField` as a real normalized child table, not two hardcoded `Field1Label`/`Field2Label` columns on `BespokeJournal` — matches every other multi-item concept already in this schema (`BespokeOption`, `PlaybookMove`, `PlaybookGearOption`, ...) and generalizes to a future playbook needing 1, 3, or differently-labeled fields without a schema change, not just this one 2-field case.

**Instance side — the first Hunter-instance concept storing genuinely free-authored, growing content, not a fixed selection from a template**: mirrors the template shape directly, one row per entry and one row per field-value within an entry, since the entry's actual text has to live somewhere and there's no template row to point at instead:

```
HunterJournalEntry
  Id, HunterId, JournalId, SortOrder (or CreatedAt, for entry ordering)

HunterJournalEntryFieldValue
  Id, EntryId, JournalFieldId, Text
```

This is a real departure from every other Hunter-side concept designed so far (`HunterMove`/`HunterGearSelection`/`HunterBespokeSelection` are all FK-only references to predefined template rows) — flagged prominently as such when proposed, and confirmed by Skyler rather than assumed.

**New concept, approved by Skyler 2026-08-27 — repeatable `BespokeSection`s (`MinInstances`/`MaxInstances`), rejected from `BespokeJournal` on Skyler's explicit correction.** The Hex's "Rotes" was originally proposed here as a `BespokeJournal` case (growing, per-instance content, like Consumed Magic) — **Skyler rejected that framing directly**: "I would not treat this like a BespokeJournal at all... this has lots of structure with a few freeform entry fields. The only problem is that Section/Option lacks a way to propagate more of the same Section." The distinction that matters: `BespokeJournal` exists for content with **no real structure to speak of**, just a fixed set of free-text field *labels* (Power/Downside — nothing enumerable, nothing pickable). Rotes is the opposite — real structure (Requirements is a genuine pick-2-of-5 from a fixed, described option pool; Effect is 3 mandatory die-result-keyed slots) with the *only* new wrinkle being that a Hunter can end up with an open-ended, growing number of independent *instances* of that same structure. The fix belongs on `BespokeSection`, not a parallel Journal concept.

**Requirements and Effect need zero new option-level schema — verified directly against the source, not assumed to fit.** Requirements is a top-level `BespokeOption` ("Requirements", `MinSelect=2, MaxSelect=2`) with 5 children, each `Title` (short worksheet label) + `DescriptionText` (long explanatory form) populated — the exact same shape already validated for Dual Nature's Benefits. Effect is a top-level `BespokeOption` ("Effect", `MinSelect=3, MaxSelect=3` — all 3 mandatory, the same "pick all N of N" idiom as Fate's/Origin's categories) with 3 children, `Title` = the fixed die-result label ("10+"/"7-9"/"Miss"), `DescriptionText` = the literal token `"{{blank}}"` alone — a new *usage* of the existing `{{blank}}` mechanism (previously always embedded inside otherwise-fixed sentence text, or as one optional catch-all's entire content; here it's the entire content of a mandatory, non-catch-all option), but not a new field or schema change.

```
BespokeSection
  Id, PlaybookId, Title, Description, EffectText, FreeTextLabel
  MinSelect, MaxSelect
  MinInstances, MaxInstances (nullable ints, new 2026-08-27 — "how many times can this Section's whole option-tree be instantiated," same idiom as MinSelect/MaxSelect one level up)
```

Every Section processed before Rotes: both `null` — "the concept doesn't apply," exactly one instance, current behavior unchanged, no retroactive edits to any already-catalogued Section. Rotes: `MinInstances=0` (page 29, verbatim: "You start out knowing **up to** one rote" — 0 or 1 at creation, not a hard starting requirement), `MaxInstances=null` (unbounded — the worksheet's 8 printed blank Rote slots are a page-space artifact, not a confirmed rule; checked for an explicit cap and found none, only "You can learn more by taking improvements").

**Deliberately not a separate `IsRepeatable` boolean.** "Is this Section repeatable" is fully derivable from whether either bound is populated — the same "no redundant discriminator, shape emerges from populated fields" philosophy already governing this whole schema (no `ShapeKind` enum anywhere). A standalone boolean would also permit an inconsistent state (`IsRepeatable=true` with both bounds left null) that this design rules out by construction.

**Instance side — a new grouping table, not a bare instance-number column:**

```
HunterBespokeSectionInstance
  Id, HunterId, SectionId (FK), Name (nullable — per-instance free text, e.g. a Rote's own name), SortOrder

HunterBespokeSelection
  Id, HunterId, BespokeOptionId, FreeformText (nullable)
  SectionInstanceId (nullable FK -> HunterBespokeSectionInstance, new — populated only for repeatable Sections)
```

One `HunterBespokeSectionInstance` row per Rote a Hunter actually has; every `HunterBespokeSelection` row for that Rote's Requirements/Effect picks carries the same `SectionInstanceId`, which is what keeps Rote #1's picks from colliding with Rote #2's. For non-repeatable Sections, `SectionInstanceId` stays null and nothing changes. `SectionId` lives directly on the instance row rather than being derived transitively through its selections, so the UI can enumerate "how many Rotes does this Hunter have" directly and so a freshly-added, not-yet-filled-in Rote (zero selections yet) is a valid, representable state during creation/level-up, not an edge case to design around.

**One alternative considered and rejected**: a plain `InstanceNumber` int directly on `HunterBespokeSelection`, no separate table. Rejected because it has nowhere to hang the per-instance name (would need a second new mechanism anyway) and can't represent an in-progress Rote with zero selections yet. The dedicated table is the same "a growing per-Hunter thing needs its own identity-bearing row" shape already proven for `HunterJournalEntry` just above — applied here to Section-repetition instead of journal-entries, not a coequal fork worth presenting as a real second option.

**Rote's own free-text name lives on `HunterBespokeSectionInstance.Name`, not as a `BespokeOption`.** Confirmed per-repetition, per-Hunter data ("Give your new rote a name") — the template (`BespokeOption` rows for Requirements/Effect) is shared across every Rote of every Hunter of this Playbook; the name is not.

Net schema delta for this whole concept: two new nullable ints on `BespokeSection`, one new table, one new nullable FK on the existing `HunterBespokeSelection`. Zero changes to `BespokeOption`.

**New leaf shape, proposed by Skyler and evaluated on its merits 2026-08-29 — `BespokeOption.NumericMin`/`NumericMax` (nullable ints), for an option-conditional bounded numeric resource.** The Spooktacular's "The Show" ruleset has an option ("An Infernal Power") that grants a real, printed 3-box track ("Infernal Favour: b b b") functioning exactly like Luck — spend the boxes, restorable by an external party — but **only for the subset of Hunters who picked that specific option**, unlike Corruption/Relationship Status (both `PlaybookExtraTrack`, both universal to every Hunter of their playbook). The original question raised (`.squad/decisions/inbox/yoshi-hunter-playbooks-spooktacular-infernal-favour-track.md`) was whether to extend `PlaybookExtraTrack` with a nullable FK pointing at a triggering `BespokeOption`. **Skyler's counter-proposal, adopted instead**: don't extend `PlaybookExtraTrack` at all — add a new *kind of leaf option content* directly to `BespokeOption`, "as simple as a numeric input value with a minimum and maximum value." This makes the original conditionality question moot by construction: the numeric bounds live *on* the option that gates them, so there's no separate FK needed to express "only exists if this was picked" — the relationship is already direct.

```
BespokeOption
  Id, SectionId
  ParentOptionId (nullable, self-referencing)
  Title (nullable)
  DescriptionText (nullable)
  MinSelect, MaxSelect (nullable — "how many of my own children must/may be picked")
  NumericMin, NumericMax (nullable ints — new, 2026-08-29)
```

**Evaluated against the existing model before adopting, not rubber-stamped:**
- **Not the same "min/max" Skyler proposed generically back in Section 4** — worth stating explicitly since the naming echoes that earlier discussion and could otherwise read as reopening a declined idea. Section 4's min/max was about *pick counts* (`MinSelect`/`MaxSelect` — "how many options may I choose"), confirmed as real typed columns rather than a generic attribute table. This is a completely different concept — *value bounds for a numeric quantity a Hunter records and mutates during play* — sharing only the word "min/max," not the underlying question. No conflict with that earlier decision, and no reason to reopen it.
- **Fits the "shape emerges from populated fields" philosophy directly** — exactly the same discriminator-free approach already governing every other leaf kind (`Title`-only, `DescriptionText`-only, both, neither-with-children). `NumericMin`/`NumericMax` populated is simply one more combination in that same space, not a parallel mechanism.
- **No naming collision with `MinSelect`/`MaxSelect`** — those govern *this option's own children* (a pick-count), `NumericMin`/`NumericMax` govern *a value this option's own selection produces* (a quantity range). Structurally unrelated concepts on the same row; a leaf numeric option has no children, so its own `MinSelect`/`MaxSelect` stay null, same as every other childless option today.
- **Reuses the existing parent/child pick mechanism for attachment, rather than needing a new "auto-included leaf" concept.** Modeled as: "An Infernal Power" gets `MinSelect=1, MaxSelect=1` with exactly one child option (`Title="Infernal Favour"`, `DescriptionText=null`, `NumericMin=0, NumericMax=3`) — the identical structural shape already used for Professional's synthesized "Agency name:" child (one mandatory child, `{{blank}}`-only) and Forged's Dual Nature Effect children (each child distinguishing itself from siblings via its own `Title`). The only difference is the *leaf content kind* — a numeric range instead of a `{{blank}}` text marker — not a new attachment mechanism.
- **Two alternatives considered and declined, same rigor as every other schema proposal in this doc:**
  - **My own original recommendation** (nullable `TriggeringBespokeOptionId` FK on `PlaybookExtraTrack`) — would have reused the full existing track vocabulary (`Name`/`BoxCount`/`StartLabel`/`EndLabel`) for free, but at the cost of a cross-table FK pointing from a Playbook-level concept down into a specific Option nested inside a Section, and doesn't keep "what this option grants" co-located with the option itself. Declined in favor of Skyler's proposal, which is structurally tighter and generalizes to non-track numeric needs too (not just spend/restore resources).
  - **Reuse `{{blank}}` for a numeric fill-in** (e.g. `DescriptionText = "{{blank}}"` on a child option, same as Agency's synthesized child) — rejected for the same reason `FreeTextLabel` wasn't modeled by overloading `{{blank}}`: it would give the token a second meaning (free text vs. a bounded, mutable, game-mechanical quantity with real Min/Max enforcement) depending on context, and loses the actual bounds entirely (nothing about `{{blank}}` can express "0 to 3").
- **`StartLabel`/`EndLabel` deliberately not added to this new leaf shape** — Infernal Favour has no printed start/end labels at all (checked directly, confirmed absent — not even Luck/Harm's literal "Okay"), so there's no live case demonstrating the need yet. Same "don't add a field speculatively, only build it when an actual instance demonstrates the need" discipline already applied to `PlaybookExtraTrack.StartLabel` itself (only added once Pararomantic's Relationship Status showed a real non-"Okay" case) and to declining a preemptive `Required`-on-`BespokeOption` flag above. Noted here as a natural future extension point if a labeled-boundary case shows up later, not built ahead of it.

**Instance side**: one new nullable `NumericValue` (int) column on the existing `HunterBespokeSelection` — populated only on the row for a `BespokeOption` that itself has `NumericMin`/`NumericMax` set, representing the Hunter's *current* value for that resource. This is the first `HunterBespokeSelection` field that's genuinely mutable throughout play rather than fixed at creation (every other field on that table — `BespokeOptionId`, `FreeformText` — is set once when the pick is made and not expected to change afterward); flagged explicitly so Phase 4/9 doesn't assume the standard "set once at creation" pattern applies here. **Initialization convention, not a schema concern**: for spend/restore-shaped resources like Infernal Favour, `NumericValue` initializes to `NumericMax` (starts full, gets spent down toward `NumericMin`) — a documented authoring/UI convention, not a new field, the same way "default `MinSelect`/`MaxSelect` to 1 unless wording implies otherwise" is a documented authoring rule rather than a schema mechanism.

Net schema delta for this whole concept: two new nullable ints on `BespokeOption`, one new nullable int on the existing `HunterBespokeSelection`. Zero new tables, zero changes to `BespokeSection` or `PlaybookExtraTrack`.

**Content-fidelity split, corrected 2026-08-27 — the original 3-way split was wrong as a matter of source fact, not just a call worth revisiting.** This section originally proposed attributing "Record what the magic was, the power it offers you, and the downside it asks of you..." to `BespokeJournal.Description` on semantic grounds (it's clearly about recording magic/power/downside, matching the Journal's own field labels). Bowser checked the raw PDF item stream directly and found "Consumed MagiC (Power, Downside)" has **zero body text of its own** — a bare table heading, the last item in the column, nothing printed after it. The entire paragraph, that sentence included, sits under "Corruption" alone.

**Resolved: `BespokeJournal.Description` is genuinely `null`.** The source gives this Journal nothing beyond its own heading — which already supplies `Title` ("Consumed Magic") and both `BespokeJournalField` labels ("Power", "Downside"). A real, honest null, not a gap to fill later. The whole explanatory paragraph belongs to Corruption's `Description`/`EffectText` — see `architecture.md`'s "Extra Tracks" section for the corrected split and the reasoning for why the header boundary was respected rather than stretched (same precedent Skyler already set for Covenant's "Covenant" ability, applied consistently here rather than re-litigated).

**"How Consuming Magic Works" — an ordinary, already-modeled `BespokeSection`, no new concept.** Distinct from both Corruption and the Consumed Magic journal: a real pick-list ("When you consume/absorb evil magic, how does it work?", 5 description-only options, pick 1 — inferred from the singular framing, same confidence as Background's implicit pick-1), matching the Mission shape exactly. **Split criterion, stated explicitly so it's applied consistently going forward**: `EffectText` applies only when the source presents genuine follow-through/consequence content as a **distinctly, separately-positioned block** in the source (Changeling's trailing paragraph is printed after the options, in a different position than the intro; Fate's closing sentence is likewise separated from the early blurb by the entire options list). A single continuous `Description` paragraph that merely contains one forward-looking clause partway through (e.g. Underworld's "Pick how you discovered about the real underworld. **Flagged, not designed, 2026-08-27 — watch for a "required option" concept eventually showing up here too.** The standard Moves model just gained a `Required` field (`PlaybookMove`, renamed from `IsAutoGranted` — `architecture.md`'s Moves section) after Celebrity's "Fakelore" confirmed a playbook can have a mandatory grant alongside a separate pick-N-of-M pool, at the same time. Nothing in the 4 playbooks read for bespoke content so far has needed the equivalent on a `BespokeOption` (every bespoke pick-list seen is either "pick N of M, no option is individually mandatory" or, per Chosen's Fate, "pick all N of N" — which the existing `MinSelect == MaxSelect == count` mechanism already covers without a per-option flag). Noted here so it isn't rediscovered as a surprise later if/when a bespoke ruleset does turn out to need it.

## 4. Reacting to Skyler's specific questions

**Naming the Background shape.** "Traditional" or "Classic" describe the game's *flavor*, not the schema's *structure*, which risks being confusing later (does "Classic" mean "title+description," or does it mean "the original/simplest shape" — those aren't the same thing once Mission's flat description-only shape turned out to be even simpler). Suggested name: **"Titled Choice"** — describes exactly the one structural trait that distinguishes it (options have their own title, unlike every other shape found so far). Companion names for the others, purely as vocabulary: **"Blank-Fill Choice"** (Heat), **"Nested Choice"** (Underworld), **"Tag Pick"** (Chosen's label-only groups), **"Simple Choice"** (Mission's flat description-only case).

**Should min-select/max-select/blank live in a generic `bespoke_rule_attributes` table? Confirmed 2026-08-26.** Min-select and max-select: real typed nullable-int columns directly on `BespokeSection`/`BespokeOption` (Section 3), not a generic attribute table — there are only ever two of them, every shape found so far uses the same two, and a generic mechanism buys nothing here a plain nullable-int pair doesn't already give for free. **Skyler's refinement**: default `MinSelect`/`MaxSelect` to **1** unless the source wording implies otherwise, and treat genuinely ambiguous wording (e.g. no explicit count stated at all) as a **case-by-case judgment call made during ingestion**, not something to solve generically in the schema now. This matches how every "inferred" row in Section 1's table was already being read — codifies it as the actual authoring rule rather than leaving it implicit.

**The "blank" concept — confirmed and substantially expanded, 2026-08-26.** Don't model it as a flag or attribute. Adopt a **handlebars-style placeholder token, `{{blank}}`, embedded directly in `DescriptionText`**, marking exactly where the UI renders an input control — confirmed as the right framework: simple for the frontend to detect and react to. (Verified this doesn't collide with Angular's own `{{ }}` template interpolation syntax: Angular only compiles `{{ }}` expressions that appear in a template's *own* static markup, never inside the *value* of a bound data string — a `DescriptionText` value containing the literal characters `{{blank}}`, whether rendered via ordinary interpolation or `[innerHTML]`, is inert data to Angular, not re-parsed as an expression. Non-issue, but worth stating since it looks like it might collide at a glance.)

**New scope, 2026-08-26 — preserving inline formatting (bold/italic/bulleted lists) within description text.** Real examples from the source: each Crooked Background option has a bolded phrase naming its mechanical effect; custom-move sections across playbooks (a Phase 2/standard-sections concern, not just bespoke — see the cross-reference below) use bulleted lists for roll-result breakdowns (10+/7–9/miss-style). Skyler wants this preserved as real structure, not flattened to plain text, but explicitly scoped to **section/option description text only** — Look and History content is typically bulleted in the source too, but that's being treated as a UI-component-level presentation concern specific to those two sections, not something to persist as marked-up content.

**Recommendation on representation: a small, constrained-tag HTML subset — `<b>`/`<strong>`, `<i>`/`<em>`, `<ul>`/`<li>` only — not full Markdown syntax.** Checked this codebase directly before recommending (no markdown library in `package.json`, no existing `[innerHTML]` usage anywhere in the Angular app) — so neither option inherits an existing pattern, and the choice is genuinely open. HTML wins because Angular's `[innerHTML]` binding + its built-in `DomSanitizer` already safely renders exactly this tag set by default, with **zero new dependency** — Markdown would require adding and maintaining a markdown-to-HTML parser purely to support a narrow, fixed formatting need (bold/italic/bullets, nothing else — no links, headers, tables, code blocks). The allowed-tag set should stay deliberately small and enumerated, both to avoid this becoming a general-purpose rich-text field and to make server-side validation straightforward if that's ever added as defense-in-depth alongside Angular's client-side sanitizer.

**So `DescriptionText`'s actual representation, put together**: a string containing plain text, a small fixed set of inline/block HTML tags for emphasis and bulleted lists, and — independently, not in conflict — literal `{{blank}}` tokens wherever the source has a fill-in blank. Not "lightweight Markdown" as originally floated in the question; a constrained HTML subset instead, for the dependency reason above.

**Also new, 2026-08-26 — normalize inconsistent source wording during authoring, don't preserve it literally.** Where the PDF's own wording is internally inconsistent (Skyler's example: Crooked's Underworld's last option says "(choose one)" while every other option in the same ruleset says "Pick one:") — normalize to consistent phrasing during import, working from assumed intent rather than literal source fidelity. Not a schema concern; this is authoring guidance that belongs in the Phase 4 Skill's checklist (`open-questions.md` Q10) once that Skill is written.

Skyler is explicitly fine with the real parsing complexity this adds per playbook, given the plan is to ingest one playbook at a time and handle formatting edge cases as they come up rather than solving every fidelity case up front.

**Cross-cutting consequence — confirmed 2026-08-26, then narrowed the same day.** This formatting decision isn't confined to the new bespoke-ruleset schema — Skyler confirmed it as a genuine missed requirement in the original Phase 2 pass. **But it's scoped to Moves specifically, not a general rule**: only `PlaybookMove.DescriptionText` needs the constrained-HTML-subset treatment. Skyler explicitly reviewed every other standard section (ability ratings, luck/harm/experience, gear, pronouns, looks, history, improvements, advanced improvements) and confirmed plain text is sufficient for all of them — an earlier version of this paragraph stated the requirement more broadly ("any Description-type standard field"), which overstated it. Now noted correctly in `architecture.md`'s Phase 2/Moves section, not just here. **Process change accompanying this**: Phase 4 gains an explicit validation checkpoint — Skyler personally confirms formatting fidelity is being correctly captured in the 3 pilots' Moves content specifically before Phase 5 (bespoke rulesets) proceeds (`phases.md` Phase 4).

**Extraction pipeline for actually capturing bold/italic/lists — resolved and now permanent, not a spike.** The prior round flagged that `pdftotext -layout` (this task's established extraction tool) cannot see or preserve bold/italic/font-weight information, meaning the constrained-HTML-subset representation had no verified source of truth for *where* the markup goes. **Now confirmed solved and locked in**: Bowser's pdf.js-based extraction pipeline passed both the original acceptance test (Crooked/Background/Hoodlum, `<b>` only) and a second validation pass against The Covenant's Moves section (confirming `<i>` and nested `<ul>`/`<li>` roll-result breakdowns), and Skyler approved it for standing use — `docs/hunter-playbooks/pdf-extraction-pipeline.md` and `tools/pdf-extract/` are the reference, formalized into `phases.md` Phase 4. No Angular/Luigi preview UI was needed to validate the raw output — Luigi stays on hold, not activated. Not this doc's design work; noted here so the record reflects the resolved state.

**Underworld's parent/sub-option nesting — one attribute-heavy table, or does every attribute need its own table?** Recommendation: **neither extreme** — a single self-referencing `ParentOptionId` on the *same* `BespokeOption` table (an adjacency-list, the standard normalized shape for shallow trees), not a dedicated "sub-option" table and not a generic attribute mechanism. This generalizes past 2 levels for free if a future playbook needs deeper nesting (untested, but the shape doesn't care), and it's how the recursive `MinSelect`/`MaxSelect`-per-option-with-children idea above falls out naturally — "pick N of my children" is the same concept whether "my children" are a Section's top-level options or an Option's nested sub-options. **Confirmed 2026-08-26 (see Section 5, Q1)**: sub-options follow exactly the same rules as parent options at any depth, no special-casing anywhere — this is precisely what's described here, already.

**Both predictions in the paragraph above actually exercised for the first time, 2026-08-29 — The Visitor's "Expatriation."** (1) **3-level nesting**: Section ("Expatriation") → category divider ("Home Culture") → line ("Line 1"/"Line 2"/"Line 3") → tag item, confirmed to work with zero schema changes, exactly as predicted. (2) **A real range at the "how many of my direct categories" level**, not a fixed `MinSelect == MaxSelect == count`: Home Culture's own children (its 3 Lines) use `MinSelect=2, MaxSelect=3` ("at least two of three lines," not all three mandatory) — every prior nested-category case (Fate, Friendship, Combat Magic) had every category mandatory, so this is the first case distinguishing "some but not all of my children must be engaged" from "all of them, always." Confirmed this is *not* the same shape as Combat Magic's shared-numeric-budget gap: Expatriation has no cross-category total to enforce, only a categorical participation minimum, which independent per-category bounds already express without any accepted gap. One related instance-side question surfaced by the same case, resolved by reasoning rather than escalated: whether a category counts as "engaged" is a **derived** fact (≥1 child has a `HunterBespokeSelection` row), not a separately **stored** one — the first time this distinction was actually load-bearing, since every prior nested-category case had 100% category engagement by construction. Full detail: `bespoke-ruleset-catalogue.md` `## The Visitor`.

**Instance-side persistence — JSON field vs. bridge table.** Recommendation: **a bridge table, `HunterBespokeSelection`, not JSON** — and the strongest argument for this isn't just "no JSON precedent anywhere in this API project" (true, and already established earlier in this doc), it's that **Hunter already has two other pick-list persistence mechanisms in this exact same conversation, both FK-based**: `HunterMove` and `HunterGearSelection` (resolved as live-linked FK bridges when Q4 of the earlier round was answered). Using JSON here would be a third, different persistence shape on the same entity for what's conceptually the same kind of thing — "which options did this Hunter pick" — not just a break from codebase convention in general, but an internal inconsistency within Hunter itself.

Honest pros/cons, not just precedent-by-default:
- **JSON pros**: trivially absorbs shape variety with zero schema change; no bridge-table proliferation.
- **JSON cons, concretely**: no FK-enforced referential integrity (deleting/renaming a `BespokeOption` silently orphans instance data with no DB-level protection, unlike a bridge table's FK); no SQL query/join-ability without `jsonb` functions this codebase has never used anywhere (Skyler's own flagged tradeoff — real, whether or not it turns out to matter for this domain); breaks the just-established live-link pattern for Hunter's other two selection types.
- **Bridge table shape, corrected 2026-08-26 (see Section 5, Q4)**: `HunterBespokeSelection(Id, HunterId, BespokeOptionId, FreeformText [nullable])`. `BespokeOptionId` is **required, not nullable** — the earlier draft here nullable'd it to cover Divine's "mission of your creation" escape hatch, which turned out to be mis-scoped (Section 1's correction: that's an Advanced Improvement concern, not an initial-pick one). Every confirmed selection in the 3 pilots' character-creation-time bespoke picks attaches to a real predefined option. `FreeformText`, still nullable, is used only when the chosen option's `DescriptionText` contains a `{{blank}}` token — one row per selected option, its own blank's answer scoped to that row, so multi-pick-with-independent-answers (Heat) falls out for free. Underworld's parent+sub pick is just **two rows** — one selecting the parent option, one selecting the sub-option — no special "nested pick" mechanism needed beyond what multi-pick already requires.

## 5. Open questions from the last round — resolved 2026-08-26

1. **Per-option `MinSelect`/`MaxSelect` for nested sub-picks — real field vs. hardcoded convention.** **Resolved.** Skyler's answer: sub-options follow exactly the same rules as parent options, fully recursive at any depth, no special-casing of parent vs. child anywhere in the UI or API — and since `ParentOptionId` already lets any option be used as a parent, this already falls out of the existing structure with no extra field needed.

   **Reading this carefully rather than marking it closed on the first pass**: my original Section 3 draft already put `MinSelect`/`MaxSelect` directly on `BespokeOption` itself (not a separate mechanism), specifically so it would apply recursively to any option with children, parent or nested. There were two ways to read Skyler's answer — (a) confirming that design needs nothing further added, or (b) rejecting the field entirely in favor of a hardcoded "always pick 1 of children" rule. I landed on **(a)** as the correct reading: hardcoding a fixed rule would itself be a form of special-casing "how children behave" that Skyler's own wording explicitly rules out ("no special-casing... in UI or API"), whereas a single generic field usable identically whether or not an option has a parent is precisely what "no special-casing" describes. **Net effect: no change to Section 3's design** — this confirms what was already drafted rather than requiring a new one. Flagging this reasoning explicitly per Skyler's own ask, since if reading (b) was actually intended, that's a real, different design (hardcode pick-1, drop the field) worth saying so.

2. **Stored, human-readable shape label for admin UI — worth adding now?** **Resolved: no, leave it out.** Skyler's condition was "unless it would be difficult to retrofit later." Checked: it wouldn't be — a label column is fully derivable after the fact from which fields are already populated (`Title` set → "Titled Choice," blank marker present → "Blank-Fill Choice," `ParentOptionId` used → "Nested Choice," etc.) — the exact same logic Section 3 already uses to explain the design without a stored discriminator. Adding it later is a pure additive backfill with zero data-loss risk, so per Skyler's own stated condition, it stays out for now.

3. **Blank-marker / formatting fidelity.** **Resolved, substantially expanded** — see the new subsection under "Reacting to Skyler's specific questions" above (`{{blank}}` token confirmed; constrained-HTML-subset representation recommended and reasoned through; source-wording normalization during authoring; explicit Look/History exclusion; the `PlaybookMove.DescriptionText` cross-cutting consequence flagged, not yet acted on).

4. **Does `HunterBespokeSelection.FreeformText` need to distinguish "filled a blank" from "replaced with something wholly custom"?** **Resolved, and this answer corrected a real scoping error in how the question was originally framed.** Skyler's answer: this distinction only actually matters for Advanced Improvements — one shared column is fine for now; splitting into two later is cheap if it turns out to matter. Tracing through *why* landed on more than just "keep one column": the "wholly custom" case this question was built around (Divine's "mission of your creation") isn't actually something `HunterBespokeSelection` needs to handle at all — it's an Advanced Improvement (level-up-time), not part of the initial Mission pick, and Advanced Improvement tracking is a separate, not-yet-designed, currently out-of-scope mechanism (Section 1's correction above). So `BespokeOptionId` reverts to **required**, not nullable, and `FreeformText` serves exactly one purpose for this pass — blank fill-in text — with no ambiguity to disambiguate in the first place. Simpler than either original option (one shared column, or a split flag) because the case that motivated the split doesn't apply here.
