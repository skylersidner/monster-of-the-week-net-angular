## Overview

Both bugs below were discovered incidentally while verifying Phase 6's dark-mode behavior — neither is related to theming, and neither was touched during the theming rollout. They're documented here so they can be picked up as their own piece of work in a future session, rather than getting lost as a throwaway note in a phase's decision file.

## Bug 1 — Monster Type has no visible "required" indicator

**Where:** `src/web/monster-of-the-week-web/src/app/features/mysteries/pages/mystery-create/mystery-create-monster-phase.html`, line 22, and the corresponding validator in `mystery-create.store.ts`, line 253.

**What happens:** The wizard's Monster phase has three fields with `Validators.required`: Name, Monster Type, and Monster Archetype (`mystery-create.store.ts:250-254`). Name and Monster Archetype both show a red `*` next to their label and a red inline error ("Name is required" / "Archetype is required") when left empty and touched — see `mystery-create-monster-phase.html` lines 4/7-9 and 26/28-30. **Monster Type has neither.** Its label (line 22) is plain text, and there is no `@if` block watching `monsterTypeId.invalid && touched` to show an error.

**User-facing effect:** if a user leaves Monster Type unset and clicks Next, `validateCurrentStep()` (`mystery-create.store.ts:850-852`) correctly blocks navigation and calls `markAllAsTouched()` — but because the template has no error text wired to this specific field, nothing visibly changes. The wizard just silently refuses to advance, with no indication of why. This is how Skyler originally noticed the issue — as a behavioral discrepancy (the wizard "getting stuck") rather than a visible error message.

**Likely fix:** add a `<span class="text-danger">*</span>` to the Monster Type label and an `@if (store.monsterForm.controls.monsterTypeId.invalid && store.monsterForm.controls.monsterTypeId.touched)` error block, matching the pattern already used for Name and Monster Archetype immediately above and below it.

## Bug 2 — Re-entering a completed wizard phase re-submits it, creating duplicate entities

**Where:** `src/web/monster-of-the-week-web/src/app/features/mysteries/pages/mystery-create/mystery-create.store.ts` — `next()` (line 690), `jumpToPhase()`/`isPhaseAccessible()` (lines 719-733), and `submitCurrentPhase()` (line 858).

**What happens:** `isPhaseAccessible()` allows navigating into any phase that is either the current phase or already marked complete (`phase === this.currentPhase() || this.phaseComplete()[phase] === true`), which is how the tracker bubbles let you jump backward to a finished phase. But `next()` has no matching guard: stepping through to the end of *any* phase — including one you've already completed and are only revisiting — unconditionally calls `submitCurrentPhase()`, which calls the phase's own submit method (e.g. `submitPhase1()` for the monster phase) with no check for "has this phase already been submitted in this session." Each submit is a fresh `POST` (e.g. a new monster/location/bystander create call), not an update.

**Reproduction (confirmed deterministically):** complete phase 1 (create a monster), jump back to phase 0 via the tracker, then walk forward through Next again without changing anything. Phase 1 re-submits, producing two identical `POST` calls and two same-named monsters attached to the same mystery.

**Evidence this has already happened during real use, not just testing:** the dev database currently contains four monsters named "The Miller," two locations named "The Old Mill," and two bystanders named "Deputy Marsh," all attached to mysteries that were hand-created (not generated by any automated test or agent session). This strongly suggests the bug has already produced duplicate data outside of this investigation. That data was left in place — it wasn't created by this work, so it wasn't ours to clean up.

**Likely fix:** either disable/skip re-submission when `phaseComplete()[phase]` is already `true` and nothing in that phase's form has changed since it was marked complete, or convert the affected submit methods to upsert-by-ID (the way `submitPhase0()` already does via `isEditMode()` — though note that flag reflects whether the *whole mystery* is in edit mode, not whether an individual phase within a new mystery has already been submitted once, so it doesn't cover this case as-is).
