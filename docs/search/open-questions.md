## Genuine design forks (full Option A/B tables in `phases.md`)

These aren't defaults quietly picked — they're real architectural forks with opposite trade-offs, written up as Option A/B in `phases.md`:

- **Endpoint shape** — one `GET /api/search` with optional paging params vs. two purpose-built endpoints (`/api/search/quick` + `/api/search`). Recommended and shipped: two endpoints. See `phases.md` → "Architectural Decision: Endpoint Shape".
- **Extensibility mechanism** — code-level `ISearchProvider` registry vs. a persisted `SearchableField`/index table synced on write. Recommended and shipped through Phase 1–3, and confirmed to scale cleanly through Phase 4's field/sub-resource expansion without needing the persisted-table alternative. See `phases.md` → "Architectural Decision: Extensibility Mechanism".

No part of either round of feedback is being pushed back on. Round 1 (substring tier, min-length bump, titles-only scoping, sub-resource-name reweighting, forward-shaped `snippet` contract) shipped as designed in Phases 1–3. Round 2's new Phase 4 requirement (snippet + highlight + field label on the results page) is fully implementable as specced — the judgment calls in rows 14–21 above are the concrete decisions that make it buildable, not places where the request itself was problematic.

## Sequencing note

Phase 2 (header dropdown) shipped before Phase 3 (results page); the transient "Enter with nothing highlighted → 404" gap this could have caused did not end up mattering since both shipped in the same round. For Phase 4: 4a (entity long-text matching) and 4b (sub-resource matching) can each ship independently and are each a strict improvement on their own (more matchable content, real `snippet` text even before 4c's highlighting lands — `phases.md` Known Gaps table). 4c (frontend highlighting) has no similar deploy-order constraint but delivers the most value once 4a+4b are live, since a bigger share of results will carry a real `snippet` by then.
