## Genuine design forks (full Option A/B tables in `phases.md`)

These aren't defaults quietly picked — they're real architectural forks with opposite trade-offs, written up as Option A/B in `phases.md`:

- **Endpoint shape** — one `GET /api/search` with optional paging params vs. two purpose-built endpoints (`/api/search/quick` + `/api/search`). Recommended: two endpoints. See `phases.md` → "Architectural Decision: Endpoint Shape".
- **Extensibility mechanism** — code-level `ISearchProvider` registry vs. a persisted `SearchableField`/index table synced on write. Recommended: code-level registry now, revisit alongside a `pg_trgm`/`tsvector` migration later if scale demands it. See `phases.md` → "Architectural Decision: Extensibility Mechanism".

No part of the 2026-08-01 feedback is being pushed back on — everything requested (substring tier, min-length bump, titles-only scoping, sub-resource-name reweighting, forward-shaped `snippet` contract) is implemented in `architecture.md`/`phases.md` as described above, with the refinements noted in rows 11–13 (titles-only scope tied to the weight tiers; long-text fields correspondingly demoted to `Tertiary` as the natural counterpart of promoting sub-resource names to `Secondary`).

## Sequencing note

Phase 2 (header dropdown) is written to ship before Phase 3 (results page) exists, which means "Enter with nothing highlighted" briefly routes to a 404 until Phase 3 lands (see `phases.md`'s Known Gaps table). If Phase 2 and Phase 3 won't ship close together, flag it — the simplest fix is registering an empty placeholder `/search` route in Phase 2 rather than reordering the phases.
