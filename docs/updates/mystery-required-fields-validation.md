# Required-Field Validation — Mystery (Phase 1 of a Cross-Domain Initiative)

**Prepared by:** Yoshi (Architect)
**Status:** Decisions locked — Skyler answered all 4 open product-scope questions (2026-08-06). Ready for implementation planning.
**Date:** 2026-08-05 (revised 2026-08-06)

> This is **Phase 1 of a repeatable pattern**: required-field validation, audited and fixed one domain at a time, starting with Mystery. The deliverable here is two things — (1) Mystery's own field decisions, and (2) a validation *mechanism* verified to generalize cleanly to Monster, Minion, Location, and Bystander, each of which gets its own follow-up pass applying the same mechanism to its own field list. No C#/TypeScript files were edited to produce this document — every claim below was checked against live source and, where the claim was about runtime behavior rather than code shape, against the actual running API (`docker compose up -d postgres` + the already-running `dotnet run` dev instance on `http://localhost:5225`, confirmed live before testing; test data created during verification was deleted afterward).

## Background — Confirmed From Current Source

### Entity / DTO / migration inventory

- `Mystery` (`src/api/MonsterOfTheWeek.Api/Data/Entities/DomainEntities.cs:27-45`): `Name` (`required string`, non-null), `AdventureTypeId` (`Guid`, non-null FK), `Concept`/`Hook`/`Overview`/`Notes` (all `string?`), plus `CreatedAt`/`UpdatedAt` (server-set) and navigation collections (`Countdown`, `MysteryMonsters`, `MysteryLocations`, `MysteryBystanders`, `CustomMoves`).
- `Countdown` (`DomainEntities.cs:47-59`): six independent nullable stage fields (`Day`/`Shadows`/`Sunset`/`Dusk`/`Nightfall`/`Midnight`, all `string?`), 1:1 with `Mystery`, always auto-created empty at mystery-creation time (`MysteryService.cs:44`).
- No `Clue` entity exists anywhere in the schema — the countdown stages are the closest analog to "clues" in this domain model.
- DB fluent config (`Data/MotwDbContext.cs:63-78`) matches the entity's C# nullability exactly: `Name` and `AdventureTypeId` are `.IsRequired()`; `Concept` additionally carries `.HasMaxLength(500)` (no equivalent client or server length guard exists anywhere — see Known Gaps); `Hook`/`Overview`/`Notes` have no length cap. No migration or DB constraint enforces anything beyond null-vs-not-null and the one length cap.
- `UpsertMysteryRequest` (`Contracts/ApiContracts.cs:59-65`): `string Name` (non-nullable), `Concept`/`Hook`/`Overview`/`Notes` (`string?`), `Guid AdventureTypeId`. `UpsertCountdownRequest` (`ApiContracts.cs:67-73`): all six stages `string?`. Both are plain records — **zero DataAnnotations attributes on either**, unlike four other request types in this same file (see next section).
- `MysteryListItemResponse`/`MysteryDetailResponse` (`ApiContracts.cs:23-57`) mirror the entity's nullability 1:1; Angular's `models.ts:75-121` mirrors the C# contracts exactly, field-for-field, nullable-for-nullable.
- **Mystery-level custom moves have entity + DTO shape (`MysteryCustomMove`, `MysteryDetailResponse.CustomMoves`) but zero API surface** — `MysteriesController.cs` has no `custom-moves` routes at all, and neither `IMysteryService`/`MysteryService` nor `IMysteryRepository` have any `GetCustomMoves`/`CreateCustomMove`/etc. methods, unlike every other domain (`MonstersController.cs:143-157` has full CRUD for `MonsterCustomMove`; Minion/Location/Bystander all have the equivalent). `CustomMoves` on a `MysteryDetailResponse` will always be `[]` today — not a required-field question, but a real, previously-undocumented CRUD-parity gap worth flagging (see Known Gaps).

### Current server-side validation — precisely, not approximately

- **DataAnnotations validation is not merely "possible," it is already fully wired and already firing in this app, with zero explicit configuration anywhere in `Program.cs`.** `Program.cs:16` calls `builder.Services.AddControllers()` and every controller (`MysteriesController` included, `Controllers/MysteriesController.cs:7`) carries `[ApiController]`, which enables ASP.NET's automatic invalid-`ModelState` → 400 behavior by default. Verified live: `POST /api/mysteries` with `"name": null` (or the field omitted entirely) returns `400 {"errors":{"Name":["The Name field is required."]}}` today — with **no `[Required]` attribute anywhere on `UpsertMysteryRequest`**. This is `[ApiController]`'s built-in implicit-required inference for non-nullable reference-type properties (the project has `<Nullable>enable</Nullable>`, `MonsterOfTheWeek.Api.csproj:5`) — it silently protects every non-nullable `string` property on every request DTO in the app today, already, for free.
- **That implicit inference only catches null/missing — not blank or whitespace-only strings, and it only applies to reference types, not value types.** Verified live: `POST /api/mysteries` with `"name": ""` or `"name": "   "` and a valid `adventureTypeId` returns **`201 Created`**, persisting a Mystery with `"name":""`. The trimmed-empty-string case sails straight through model binding (a non-null empty string satisfies "is this non-null"), then straight through `MysteryService.CreateAsync` (`Services/MysteryService.cs:32-51`), which calls `request.Name.Trim()` and saves it with no `IsNullOrWhiteSpace` check anywhere. Confirms and extends the prior finding already logged in `.squad/agents/Yoshi/history.md` (2026-08-04, Bug 2 follow-up) that this is a codebase-wide pattern, not Mystery-specific — now directly confirmed for Mystery itself, with a live repro.
- **A separate, distinct gap: `AdventureTypeId`'s FK existence is never checked, and unlike `Name`, ASP.NET's implicit-required inference does not protect it at all** (it's a non-nullable `Guid`, a value type — the implicit-required feature only applies to reference types). Omitting `adventureTypeId` from the request body silently binds it to `Guid.Empty` rather than failing model binding. Verified live: `POST /api/mysteries` with a syntactically valid but non-existent `adventureTypeId` returns an **unhandled `500`** (`Program.cs:50`'s generic `UseExceptionHandler()`/`AddProblemDetails()` catching a DB foreign-key violation, not a clean validation error). Compare `MonsterService.CreateAsync` (`Services/MonsterService.cs:23-41,66-74`), which explicitly checks `MonsterTypeExistsAsync`/`MonsterArchetypeExistsAsync` before touching the DB and returns `ServiceResult<T>.Validation(...)` (a clean `400`) on failure — `MysteryService` has never been given the equivalent `AdventureTypeExistsAsync` check. `IMysteryRepository` (`Repositories/IMysteryRepository.cs`) has no such method today, and grep confirms `AdventureTypeExistsAsync` doesn't exist anywhere in the API project.
- **`MysteryService.CreateAsync`/`UpdateAsync` return raw `MysteryDetailResponse`/`MysteryDetailResponse?`, not `ServiceResult<T>`** (`IMysteryService.cs:9-10`), unlike every other domain's top-level create/update (`MonsterService.CreateAsync` → `ServiceResult<MonsterDetailResponse>`, `Services/MonsterService.cs:23,62`; `LocationService.CreateAsync` → `ServiceResult<LocationDetailResponse>`, `Services/LocationService.cs:48`) and unlike **`MysteryService`'s own `UpsertCountdownAsync`** (`MysteryService.cs:86-113`), which *does* use `ServiceResult<T>` (a `NotFound` check on `MysteryExistsAsync`). `MysteriesController.Create`/`Update` (`Controllers/MysteriesController.cs:22-39`) correspondingly never call anything resembling the `ToErrorResult`/`ToActionResult` helpers every other controller has (`MonstersController.cs:159-168`, `MinionsController.cs:156` — both private, per-controller, not a shared base class). **Mystery is the one domain whose own service doesn't consistently follow its own already-proven internal convention** — `UpsertCountdownAsync` in the same file shows the pattern is known and already used, just not applied to `CreateAsync`/`UpdateAsync`.
- Existing explicit-DataAnnotations precedent already lives in this exact file, just not applied to any of the five domains' own `Upsert*Request` types: `CreateTypeRefRequest`, `CreateWeaponTagRefRequest`, `CreateAdventureTypeRequest`, `CreateMonsterArchetypeRequest` (`ApiContracts.cs:6-20`) all carry `[param: Required, MinLength(N)]` on their `Name`/`Description`/`Motivation` fields — these back the **reference-data** creation endpoints (`ReferenceController.cs`), not the domain entities. Verified live that this precedent actually works end-to-end today: `POST /api/adventure-types` with `"name": "   "` returns `400 {"errors":{"Name":["The Name field is required."]}}` (confirms `[Required]`'s default `AllowEmptyStrings=false` trims and rejects whitespace-only strings — not just nulls), and `"description": "hi"` against `[MinLength(5)]` returns `400` with the expected message. **This is the single cheapest, already-proven-in-this-codebase mechanism for closing the blank-string gap** — see Architecture Discussion.

### Frontend inventory — structurally different from the other four domains

- **Mystery has no separate create/edit page.** `mysteries.routes.ts:7-10,32-34` routes both `create` and `:id/edit` to the same `MysteryCreateComponent` (the multi-phase wizard). `mystery-detail.ts`/`.html` (`features/mysteries/pages/mystery-detail/`) is **read-only** — no `FormGroup`, no save method, no call to `MysteryService.update(...)` anywhere in the file. This is architecturally distinct from Monster/Minion/Location/Bystander, each of which now has (per the completed four-phase "standalone creation" initiative) its own dedicated `*-form` shared component used identically by a standalone create page and its own detail/edit page. **Mystery's only core-fields form is the wizard's phase-0 `conceptForm`**, and it's the only place, create or edit, that Mystery's own fields get touched client-side.
- `MysteryCreateStore.conceptForm` (`pages/mystery-create/mystery-create.store.ts:252-256`): `name` — `[Validators.required, Validators.minLength(1)]`; `adventureTypeId` — `[Validators.required]` (rendered as a `<select>` with a disabled blank placeholder option, `mystery-create-mystery-phase.html:13-19`); `concept` — no validators. `hookForm`/`overviewForm`/`countdownForm` (lines 258-273): no validators on any field — `hook`, `overview`, and all six countdown stages are unconditionally optional, matching the entity/DTO.
- **`Validators.minLength(1)` on a non-trimmed live control does not close the whitespace gap** — Angular's `Validators.required` (and `minLength`) operate on the raw, untrimmed control value; a value of `"   "` has length 3 and is non-empty, so it passes both validators. The component does call `.trim()` at submit time (`submitPhase0`, `mystery-create.store.ts:943`), but only *after* validation has already passed — there is no re-check of trimmed length before the API call. This is the client-side half of the same gap confirmed server-side above: **a whitespace-only Name currently passes every validation layer that exists today, client and server, and is silently persisted as `""`.**
- The visual required-field indicator convention (`<span class="text-danger">*</span>` next to the label, `mystery-create-mystery-phase.html:4,12`) is present for `name` and `adventureTypeId` and correctly absent for `concept`/`hook`/`overview`/countdown stages — the asterisk convention in the UI is not the gap; the underlying validator is.
- **`notes` has zero UI surface anywhere in the app.** `submitPhase0` (`mystery-create.store.ts:947`) hardcodes `notes: null` on every submit; no wizard phase has a `notes` form control, and `mystery-detail.html` never renders it. `Notes` is a fully-modeled, fully-nullable, fully-plumbed-through-the-DTO field that no UI path can ever populate except a direct API call. Distinct from the required-field question (it's optional either way) but worth flagging as an inventory finding — see Known Gaps.
- **Confirmed latent-bug pattern the task asked me to check for**: `mystery-detail.html:10` renders `<h2 class="m-0">{{ mystery()!.name }}</h2>` unguarded, and `mysteries-list.html:19` renders `{{ mystery.name }}` as the entire link text of the mystery's list-row link — both assume a non-empty `Name` despite the type only guaranteeing non-null. Verified live: creating a Mystery with `Name: ""` via the API (the same live repro used above) produces exactly the broken UI this predicts — a blank `<h2>` page title on the detail page and an empty, effectively unclickable-looking link label on the list page. `Concept`/`Hook`/`Overview`/countdown stages are all correctly wrapped in `@if (...)` guards in both templates — only `Name` (and, on the list page, `adventureType.name`, which is server-guaranteed non-blank via its own FK+DB-required chain) is rendered unguarded, which is itself evidence the app already treats `Name` as implicitly required in practice — the bug is that nothing actually enforces that assumption.

### Cross-domain spot check (per the task's completeness requirement)

Globbed the full `src/api/MonsterOfTheWeek.Api/` and `.../features/` trees (not just the directories named in the task) before concluding anything about "the pattern." Confirmed:
- `[ApiController]` is present on **every** controller (`MinionsController`, `MonstersController`, `LocationsController`, `BystandersController`, `SearchController`, `ReferenceController`, `MysteriesController`) — the implicit-required/DataAnnotations mechanism above is already active for every domain's `Upsert*Request` types today, not just Mystery's.
- `MonsterService` and `LocationService` (spot-checked in full) both already use `ServiceResult<T>` + an `XxxExistsAsync` pre-check for every FK on their `CreateAsync` — `MonsterService.CreateAsync(UpsertMonsterRequest, ...)` (`Services/MonsterService.cs:62-90`) is the cleanest reference example: two `ExistsAsync` checks, each returning `ServiceResult<T>.Validation(...)` on failure, before ever touching the DB. Every controller (`MonstersController`, `MinionsController`, confirmed by grep) has its own private `ToErrorResult(ServiceError)`/`ToActionResult<T>(ServiceResult<T>)` pair — duplicated per-controller, not a shared base class, which is itself a real (if minor) existing convention worth preserving rather than "fixing" as part of this pass.
- None of the five domains' own `Upsert*Request` types (`UpsertMysteryRequest`, `UpsertMonsterRequest`, `UpsertMinionRequest`, `UpsertLocationRequest`, `UpsertBystanderRequest`) carry any DataAnnotations today — the blank-string gap confirmed for Mystery above is confirmed by direct code inspection (not re-tested live) to be structurally identical across all five domains' `Name` fields, matching the prior Bug-2-era finding in `.squad/agents/Yoshi/history.md`.
- **Conclusion: the validation mechanism recommended below (DataAnnotations for presence/shape, `ServiceResult<T>` + `XxxExistsAsync` for FK existence) requires no new infrastructure for any of the other four domains** — every piece of plumbing it needs (`[ApiController]`, the `ServiceResult<T>`/`ToErrorResult` convention, the `XxxExistsAsync` repository-method shape) already exists and is already exercised by at least Monster and Location today. The only per-domain work in a follow-up phase would be adding the actual attributes/checks to that domain's own `Upsert*Request`/`*Service`, not building anything new.

## Recommended Validation Pattern

**Recommendation: two-layer split, both layers already-proven in this exact codebase, neither one new.**

1. **Presence/shape of a scalar value → DataAnnotations on the `Upsert*Request` record**, evaluated automatically by `[ApiController]`'s existing model-validation pipeline before the controller action (and therefore the service) ever runs. For Mystery: add `[param: Required]` to `Name` (catches null, missing, and — per `RequiredAttribute`'s default `AllowEmptyStrings=false` behavior, verified live against the existing `CreateAdventureTypeRequest` endpoint — whitespace-only too, with zero extra code). Optionally `[param: MaxLength(500)]` on `Concept` to close the adjacent length gap the same way.
2. **Existence/validity of a referenced entity → stays in the service layer, using `ServiceResult<T>`**, exactly the shape `MonsterService`/`LocationService`/`BystanderService` already use for their own FKs. For Mystery: add `AdventureTypeExistsAsync` to `IMysteryRepository`/`MysteryRepository`, check it at the top of `MysteryService.CreateAsync`/`UpdateAsync`, return `ServiceResult<MysteryDetailResponse>.Validation(...)` on failure. This requires widening `IMysteryService.CreateAsync`/`UpdateAsync`'s return types from raw `MysteryDetailResponse`/`MysteryDetailResponse?` to `ServiceResult<MysteryDetailResponse>`, and giving `MysteriesController` the same private `ToErrorResult`/`ToActionResult` pair `MonstersController`/`MinionsController` already each have (not a shared base class — matches the existing per-controller-duplication convention rather than introducing a new one).

**Why this over FluentValidation or a hand-rolled manual-check helper:**

- **FluentValidation is not used anywhere in this codebase today** (confirmed by grep across the whole API project — zero hits for the package or the `AbstractValidator<T>` pattern). Adopting it here would mean introducing a new dependency, a new registration step in `Program.cs`, and a second validation idiom running alongside the DataAnnotations pipeline that's already active for every request type in the app (including, right now, four working reference-data endpoints) — all to solve a problem (blank-string rejection) that `[Required]`'s existing default behavior already solves with one attribute. FluentValidation earns its complexity when validation rules need to be conditional/cross-field/context-dependent in ways DataAnnotations genuinely can't express — none of Mystery's required-field gaps are that shape. If a future domain's required-field pass surfaces a genuinely conditional rule DataAnnotations can't express cleanly, that's the moment to reconsider, not now.
- **A hand-rolled `IsNullOrWhiteSpace` check inside `MysteryService.CreateAsync`/`UpdateAsync` (the "manual validation helper in the service" option) would work, but duplicates a check ASP.NET's model-validation pipeline already performs for free, one layer earlier, before the request even reaches the service** — and it would need to be re-written per-domain, per-field, whereas the DataAnnotations attribute is copy-paste-identical across all five domains' `Name` fields. It also blurs a distinction this codebase's own `ServiceResult<T>` pattern already draws implicitly: every existing `ServiceResult<T>.Validation(...)` call in `MonsterService`/`LocationService`/`BystanderService` is checking *does a referenced entity exist* (a DB round-trip, necessarily service-layer), never *is this string blank* (a pure, DB-free syntax check). Keeping that split explicit — syntax at the model-binding layer, semantics at the service layer — is more consistent with how the codebase already behaves than adding a third place blank-string checks could live.
- **DataAnnotations costs nothing to wire up because it's already wired up.** No `Program.cs` change, no new package, no new middleware — verified live, twice (Mystery's implicit-required inference, and the pre-existing explicit `[Required]` on `CreateAdventureTypeRequest`). The entire fix for the presence/shape half of this pass, for Mystery, is two attributes on one existing record.

**The generalization this establishes for Monster/Minion/Location/Bystander (not designed here, per scope):** each domain's own follow-up pass should (a) add `[Required]` (and any adjacent `[MaxLength]`) to that domain's `Upsert*Request` string fields the same way, and (b) audit that domain's own FK fields for the same "already validated" vs. "silently 500s on a bad ID" split Mystery had between `MonsterTypeId`/`MonsterArchetypeId` (already checked) — Monster itself needs no fix here, it's already correct; the audit is what needs repeating, not the fix.

## Architecture Discussion

### Why the "two categories of required" distinction matters beyond this one pass

`Name` and `AdventureTypeId` are both, informally, "required fields on a Mystery" — but they failed differently and need different fixes, and that difference generalizes. A `string` field's required-ness is a pure syntax question answerable by looking at the value alone (is it null, is it blank after trimming) — DataAnnotations was built for exactly this and ASP.NET already runs it, for free, before any service code executes. A `Guid` FK field's required-ness is not fully answerable without a database round-trip (is *this specific value* a real row) — DataAnnotations cannot express that, and it correctly stays a service-layer concern. The mistake this pass would have made without separating them: treating "add `[Required]` everywhere" as sufficient would have left `AdventureTypeId`'s 500 untouched (a `[Required]` attribute on a non-nullable `Guid` is a no-op — `Guid.Empty` is a valid, non-null `Guid`), and treating "add existence checks everywhere" as sufficient would have meant re-implementing blank-string rejection by hand in every service, discarding a mechanism the framework already provides. Worth carrying this exact split into each of the four follow-up domain passes rather than re-deriving it.

### Why Mystery's own `ServiceResult<T>` gap is worth fixing now, not deferred

`MysteryService.UpsertCountdownAsync` already proves the author of this file knows and uses the `ServiceResult<T>` pattern correctly (`MysteryService.cs:86-113`) — `CreateAsync`/`UpdateAsync` simply predate that convention being applied consistently within the same file. Fixing the `AdventureTypeId` existence-check gap *requires* this change anyway (there's no way to surface a clean `400 Validation` error from a method that returns a raw `MysteryDetailResponse`), so this isn't an additional scope decision so much as a precondition of the FK fix — flagged here explicitly so it isn't mistaken for optional cleanup.

### Why the blank-Name gap is worth fixing over the whitespace-only edge case specifically (not just null)

The null/missing case was already accidentally protected (implicit-required inference) before this analysis started — the actual, currently-live gap is narrower and easy to underestimate: a user (or any API caller) who types or sends only whitespace. The live repro in Background is not hypothetical — two Mysteries with `Name: ""` were created directly against the running dev API during this analysis (and deleted afterward) using the exact payload shape the wizard's own `submitPhase0` would send after its own client-side `.trim()` masks the problem from the user's perspective (the form *looks* like it required something, the server *looks* like it validates, and the record that gets saved is silently broken). This is precisely the kind of gap that's invisible in code review of either layer alone — the client's `Validators.required` genuinely does its job against the untrimmed live value, and the server's implicit-required genuinely does its job against null — and only becomes visible when both are traced through to the same live request.

## Concrete UI Gaps Found

1. **Whitespace-only Name passes every existing validation layer, client and server**, and is silently persisted as `""` — confirmed live. `Validators.minLength(1)` on the untrimmed control (`mystery-create.store.ts:253`) doesn't close this; a trimmed-length re-check would need to run either as a custom Angular validator or, more consistently with the recommended pattern above, be left to the server's new `[Required]` attribute to reject with a normal 400 the wizard's existing submit-error handling already displays.
2. **`AdventureTypeId`'s FK-existence gap is not reachable through today's UI** — the wizard's `<select>` (`mystery-create-mystery-phase.html:13-19`) always sends a real, valid ID once a user makes any selection, and `Validators.required` blocks submission with none selected. This is a real robustness/API-consistency gap (any direct API caller, and any future UI surface for Mystery, would hit the same unhandled 500 Monster/Location/Bystander's own FK fields never expose), but it is not currently a "a user can click through the app and break it" gap — worth being precise about that distinction rather than overstating severity.
3. **No client-side length guard on `Concept` matches the DB's `HasMaxLength(500)`** — the textarea (`mystery-create-mystery-phase.html:26-27`) has no `maxlength` attribute and no Angular validator; a sufficiently long paste would currently 500 the same way the bad-`AdventureTypeId` case does. Adjacent to this pass's core scope (length, not presence) but discovered during the same inventory and cheap to close with the same mechanism (`[MaxLength(500)]`) if Skyler wants it bundled.
4. **`Notes` has no UI surface at all**, in create or edit — not a validation gap (it's correctly optional either way) but a completeness gap worth surfacing since the task asked for a full field inventory.

1. **Should `Concept`'s DB-level 500-character cap be enforced client-side and server-side as part of this same fix, or handled as its own separate follow-up?** It's the same mechanism (`[MaxLength(500)]`) as the `Name` fix and touches the same file/line, so bundling is cheap — but it's a length question, not a required-field question, so it's outside this task's stated scope unless Skyler wants it folded in. **My lean: bundle it** — it's a one-line addition once the file is already being touched for the `Name` fix, and leaving a known 500-producing gap unfixed *right next to* the fix for a sibling gap in the same file would be an odd place to stop.
2. **Should `Notes` get a real UI surface (a wizard phase or a field on some future Mystery edit surface), or is its current "modeled but unreachable" state intentional/deferred on purpose?** This isn't a required-field question (it would stay optional either way) but it came up directly during the field inventory the task asked for. **My lean: no strong opinion either way** — this reads as a product/UX backlog item (does Skyler want a "GM notes" field to actually be usable) rather than an architecture call.
3. **Should a Mystery be allowed to be considered "complete"/ready-to-run with all six Countdown stages blank, or should at least one (or all) be required before some future "ready" state?** Nothing in the schema or UI enforces any minimum today, and this document recommends leaving that as-is because it's a product-scope question, not a data-shape one — explicitly the same shape of question the task's own brief called out ("should a Mystery be allowed to exist with zero clues"), just mapped onto this domain's actual sub-structure (there is no `Clue` entity; `Countdown` stages are the closest analog). **My lean: leave fully optional, as today** — Countdown is explicitly designed in the wizard as something built up over the four dossier phases, and the app already treats a mystery as valid/listable/playable-in-principle with an empty countdown; introducing a stricter "readiness" gate would be new product behavior, not a bug fix.
4. **Should the `AdventureTypeId` existence-check fix (and the accompanying `ServiceResult<T>` retrofit of `MysteryService.CreateAsync`/`UpdateAsync`) ship together with the `Name` blank-string fix, or as a separate, smaller PR?** They're independent at the code level (one's a DTO attribute, the other's a service/repository/controller change spanning three files), but both close gaps found in the same pass. **My lean: same PR** — the `ServiceResult<T>` retrofit is small, well-precedented (copy `MonsterService`'s own shape), and shipping Mystery's required-field fix "half-done" (strings fixed, the one FK still 500s) would be a strange place to stop given both were found together.
