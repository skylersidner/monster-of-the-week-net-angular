# Required-Field Validation — Monster (Phase 2 of a Cross-Domain Initiative)

**Prepared by:** Yoshi (Architect)
**Status:** Decisions locked — Skyler answered all 4 open questions (2026-08-06). Ready for implementation (Bowser + Luigi).
**Date:** 2026-08-06 (revised 2026-08-06)

> This is **Phase 2** of the repeatable required-field-validation initiative started in `docs/updates/mystery-required-fields-validation.md`. The validation *mechanism* was decided and shipped in Phase 1, not re-litigated here: (1) DataAnnotations (`[Required]`, `[MaxLength]`) on `Upsert*Request` DTOs for presence/shape, evaluated automatically by `[ApiController]`'s existing model-validation pipeline; (2) `ServiceResult<T>` + an `XxxExistsAsync` check in the service layer for FK existence. This document applies that mechanism to Monster's own field list and FK audit. No C#/TypeScript files were edited to produce it — every claim below was checked against live source and, where the claim was about runtime behavior, against the actual running dev API (`docker compose up -d postgres` + the already-running `dotnet run` instance on `http://localhost:5225`, confirmed live before testing; all test data created during verification was deleted afterward).

## Background — Confirmed From Current Source

- `Monster` (`src/api/MonsterOfTheWeek.Api/Data/Entities/DomainEntities.cs:79-99`): `Name` (`required string`, non-null), `MonsterTypeId`/`MonsterArchetypeId` (`Guid`, non-null FKs), `Description` (`string?`), `HarmCapacity` (`int`, non-nullable value type), plus `CreatedAt`/`UpdatedAt` (server-set) and navigation collections (`Mysteries` via the `MysteryMonster` bridge table — M:N, no `MysteryId` FK on `Monster` itself — `Attacks`, `Powers`, `Armors`, `Weaknesses`, `CustomMoves`, `Minions`).
- Four sub-resource entities plus the shared custom-move entity, all structurally identical in shape: `MonsterAttack` (`Name` required, `Description` optional, `Harm` int), `MonsterPower` (`Name` required, `Description` optional), `MonsterArmor` (`Name` required, `Description`/`SpecialDescription` optional, `HarmSoak` int, `IsSpecial` bool), `MonsterWeakness` (`Name` required, `Description` optional), `MonsterCustomMove` (`Name` required, `Description` optional) — `DomainEntities.cs:101-173`. Each has a single required `MonsterId` FK back to its parent.
- DB fluent config (`Data/MotwDbContext.cs:123-218`) matches every entity's C# nullability exactly. **Every one of the six `Name` fields above (`Monster` + 5 sub-resource types) carries `.HasMaxLength(255).IsRequired()`** — confirmed by grep across the whole file, not just Monster's own block. No client or server-side length guard exists anywhere for any of them (see live repro below). `Description`/`SpecialDescription` columns have no length cap (unbounded `text`).
- `UpsertMonsterRequest` (`Contracts/ApiContracts.cs:116-121`) and all five sub-resource `Upsert*Request` types (`UpsertMonsterAttackRequest`, `UpsertMonsterPowerRequest`, `UpsertMonsterArmorRequest`, `UpsertMonsterWeaknessRequest`, `UpsertCustomMoveRequest` — `ApiContracts.cs:123-128`) are plain records — **zero DataAnnotations attributes on any of them**, identical gap shape to Mystery's `UpsertMysteryRequest` before Phase 1's fix.
- `UpsertCustomMoveRequest` (`ApiContracts.cs:128`) is **not Monster-specific** — it's the single shared record backing every domain's custom-move create/update endpoints (Monster, Minion, Location, Bystander all reuse it; Mystery has the entity/DTO shape but no API surface, per the Phase 1 doc's Known Gaps). Fixing its `Name` field here closes the identical gap for all four domains' custom moves in one edit — a genuine multiplier, not scope creep, since it's on Monster's own custom-move field list regardless.
- `MonsterListItemResponse`/`MonsterDetailResponse` (`ApiContracts.cs:75-114`) mirror the entities' nullability 1:1; Angular's `models.ts:132-227` mirrors the C# contracts field-for-field, nullable-for-nullable (verified directly, not assumed).

### Current server-side validation — precisely, not approximately, live-verified

- **`Name`'s blank/whitespace gap is confirmed live, identically shaped to Mystery's, and it reproduces across all six entities (Monster + 5 sub-resource types), not just one field.** `POST /api/monsters` with `"name": ""` or `"name": "   "` (valid `monsterTypeId`/`monsterArchetypeId`) returns **`201 Created`**, persisting a Monster with `"name":""`. `POST /api/monsters/{id}/attacks|powers|armors|weaknesses|custom-moves` with `"name": ""` each return **`200 OK`**, persisting the same way. `"name": null` correctly 400s on all six (`[ApiController]`'s implicit-required inference for non-nullable reference types, same free mechanism Phase 1 found already active — zero explicit attributes needed for the null case, but it doesn't cover blank/whitespace).
- **Monster's FK-existence checks are already fully correct — confirmed live, not just by reading the code.** `MonsterService.CreateAsync(Guid mysteryId, ...)`, `CreateAsync(UpsertMonsterRequest, ...)` (the mysteryless overload added in the Standalone Creation Phase 1 initiative), and `UpdateAsync` (`Services/MonsterService.cs:23-128`) **all three** check `MonsterTypeExistsAsync`/`MonsterArchetypeExistsAsync` and return `ServiceResult<MonsterDetailResponse>.Validation(...)` on failure, before any DB write — this closes the exact asymmetry Mystery's `CreateAsync`/`UpdateAsync` had (Phase 1's core finding). Live-verified three ways: a syntactically-invalid-but-nonexistent `monsterTypeId` → clean `400 {"message":"MonsterType ... does not exist."}`; `monsterTypeId` omitted entirely (binds to `Guid.Empty`) → the same clean `400` (the existence check catches `Guid.Empty` correctly, since no row has that id — no FK constraint violation, no 500); `monsterTypeId: ""` → a clean `400` from JSON deserialization itself (empty string isn't a valid `Guid`, caught before model binding completes). **None of the three produces an unhandled 500** — Monster does not have Mystery's `AdventureTypeId` gap. This confirms the Phase 1 doc's "head-start" note was correct and is now independently re-verified, not just carried forward.
- Monster's sub-resources need no analogous FK-existence work: `CreateAttackAsync`/`CreatePowerAsync`/`CreateArmorAsync`/`CreateWeaknessAsync`/`CreateCustomMoveAsync` (`MonsterService.cs:147-419`) each check only `MonsterExistsAsync` (their one real FK, the parent) before writing — already correct, already `ServiceResult<T>`-wrapped. `AssignAttackWeaponTagAsync` (`MonsterService.cs:207-233`) additionally checks `WeaponTagExistsAsync` before assigning a tag — also already correct. **The FK-existence half of the required-field pattern needs zero backend changes for Monster.** This is the legitimate "nothing to fix here" outcome the initiative anticipated (Phase 1's own closing note: "Monster itself needs no fix here, it's already correct — the audit is what needs repeating, not the fix").
- **A real, adjacent length-overflow gap, worse than Mystery's `Concept` case because it sits on the *required* field itself, not an optional one.** `POST /api/monsters` with a 300-character `name` (DB cap is 255) returns an **unhandled `500`** (Postgres `data too long for column`, surfaced through `Program.cs`'s generic exception handler) — live-reproduced, no partial row persisted (confirmed by re-listing `/api/monsters` afterward). This is the identical shape to Mystery's `Concept` gap (Phase 1, Known Gaps) but present on all six of Monster's `Name` fields, and on the field the fix is already adding `[Required]` to — meaning the same DTO edit is the natural place to close it. See Field-by-Field Recommendation and Open Questions.
- **A real, previously-undocumented client-side asymmetry inside `MonsterFormComponent` itself**, found by reading the form definition, not inferred: `monsterTypeId`'s control (`shared/monster-form/monster-form.ts:40`) has **no validators at all** — `this.formBuilder.nonNullable.control('')` — while the structurally identical `monsterArchetypeId` control on the very next line **does** carry `Validators.required`. Both are required `Guid` FKs at every other layer (DB `.IsRequired()`, service-layer existence check). A user can click "Create Monster"/"Save Monster" with no Monster Type selected; `MonsterFormComponent`'s own `onSubmit()` guard (`monsterForm.invalid` check) never catches it because the control is never invalid. This is not a hypothetical: the component's own spec file (`monster-form.spec.ts:72-78`) asserts `name.touched` and `monsterArchetypeId.touched` after an invalid-submit attempt but never asserts anything about `monsterTypeId` — the gap wasn't caught because nothing ever checked for it, not because it's edge-case-only.
- **No visual required-field indicator convention exists anywhere in the Monster feature**, unlike Mystery's wizard (`<span class="text-danger">*</span>` next to `name`/`adventureTypeId`'s labels, Phase 1 doc). Grepped `monster-form.html`, `monster-create.html`, `monster-detail.html` for the literal `text-danger">*` pattern used elsewhere in the app — zero matches. `Name`, `Harm Capacity`, and `Monster Archetype` all already carry `Validators.required` today (and have since before this pass) with no visual cue distinguishing them from the genuinely-optional `Description`/`Monster Type` fields. This predates this pass — not introduced by it — but is a real completeness gap surfaced by the same inventory this task asked for.

## Recommended Validation Pattern

**Unchanged from Phase 1 — this pass applies it, doesn't redesign it.** Two layers, neither new:

1. **Presence/shape of a scalar value → DataAnnotations on the `Upsert*Request` record**, evaluated automatically by `[ApiController]`'s existing model-validation pipeline. For Monster: add `[param: Required, MaxLength(255)]` to `Name` on **six** records (`UpsertMonsterRequest`, `UpsertMonsterAttackRequest`, `UpsertMonsterPowerRequest`, `UpsertMonsterArmorRequest`, `UpsertMonsterWeaknessRequest`, `UpsertCustomMoveRequest`), matching `CreateAdventureTypeRequest`'s already-proven precedent in the same file. Optionally `[param: Range(0, int.MaxValue)]` on `HarmCapacity` (`UpsertMonsterRequest`), `Harm` (`UpsertMonsterAttackRequest`), `HarmSoak` (`UpsertMonsterArmorRequest`) — see Open Questions.
2. **Existence/validity of a referenced entity → stays in the service layer via `ServiceResult<T>`.** **No changes needed for Monster** — `MonsterTypeExistsAsync`, `MonsterArchetypeExistsAsync`, `MysteryExistsAsync`, `MonsterExistsAsync`, `WeaponTagExistsAsync` are all already correctly wired, already `ServiceResult<T>`-wrapped, and live-verified to never 500 on a bad/missing/zero-value FK. This is the legitimate "the audit found nothing to fix" outcome for this half of the pattern.

**Why sub-resource fields are in scope for this same pass, not a separate follow-up (the judgment call the task asked me to make explicitly):**

Monster has four sub-resource types plus the shared custom-move type that weren't in scope for Mystery (which only had Countdown, already covered). I'm treating all five as in-scope for this same pass, for four reasons:

1. **The gap is identical in shape and identical in fix** to Monster's own top-level `Name` gap — live-verified to reproduce on all five create-sub-resource endpoints, closed by the exact same one-line `[param: Required, MaxLength(255)]` addition to the exact same file already being touched for `UpsertMonsterRequest`.
2. **Zero incremental FK-existence work is needed.** Every sub-resource create method already checks only `MonsterExistsAsync` (its one real FK), already correctly. There's no service-layer risk or design decision hiding in the sub-resources — it's presence/shape only, the cheapest half of the pattern.
3. **`UpsertCustomMoveRequest` is shared cross-domain infrastructure.** Fixing it here closes the identical gap for Minion, Location, and Bystander custom moves in the same edit — a genuine multiplier that *reduces* each of those three domains' own future required-field passes by one field, not scope creep against this one.
4. **Deferring them would mean re-opening this exact file (`ApiContracts.cs`) and this exact service (`MonsterService.cs`) a second time** for a fix that's mechanically identical to the one already being made, with no new information a "wait and see" approach would surface in the meantime.

The one place I'm *not* extending scope: **Minion's own sub-resources** (`MinionAttack`/`MinionPower`/`MinionArmor`/`MinionWeakness`, separate `Upsert*Request` records) are structurally identical to Monster's but belong to Minion's own domain and its own future pass — not touched here, consistent with the initiative's one-domain-per-phase framing.

## Architecture Discussion

### Why this phase found "nothing to fix" on the FK-existence half, and why that's not a wasted audit

Phase 1's own closing note predicted this: "Monster itself needs no fix here, it's already correct — the audit is what needs repeating, not the fix." This phase re-verified that prediction rather than trusting it — reading `MonsterService.cs` in full (not spot-checking) and live-testing all three of `Guid.Empty`, an omitted field, and an empty-string field against `monsterTypeId`, none of which 500 the way Mystery's `AdventureTypeId` did before its fix. The value of the re-check wasn't finding a new bug — it's confirming a "this is already fine" claim is still true after however much has changed in `MonsterService.cs` since Phase 1's cross-domain spot check was written (in this case: an entire new `CreateAsync` overload was added by the Standalone Creation Phase 1 initiative, after the spot check ran — and it inherited the correct pattern). A prediction that turns out true on re-check is still worth re-checking; a stale "probably fine" note is exactly the kind of thing that silently rots.

### Why the `[Range]` recommendation is new to this phase and wasn't part of Phase 1's pattern

Mystery has no `int` fields at all — every field is a string or a countdown stage. Monster's three `int` fields (`HarmCapacity`, `Harm`, `HarmSoak`) surface a validity question DataAnnotations can express just as cleanly as `[Required]`, but that Phase 1 never had occasion to recommend: an `int` is always "present" (no null/missing case exists for a non-nullable value type), but it can still be *invalid* in a domain sense (negative harm makes no sense for this game's rules). This isn't a new category of the two-layer split from Phase 1 (presence/shape vs. existence/validity) — it's a second kind of *presence/shape* question, still resolvable with zero DB round-trip, still belongs at the DataAnnotations layer. Worth carrying forward: any future domain pass with numeric fields should ask this question too, not just the string-blank question.

### Why the `MonsterTypeId` client-side gap is a bug fix, not a product question

Unlike the `[MaxLength]`/`[Range]` bundling questions below (genuinely Skyler's call — they're about how strict validation *should* be), the missing `Validators.required` on `monsterTypeId` isn't a scope decision — it's an inconsistency within a single, already-shipped component, where the sibling field one line below has the validator this one is missing, and every other layer of the stack (DB, service) already treats it as required. There is no version of "leave `monsterTypeId` optional" that's internally consistent with the rest of the system. This is listed as a concrete UI gap to fix, not an open question.

## Open Questions Left to Skyler

1. **Should `[MaxLength(255)]` be bundled into the same change as `[Required]` on all six `Name` fields, or handled as its own follow-up?** Same shape of question Phase 1 asked about Mystery's `Concept` field, which Skyler answered "bundle." **My lean here is stronger than Phase 1's**: this isn't an optional field's length cap, it's the *required* `Name` field's own cap, live-reproduced as an actual unhandled `500` during this pass's verification (not hypothetical). Recommend applying Phase 1's precedent directly rather than re-litigating: bundle `[MaxLength(255)]` alongside `[Required]` on all six records in the same edit, plus a matching `maxlength="255"` HTML attribute on the six corresponding Name inputs (Concrete UI Gap 3).
2. **Should `[Range(0, int.MaxValue)]` be added to `HarmCapacity`/`Harm`/`HarmSoak`?** New question this phase — Mystery had no numeric fields to raise it. Nothing currently exploits a negative value (this is a data-integrity/domain-sanity question, not a reproduced bug), but the client already treats negative values as invalid (`Validators.min(0)`) with no server-side backstop. **My lean: yes, bundle it** — same file, same mechanism, same DataAnnotations pass already touching these three records for the `Name` fix, and it closes a real (if currently harmless) gap between client and server assumptions.
3. **Should `MonsterArmor.SpecialDescription` become required whenever `IsSpecial` is `true`?** A genuine conditional-required product question, not a bug — today `IsSpecial: true` with a blank `SpecialDescription` renders fine (guarded `@if`) and isn't reachable as broken UI. **My lean: leave uncoupled, as today** — this is a stricter product rule than "does this field exist," parallel to Phase 1's Countdown-completeness question, which Skyler declined to add. Flagging for symmetry with that precedent, not because I see new evidence favoring it.
4. **Should the Monster feature adopt the asterisk required-field-indicator convention Mystery's wizard already uses?** Not a required-field-*validation* question (nothing here changes what's enforced), but it's a real, pre-existing UI-consistency gap surfaced by this inventory. **My lean: no strong opinion** — reads as a Rosalina/UX-polish backlog item rather than an architecture call, same shape as Phase 1's "should `Notes` get a UI surface" question, which Skyler treated as a deferred backlog item rather than in-scope work.

## Addendum — Wizard Coverage Gap Found During Follow-Up Polish (2026-08-06, Luigi)

This doc's audit and implementation scope was explicitly limited to `MonsterFormComponent` (`shared/monster-form/monster-form.ts`) and the two standalone pages (`monster-create.ts`, `monster-detail.ts`) — the Mystery creation wizard's own monster-authoring step (`mystery-create-monster-phase.html`/`mystery-create.store.ts`) was never in scope here (it predates this initiative and was the *source* of the asterisk convention this doc's Concrete UI Gap 4 recommended adopting elsewhere).

When Skyler asked for the same asterisk convention to be extended to the wizard for visual consistency (separate follow-up task, not a re-open of this doc's scope), the wizard's own `monsterForm`/`monsterAttackForm`/`monsterArmorForm` (`mystery-create.store.ts`) turned out to have the **identical class of client-side gap** this doc found in `MonsterFormComponent`: `harmCapacity` (`monsterForm`), `harm` (`monsterAttackForm`), and `harmSoak` (`monsterArmorForm`) each had only `Validators.min(0)`, missing `Validators.required` — the same "structurally-always-present-but-should-still-be-flagged-required" fields this doc's Field-by-Field Recommendation covers for the standalone form. `monsterTypeId` already had `Validators.required` in the wizard's store (no gap there), it just had no visual asterisk yet.

Not a re-audit failure — this doc's stated file scope never included the wizard's store, so this wasn't missed, it was out of bounds. Flagging here only because the bug *class* is identical and a future domain pass (or a wizard-focused pass) should know these three wizard-side gaps were closed already: `mystery-create.store.ts`'s `monsterForm.harmCapacity`, `monsterAttackForm.harm`, and `monsterArmorForm.harmSoak` now all carry `Validators.required` alongside their existing `Validators.min(0)`. Minion-side forms in the same store (`minionForm`, `minionAttackForm`, `minionArmorForm`) were deliberately left untouched, consistent with this doc's own "Minion's own sub-resource field audit is a separate future phase" call.
