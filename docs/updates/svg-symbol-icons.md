# SVG `<symbol>` Sprite for Icons — Evaluation & Organization Plan

**Prepared by:** Luigi (Frontend Developer)
**Requested by:** Skyler Sidner
**Date:** 2026-08-05 (revised 2026-08-06 — Skyler's decisions on all three open questions folded in)
**Status:** Decisions locked — Skyler confirmed the typed `<app-icon>` wrapper, committed to migrating `DomainIconComponent`/`MysterySectionIconComponent` onto the sprite as their own phase (single icon pattern app-wide, no exceptions), and committed to unifying the delete-button hover-styling inconsistency as part of this same work. Ready for implementation planning. No application code changed as part of this document.

---

## Recommendation

**Adopt a single `<symbol>`-based sprite as the source of truth for every SVG icon in the app — no exceptions.** This covers both the app's small library of *action/chrome icons* (delete, edit, close, menu, plus, spinner, search), where real, verified duplication exists (13 byte-for-byte-identical copies of one trash-can `<path>`, plus several one-off inline SVGs in the shell), **and** the two existing shared icon components, `DomainIconComponent` (`shared/domain-icon.component.ts`) and `MysterySectionIconComponent` (`features/mysteries/shared/mystery-section-icon.ts`). Consumption for the generic action/chrome icons stays behind a small typed wrapper component (`<app-icon name="trash" />`), matching this codebase's own established convention rather than scattering raw `<svg><use href="#icon-trash"/></svg>` boilerplate through templates. `DomainIconComponent`/`MysterySectionIconComponent` keep their existing public APIs (`domain`/`kind` inputs, unchanged call sites) and are re-pointed internally to render from the same sprite — callers never see the difference.

**Why this is its own careful phase (Phase 4) rather than a mechanical extension of Phase 1.** Unlike the trash icon, `DomainIconComponent` and `MysterySectionIconComponent` don't have a duplication problem today — each icon's markup is written exactly once, in one `@switch` case, and reused via the component wherever needed (23 combined call sites, zero duplicated path data). Migrating them is therefore not paying down duplication; it's a deliberate consistency call (one icon-rendering mechanism app-wide, not two) that Skyler has now made, and it comes with two real, concrete risks worth calling out up front rather than discovering mid-migration:
- `MysteryDetailComponent`/`MysteryCreateComponent` specs assert exact `app-mystery-section-icon` element counts (`mystery-detail.spec.ts:142-143`, `mystery-create.spec.ts:110,139-140`). Verified these assertions target the custom element tag itself (`element.querySelectorAll('app-mystery-section-icon')`), not its internal rendered markup — so as long as the component keeps being instantiated the same number of times in the same host templates (true here; only its own internal template changes), these assertions stay valid unchanged. See Phase 4 below for the full reasoning.
- `mystery-section-icon.ts` sizes itself via a `--mystery-section-icon-size` CSS custom property applied at the `:host` level (`height`/`width: var(--mystery-section-icon-size, 1rem)`) plus a `.icon { height: 100%; width: 100%; }` inner rule. Because this sizing is host- and wrapper-level, not tied to the SVG's internal content, it's unaffected by swapping the `@switch`-rendered inline path for a `<use>` reference — see Phase 4 for the mechanics.

**Why not full Angular Material icon registry (`MatIconRegistry.addSvgIconSet`):** Angular Material isn't a dependency anywhere in this app (`package.json` has no `@angular/material`; grepped `mat-icon`/`MatIcon`/`matIcon` across the whole `src/app` tree — zero hits). Pulling in Material solely for its icon-sprite loading mechanism would mean adopting an entire component library's theming/CDK surface as a side effect, which is a much bigger decision than "how are icons organized" and isn't warranted by an app this size. `MatIconRegistry` is functionally the same idea as a hand-rolled `<symbol>` sprite + wrapper component anyway (register a sprite, reference by name) — the hand-rolled version gets the same benefit with none of the new dependency.

**Delete-button hover styling — a second, related inconsistency found during this scan.** `monsters-list.html`, `monster-detail.html`, and `minion-detail.html` use a shared `.action-btn`/`.action-btn--delete` class pair with a compound `:hover:not(:disabled)` selector defined in each page's `.scss` (`@apply bg-danger-subtle text-danger`, etc.) — this is the pattern the recent "fixing delete hover styling" commit (`370dfd0`) touched, because Tailwind can't express a compound pseudo-selector as a single template class. `minions-list.html`, `locations-list.html`, `bystanders-list.html`, and `mysteries-list.html` instead apply `hover:bg-danger-subtle hover:text-danger` directly as Tailwind utility classes on the button (they have no `[disabled]` state to combine with, so no compound selector is needed). Both approaches already rely on the icon's `fill="currentColor"` to pick up the button's text color on hover — this matters for the sprite decision below, since `<use>` preserves `currentColor` inheritance identically to inline `<svg>` (well-established cross-browser behavior, as long as the `<symbol>` itself doesn't hardcode a `fill`/`stroke`), so migrating icon *storage* to a sprite (Phase 1) doesn't by itself require touching the `.action-btn` SCSS at all — the two inconsistent hover mechanisms are a separate, adjacent problem, resolved on its own terms in Phase 2 below.

## Organization Plan

### Source of truth

A single hand-maintained sprite, mounted once in `layout/page-layout/page-layout.html` (the app shell — confirmed the one component guaranteed to render on every route, same reasoning the theming plan used to justify treating shell changes as highest blast-radius). Concretely:

- New `shared/icons/icon-sprite.component.ts` (`app-icon-sprite`) — a template-only component whose entire template is one `<svg style="display:none" aria-hidden="true">` containing every `<symbol id="icon-{name}" viewBox="...">...</symbol>` definition, one per icon.
- Mounted exactly once, near the top of `page-layout.html`'s root `<div>`. It renders nothing visible (`display:none`); it only exists so every `<use href="#icon-...">` elsewhere in the DOM has something to resolve against. Because `page-layout.html` is the routed shell (not `app.html`, which is a bare `<router-outlet>`), this guarantees the sprite exists before any routed page's icons render.
- This stays a **build-time-inert, hand-maintained file** — no `raw-loader`, no `svg-sprite`/`svgo` build step, no change to `angular.json`/`.postcssrc.json`. That matches this app's current tooling reality (nothing today processes `.svg` files at build time — there are none in the tree) and avoids adding a new pipeline dependency for what is, today, a ~10-icon library. If the icon count grows enough that hand-maintaining a sprite file becomes painful, revisit with a build-time tool then — not preemptively.
- Rejected alternative: fetching an external `public/icons/sprite.svg` at runtime and injecting it via `innerHTML`. This is the standard technique for larger icon libraries needing separate HTTP caching, but it adds an async load-order hazard (icons can render before the sprite arrives, causing a flash of missing icons) that would need its own mitigation — the same shape of problem the theming plan's Phase 8 (FOUC prevention) had to solve separately for the dark-mode class. Not worth that complexity at this app's current icon count; an inline-in-the-shell sprite has no load-order problem at all.

### Consumption

A small typed wrapper component, mirroring `DomainIconComponent`'s existing shape:

```ts
// shared/icons/icon.component.ts
export type IconName = 'trash' | 'pencil' | 'close' | 'menu' | 'plus' | 'spinner' | 'search';

@Component({
  selector: 'app-icon',
  standalone: true,
  host: { class: 'inline-flex items-center justify-center' },
  template: `<svg class="h-full w-full" aria-hidden="true"><use [attr.href]="'#icon-' + name" /></svg>`,
})
export class IconComponent {
  @Input({ required: true }) name!: IconName;
}
```

Call sites become `<app-icon name="trash" class="h-5 w-5" />` in place of the current 30+ lines of duplicated `<svg>`/`<path>` markup. This keeps the same "typed wrapper component" consumption convention as `DomainIconComponent`/`MysterySectionIconComponent` — a caller gets TypeScript union-type checking on the icon name instead of a bare string in an `href`, and a future contributor adding an icon follows a pattern they've already seen twice in this codebase rather than learning a new one.

### Naming convention

Now that `DomainIconComponent`/`MysterySectionIconComponent` are in scope (Phase 4), the sprite holds icons from three distinct sources, and a flat, unprefixed namespace would collide: `MysterySectionIconKind` already has `monster`/`minions`/`locations`/`bystanders` kinds that are visually distinct, differently-styled icons from `DomainIconComponent`'s `monsters`/`minions`/`locations`/`bystanders` nav keys (same/near-same words, different art — the nav icons are the sidebar/search-result glyphs, the mystery-section icons are the thinner, `currentColor`-sized glyphs used inside the mystery dossier). Symbol IDs are namespaced by source to keep this collision-free and to make it obvious at a glance which component a given symbol belongs to:

- **Generic action/chrome icons** (the `IconComponent`/`IconName` set): `icon-{kebab-case-name}` — unprefixed, as originally proposed (`icon-trash`, `icon-pencil`, `icon-close`, `icon-menu`, `icon-plus`, `icon-spinner`, `icon-search`). These are the only icons a template author references directly via `<app-icon name="...">`.
- **Domain/nav icons** (`DomainIconComponent`'s internal use only): `icon-nav-{key}`, one per existing `NavIconKey` (`icon-nav-dashboard`, `icon-nav-data-admin`, `icon-nav-mysteries`, `icon-nav-monsters`, `icon-nav-minions`, `icon-nav-locations`, `icon-nav-bystanders`).
- **Mystery-section icons** (`MysterySectionIconComponent`'s internal use only): `icon-mystery-{kind}`, one per existing `MysterySectionIconKind` (`icon-mystery-mystery`, `icon-mystery-countdown`, `icon-mystery-day`, `icon-mystery-shadows`, `icon-mystery-sunset`, `icon-mystery-dusk`, `icon-mystery-nightfall`, `icon-mystery-midnight`, `icon-mystery-monster`, `icon-mystery-minions`, `icon-mystery-locations`, `icon-mystery-bystanders`).

**The `IconName` union does *not* grow to include the domain/mystery-section icon names.** `IconName` stays scoped to the generic action/chrome icon set — it's the type that backs the one component (`IconComponent`) app templates call directly. `DomainIconComponent`/`MysterySectionIconComponent` keep their own existing, separate input types (`domain: string` normalized via `NavIconKey`, `kind: MysterySectionIconKind`) exactly as today; only their *internal* template swaps from a `@switch` block to a namespaced `<use href="#icon-nav-" + ...>`/`<use href="#icon-mystery-" + ...>` lookup. A caller of `<app-domain-icon>` or `<app-mystery-section-icon>` never sees or needs `IconName` at all — three call-site APIs, one physical sprite file underneath.

### Adding a new icon

1. Add a `<symbol id="icon-{name}" viewBox="...">...</symbol>` to `icon-sprite.component.ts`'s template.
2. Add `{name}` to `IconName` in `icon.component.ts`.
3. Use `<app-icon name="{name}" />` at the call site.

No build step, no asset-pipeline registration — the same two-file edit regardless of how many templates end up using the new icon. This recipe is for the generic `IconName` set; adding a new **nav** or **mystery-section** icon instead means adding a `<symbol id="icon-nav-{key}">`/`<symbol id="icon-mystery-{kind}">` to the sprite and extending that component's own `NavIconKey`/`MysterySectionIconKind` union — `IconName` is untouched either way (see Naming convention above).

### Phased rollout

Following the Goal/Risk convention established in `docs/theming/theming-plan.md`'s Phase Plan. Five phases total — icon-storage migration (0, 1, 3, 4) and the hover-styling unification (2) are sequenced together since they touch overlapping files, but they're independent concerns and could ship as separate PRs.

**Phase 0 — Sprite infrastructure.** Build `IconSpriteComponent`, `IconComponent`, mount the sprite in `page-layout.html`. No existing template is touched yet — purely additive, dead code until Phase 1 consumes it.
**Risk:** Low — additive only, nothing existing is removed or repointed.

**Phase 1 — Migrate the duplicated trash icon.** Swap all 13 occurrences (`minions-list.html`, `locations-list.html`, `bystanders-list.html`, `monsters-list.html`, `mysteries-list.html`, `monster-detail.html` ×4, `minion-detail.html` ×4) onto `<app-icon name="trash" ...>`. This is the phase that actually pays down the real duplication found above.
**Risk:** Low — mechanical, visually identical swap (same `viewBox`/path, same `currentColor` fill). Icon markup only — the hover-styling classes on the *wrapping* `<button>` are untouched here; see Phase 2.

**Phase 2 — Unify delete/edit-button hover styling onto one convention.** Resolves the `.action-btn` vs. plain-Tailwind inconsistency flagged in the inventory. **The `.action-btn`/`.action-btn--delete` SCSS-class pattern wins**, for two reasons: Tailwind genuinely cannot express the compound `:hover:not(:disabled)` selector as a single utility class (confirmed — this is exactly why the SCSS variant exists at all on the three pages that already have it), and consistency argues for one mechanism everywhere rather than "SCSS class where a disabled state happens to exist today, plain Tailwind utilities elsewhere" — a distinction that's an implementation accident, not a meaningful difference between these buttons. Applied uniformly (including to buttons/links with no `[disabled]` binding today, e.g. `minions-list`'s delete button or `mysteries-list`'s edit link) rather than only where currently load-bearing, so every consumer's CSS is copy-paste identical and future-proofed if a disabled state is ever added.
  - Extend the class family with `.action-btn--edit` (`@apply bg-accent-subtle text-accent` on `:hover:not(:disabled)`), needed for `mysteries-list.html`'s edit-pencil link, the one edit affordance in this set.
  - **Consolidate the rule definitions into `src/styles.css` as a single global block, rather than duplicating the same 3-line `@apply` rules per component `.scss` file.** These classes have zero component-specific content — every current/future consumer applies the identical `@apply` targets — so per-file duplication (already happening 3× today in `monsters-list.scss`/`monster-detail.scss`/`minion-detail.scss`, each byte-for-byte the same `.action-btn`/`.action-btn--delete` block plus `@reference` boilerplate) is duplication for its own sake, not a component-scoping requirement. This app has no existing "shared partial `.scss` file" convention to split into instead (`src/styles.css` is the sole global stylesheet; the `stylePreprocessorOptions.includePaths: ["src/styles"]` entry in `angular.json` points at a directory that doesn't currently exist), so global CSS already means "add to `styles.css`" in this codebase, not a new pattern.
  - Migration: delete the `.action-btn`/`.action-btn--delete` blocks from `monsters-list.scss`, `monster-detail.scss`, `minion-detail.scss` (superseded by the global rule; `monster-detail.scss` and `monsters-list.scss` additionally have an `.action-btn:disabled` rule to fold in — `minion-detail.scss` doesn't have one and its buttons instead rely on inline `disabled:cursor-not-allowed disabled:opacity-40` Tailwind classes today, a small pre-existing divergence worth reconciling onto the same `.action-btn:disabled` rule in this same pass rather than left mixed). Add `class="action-btn action-btn--delete"`/`class="action-btn action-btn--edit"` to the four files currently using plain Tailwind hover utilities (`minions-list.html`, `locations-list.html`, `bystanders-list.html`, `mysteries-list.html`), removing their inline `hover:bg-danger-subtle hover:text-danger`/`hover:bg-accent-subtle hover:text-accent` classes in favor of the shared class. No new per-component `.scss` files needed for those four.
**Risk:** Low — pure CSS-class rename plus a global-stylesheet consolidation; every button's computed hover appearance is unchanged (same tokens, same colors), only *which* mechanism produces it changes. Verify visually across all 7 affected pages in both themes (light/dark) before merging, same bar the theming plan used for its own Phase 4/5 sweeps.

**Phase 3 — Migrate the one-off shell/chrome icons.** `mysteries-list.html`'s edit-pencil, `header-search.html`'s magnifying glass, and `page-layout.html`'s hamburger/close/plus/spinner (4 icons, one file). Centralizing these has no duplication payoff today, but it means every icon in the app follows one convention going forward rather than two (sprite for some, inline for others indefinitely).
**Risk:** Low-medium — no duplication risk (each icon has one call site), but `page-layout.html` is the shell rendered on every route, so a mistake here has the widest blast radius of any single file in this plan, same caution the theming plan gave its own Phase 1 shell work. Worth a quick visual sanity pass across a few pages before merging, though this doesn't rise to the theming plan's "execute on a feature branch" bar since it's pure icon-markup substitution with no token/CSS-cascade risk. `page-layout.spec.ts:133` asserts `.api-modal svg` is truthy for the spinner — stays valid unchanged, since `<app-icon>` still renders a wrapping `<svg>`.

**Phase 4 — Re-point `DomainIconComponent`/`MysterySectionIconComponent` onto the sprite internally.** Committed — one icon-rendering mechanism app-wide, no exceptions (see Recommendation above). Concretely:
  - `domain-icon.component.ts`: replace the `@switch (normalizedDomain())` block's 7 inline `<svg>` cases with a single template — `<svg class="h-5 w-5" width="20" height="20" [attr.viewBox]="...VIEWBOX_BY_KEY[normalizedDomain()]" aria-hidden="true"><use [attr.href]="'#icon-nav-' + normalizedDomain()" /></svg>` (each nav icon's `viewBox` differs today — `0 0 24 24` for all seven, confirmed identical, so this can simplify to a single hardcoded `viewBox="0 0 24 24"` rather than a lookup map). The `domain`/`normalizedDomain()` input and its singular→plural normalization map are completely unchanged — this only touches the template.
  - `mystery-section-icon.ts`: replace the `@switch (kind)` block's 12 inline cases with `<svg class="icon" viewBox="0 0 24 24" aria-hidden="true"><use [attr.href]="'#icon-mystery-' + kind" /></svg>`. The `:host`/`.icon` styles (the `--mystery-section-icon-size` custom property and the `height: 100%; width: 100%` rule) are untouched — they size the wrapping `<svg class="icon">` element itself, not its internal content, so they apply identically whether that `<svg>` contains a `@switch`-selected inline `<path>` or a `<use>` reference. No sizing-contract risk.
  - `kind`/`normalizedDomain()` values map directly to symbol-name suffixes (`kind="day"` → `#icon-mystery-day`, `normalizedDomain()==='monsters'` → `#icon-nav-monsters`) — no translation table needed beyond the existing values, since the naming convention (above) was chosen to match each component's existing key/kind vocabulary exactly.
  - Spec impact: verified `mystery-detail.spec.ts:142-143` and `mystery-create.spec.ts:110,139-140` assert `element.querySelectorAll('app-mystery-section-icon').length`/`.countdown-list app-mystery-section-icon`/etc. — these count instantiations of the custom element itself in the *host* templates (`mystery-detail.html`, `mystery-create-dossier.html`, etc.), which this phase does not touch or reduce. **No spec changes needed for those assertions**; run `npm run test -- --watch=false` after the change to confirm rather than assume, per this codebase's usual verification bar, but there's no reason to expect a regression.
**Risk:** Low-medium. Technically low risk per the analysis above (host-level sizing untouched, spec assertions target the wrong DOM level to be affected), but real spec-coupling to double-check rather than skip, and this phase's blast radius includes every page that renders the sidebar/search results (`DomainIconComponent`, effectively every route) plus the entire mystery dossier/wizard (`MysterySectionIconComponent`) — worth the same "verify on a branch, visual pass in both themes" discipline as Phase 3, even though the underlying change is mechanical.
