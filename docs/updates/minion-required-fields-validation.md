# Required-Field Validation — Minion (Phase 3 of a Cross-Domain Initiative)

**Prepared by:** Yoshi (Architect)
**Status:** Decisions locked — Skyler answered all 6 open questions "yes" (2026-08-06). Ready for implementation (Bowser + Luigi).
**Date:** 2026-08-06 (revised 2026-08-06)

> This is **Phase 3** of the repeatable required-field-validation initiative started in `docs/updates/mystery-required-fields-validation.md` and applied to Monster in `docs/updates/monster-required-fields-validation.md`. The validation *mechanism* was decided in Phase 1 and is not re-litigated here: (1) DataAnnotations (`[Required]`, `[MaxLength]`, `[Range]`) on `Upsert*Request` DTOs for presence/shape, evaluated automatically by `[ApiController]`'s existing model-validation pipeline; (2) `ServiceResult<T>` + an `XxxExistsAsync` check in the service layer for FK existence. This document applies that mechanism to Minion's own field list and FK audit. No C#/TypeScript files were edited to produce it — every claim below was checked against live source and, where the claim was about runtime behavior, against the actual running dev API (`docker compose` postgres already up, an already-running `dotnet run` instance on `http://localhost:5225`, confirmed live before testing; all test data created during verification was created via `POST` and deleted afterward via `DELETE /api/minions/{id}`, confirmed gone with a follow-up `404`).

### Current server-side validation — precisely, not approximately, live-verified

- **A real, previously-undocumented finding: Minion's own top-level `Name` blank/whitespace gap is already closed today — but via a hand-rolled service-layer check, not the DataAnnotations mechanism this initiative established.** `MinionService.CreateAsync`/`UpdateAsync` (`Services/MinionService.cs:30-33`, `70-73`) both contain `if (string.IsNullOrWhiteSpace(request.Name)) return ServiceResult<MinionDetailResponse>.Validation("Name is required.");` — live-verified: `POST /api/monsters/{monsterId}/minions` with `"name": ""`, `"name": "   "`, and `"name": null` all return a clean `400` today (the first two via this hand-rolled check, the null case via `[ApiController]`'s implicit-required inference, same free mechanism every other domain gets). **This is exactly the "hand-rolled manual-check helper in the service" option Phase 1's Architecture Discussion explicitly declined in favor of DataAnnotations** ("duplicates a check ASP.NET's model-validation pipeline already does one layer earlier... blurs the existing implicit split... between syntax validation and semantic/FK validation"). It happens to work correctly for the presence/blank question, but — unlike `[MaxLength]` — it does nothing about length, which is why the length gap below still exists on this exact field despite the presence gap being closed. See Field-by-Field Recommendation and Architecture Discussion for why this should still be migrated to the standard mechanism, not left as-is just because it happens to produce the right status code today.
- **A real, live-reproduced length-overflow gap on `Minion.Name` itself, identical in shape to Monster's finding.** `POST /api/monsters/{monsterId}/minions` with a 300-character `name` (DB cap is 255) returns an **unhandled `500`** (Postgres `data too long for column`) — live-reproduced, no partial row persisted. The hand-rolled blank-check above does not and cannot catch this; only a DTO-level `[MaxLength(255)]` (or a repository/DB-level catch, which this codebase doesn't do anywhere) closes it.
- **Minion's FK-existence checks are already fully correct for both of its FKs — confirmed live, not just by reading the code.** `MonsterId` (route parameter, not part of the request body): `MinionService.CreateAsync` checks `MonsterExistsAsync` first and returns `ServiceResult<T>.NotFound(...)` — live-verified with both a syntactically-valid-but-nonexistent `monsterId` and `Guid.Empty` in the route, both cleanly `404`, no 500. `MinionTypeId`: checked via `MinionTypeExistsAsync`, returns `ServiceResult<T>.Validation(...)` — live-verified with a nonexistent id and an omitted field (binds to `Guid.Empty`), both cleanly `400`, no 500. **This matches Monster's "audit found nothing to fix" outcome for the FK-existence half of the pattern** — `IMinionRepository`/`MinionRepository` (`Repositories/IMinionRepository.cs:8,10`) already have both `XxxExistsAsync` methods, already wired, already correct.
- **Minion's four own sub-resource types (`MinionAttack`/`MinionPower`/`MinionArmor`/`MinionWeakness`) have the identical blank/whitespace-`Name` gap Monster's did, confirmed live, not just "by inspection" as Phase 2's Known Gaps table flagged it.** `POST /api/minions/{id}/attacks|powers|armors|weaknesses` with `"name": ""` each return **`200 OK`**, persisting the empty name — none of the four `CreateAttackAsync`/`CreatePowerAsync`/`CreateArmorAsync`/`CreateWeaknessAsync` methods (`Services/MinionService.cs:104-314`) have any blank-check at all, unlike the top-level `CreateAsync`/`UpdateAsync`'s hand-rolled one. `"name": null` correctly `400`s (implicit-required inference, same free mechanism). ## Recommended Validation Pattern

**Unchanged from Phase 1/2 — applied, not redesigned.** Two layers:

1. **Presence/shape of a scalar → DataAnnotations on the `Upsert*Request` record.** For Minion: add `[param: Required, MaxLength(255)]` to `Name` on **five** records (`UpsertMinionRequest`, `UpsertMinionAttackRequest`, `UpsertMinionPowerRequest`, `UpsertMinionArmorRequest`, `UpsertMinionWeaknessRequest`) — one fewer than Monster's six, because the sixth (`UpsertCustomMoveRequest`) is shared cross-domain infrastructure already fixed in Phase 2. Add `[param: Range(0, int.MaxValue)]` to `HarmCapacity` (`UpsertMinionRequest`), `Harm` (`UpsertMinionAttackRequest`), `HarmSoak` (`UpsertMinionArmorRequest`).
2. **Existence/validity of a referenced entity → stays in the service layer via `ServiceResult<T>`. No changes needed for Minion** — `MonsterExistsAsync`, `MinionTypeExistsAsync` are both already correctly wired, already `ServiceResult<T>`-wrapped, live-verified to never 500. Same "audit found nothing to fix" outcome Phase 2 found for Monster's FKs.

**One piece of cleanup this phase needs that Phase 1/2 didn't**: remove the hand-rolled `string.IsNullOrWhiteSpace(request.Name)` checks in `MinionService.CreateAsync`/`UpdateAsync` (`Services/MinionService.cs:30-33`, `70-73`) once `[Required]` is added to `UpsertMinionRequest.Name`. Leaving both in place isn't harmful (the DataAnnotations check runs first and would 400 before the service method is ever entered, so the hand-rolled check would become genuinely dead code, never reached) — but leaving dead code that duplicates a now-redundant check is worse than removing it, and matches Phase 1's explicit reasoning for declining hand-rolled checks in the first place.

**Why sub-resource fields are in scope for this same pass:** Same four reasons Phase 2 gave for Monster, all of which hold identically here: identical gap shape (live-verified on all four remaining create endpoints), zero incremental FK-existence work (each already only checks its parent's `MinionExistsAsync`), the custom-move DTO fix is already banked (not redone, just confirmed), and deferring would mean reopening the same file a second time for a mechanically identical fix.

## Architecture Discussion

### Why the hand-rolled `Name` check is worth removing even though it already "works"

It would be easy to read the live-verification results (blank/whitespace `Name` already 400s) and conclude Minion needs no `Name` fix at all — that would be a mistake for two reasons. First, and most concretely: **the hand-rolled check only solves the presence half of the problem, not the shape half** — it does nothing to stop the live-reproduced 500 on a 300-character name, which is exactly why `[MaxLength(255)]` is still needed regardless of what happens to the existing check. Second, and more structurally: this codebase now has a single established convention for this exact problem (DataAnnotations at the model-binding layer), used consistently across Mystery, Monster, and four of Minion's own five `Name` fields (via the shared custom-move DTO) — leaving one field (`Minion.Name`) validated by a different, explicitly-previously-rejected mechanism, for no reason other than "it happens to already work," is the kind of inconsistency that makes the next person auditing this codebase re-derive the same "should we use DataAnnotations or a manual check" question from scratch instead of finding one answer everywhere. Fixing it now, while the file is already being touched for the `MaxLength` addition, costs nothing extra.

### Why this phase's FK-existence audit confirms rather than contradicts the initiative's running prediction

Phase 1 predicted Monster would need no FK-existence fix; Phase 2 re-verified that live and found it true. This phase re-verified the same prediction for Minion's two FKs (`MonsterId`, `MinionTypeId`) independently — both already correct, both live-tested against the same three failure shapes (`Guid.Empty`/omitted/nonexistent) used in every prior phase. Three domains in a row (Monster, and now Minion) confirm the FK-existence half of this pattern was gotten right early and consistently in this codebase's service layer — the presence/shape half (DataAnnotations) is where the real, repeatable gap has lived in every phase so far, including this one.

### Why `MinionFormComponent.minionTypeId`'s missing validator is a bug fix, not a product question

Identical reasoning to Phase 2's `MonsterFormComponent.monsterTypeId` finding: every other layer (DB, service) already treats `MinionTypeId` as required, the sibling control (`harmCapacity`) one line below has its own validators, and the component's own spec file's touched-state assertions stop one field short of covering it — there's no internally consistent reading of "leave it optional" here. Listed as a concrete UI gap to fix directly, not deferred to Skyler.
